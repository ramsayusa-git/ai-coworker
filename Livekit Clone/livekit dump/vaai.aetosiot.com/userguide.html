User Guide

Welcome to your Powered By Aetos Techlabs LLP user guide

This guide walks you through every page of your dashboard — from logging in and creating your first AI voice agent, to connecting phone numbers, testing, monitoring calls and fine-tuning settings. Each page is explained step by step, with every option described in plain language. Click any screenshot to enlarge it.

⏱In a hurry? The fastest path to a working agent is the Quick Start (steps 1–5 below). Everything after that is a reference for the rest of the dashboard — dip in whenever you need it.

Logging in & finding your way around

How to sign in to your dashboard, and where everything lives once you’re in.

Logging in

1 Open the login page

Go to your dashboard’s web address in any browser — on a computer, tablet or phone. You’ll see a simple sign-in form.

2 Enter your email and password

Type the email address and password you were given, then click Sign In.

  • Email: your registered email address. This can be the main administrator account or a sub-user account created for you.
  • Password: your account password. You can change it any time from the user menu once you’re logged in.

3 Enter your 2FA code (only if it’s turned on)

If two-factor authentication is enabled for your account, you’ll be asked for a six-digit code from your authenticator app (such as Google Authenticator) after entering your password. Type the code shown in the app and continue. The code changes every 30 seconds, so if it’s rejected, just wait for the next one and try again.

Forgotten your password?

Click the Forgot Password? link below the sign-in button. Enter your email address and, if it matches an account, a password-reset email is sent to you. Click the link in that email and choose a new password.

  • Reset link lifetime: the link in the email works once, and only for one hour. If it expires, just request a new one.
  • Request limit: for security, you can request at most three reset emails per 15 minutes.
  • No email arriving? Password reset needs email sending to be set up in Settings → Email. If it isn’t, ask your administrator to reset your password for you.

Finding your way around

Once you’re in, the layout is the same on every page: a menu down the left side, and a bar across the top.

The left sidebar menu

The sidebar is grouped into sections. Depending on what’s enabled on your system, you’ll see:

  • Core: the everyday pages — Analytics (the home page of charts and stats), Reports, Rooms, Call History, Chat History, Recording/Egress, Tools, Knowledge Base / Memory, Voice Agents and Chatbot Agents.
  • Telephony: phone-related pages — SIP Trunks, Dispatch Rules, Phone Numbers and Campaigns. This whole group only appears once telephony has been set up; before that it shows a small “disabled” badge.
  • Testing: Agent Tester (talk to an agent from your browser), Simulation (automated test conversations) and Improvement Lab.
  • Admin: Settings — where all configuration lives. An Update Available badge appears here whenever a new version of your dashboard is ready to install.
ℹNote: your administrator controls which menu items each user can see (Settings → User Management). If you don’t see a page mentioned in this guide, your administrator may not have given you access to it — it’s not a fault.

The top bar

  • Page title: the left side of the top bar always shows the name of the page you’re on.
  • User Guide (yellow button): opens this guide in a new browser tab, so you can read it side by side with the dashboard.
  • Help button: opens a pop-up with help written specifically for the page you’re currently viewing — a quick reference for every field and button on that page.
  • User menu: the button with your name on the far right. From here you can Change Password or Logout. Sub-user accounts show a small “Sub-User” badge next to the name.
💡Tip: if you ever feel lost, click the Help button first — it always explains the exact page you’re looking at.

How it all fits together

Before diving into the individual pages, here’s the one-line mental model behind every phone call the system handles:

Phone number (bought from your carrier) → SIP trunk (the digital phone line that delivers the call) → dispatch rule (the switchboard entry that decides which agent answers) → voice agent (which must be Running) → the finished call lands in Call History with its transcript, summary, and cost.

Every “my calls aren’t working” problem is a break in one link of that chain, and the chapters of this guide follow it in order. Website chat works the same way, minus the phone parts: a visitor opens the widget → a chatbot agent (which must be Enabled) replies → the conversation lands in Chat History.

First-Time Setup — a fresh dashboard, in order

Just installed? Work through these nine steps once, top to bottom, and you’ll go from an empty dashboard to a live agent answering a real phone number.

Each step below is one paragraph with a pointer to the full chapter that covers it in depth. Steps 1–5 are one-time housekeeping; steps 6–9 get your first agent talking.

1 Whitelist your own IP address

Do this first, before anything else. Go to Settings → Security and add your office/home internet address to the Whitelisted IPs list. The dashboard’s automatic protection bans addresses that mistype passwords or make too many requests — and during setup and testing, that person is most likely to be you. Whitelisting yourself means you can never get locked out of your own system. Details in Settings → Security.

2 Set the timezone

Settings → Server → Time & Date — pick your local timezone. Call timestamps, scheduled reports, campaign schedules and overnight clean-ups all follow it, so set it correctly on day one rather than puzzling over wrong-looking times later. Details in Settings → Server.

3 Add your AI provider API keys

Settings → Integrations/API — paste in a key for at least one AI brain (e.g. OpenAI or Google), one speech-recognition service (e.g. Deepgram), and one voice service (e.g. ElevenLabs), then click each card’s Test button and wait for the green OK. Every agent you build runs on these keys; without them, agents show red health badges and stay silent. Details in Settings → Integrations/API.

4 Connect email and switch on alerts

Settings → Email — enter your SMTP details (or AWS SES), set the From address, and send a Test Email to prove it works. Then open the Notifications section on the same tab and enable the alerts you want — most importantly Service Down Alerts, plus the host and per-service resource alerts that warn you when the server (or one service) runs unusually hot. Email also powers automated Reports, sub-user password resets, and the take-a-message tool. Details in Settings → Email.

5 Check the server resource allocation

Settings → System → Resources — the Suggested Resource Allocation card looks at your server’s actual CPU and memory and recommends how much to give each service (the dashboard, the LiveKit media server, the agent worker, and the rest). On a fresh install it’s worth a minute to review and apply the suggestions — they stop one busy service from starving the others. The warm agent processes option here is also worth knowing: it keeps an agent process pre-loaded so the first call of the day answers faster. Details in Settings → System.

6 Create and start your first agent

Sidebar → Voice Agents → Create Agent. Name it, write its greeting and System Prompt, save — then press Start and wait for the green Running badge. The Quick Start walks this through step by step, and The Agent Editor chapter explains every field.

7 Talk to it in your browser

Before touching phone lines, prove the agent works: open Agent Tester (under Testing), pick your agent, choose Voice mode, and have a conversation through your microphone. Free, instant, and it catches prompt problems early. Details in Agent Tester.

8 Connect your phone line with the Setup Wizard

Telephony → SIP Trunks → Setup Wizard. Pick your carrier, enter the account credentials and phone numbers from their portal, and the wizard creates the inbound trunk, the outbound trunk, and a dispatch rule in one pass — for most people this is the only trunk setup they ever do. Details in SIP Trunks.

9 Point the number at your agent — and turn on recording

Telephony → Dispatch Rules — open the rule the wizard created, make sure Agent is set to your agent, and tick Auto-Record Calls if you want every call recorded (recordings appear on the Recording/Egress page and as a player on each call’s detail page). Save, then ring the number from your mobile: your agent answers, and a minute later the call is in Call History with its transcript and summary. Details in Dispatch Rules.

💡That’s the whole setup. From here it’s refinement: give the agent documents to answer from (Knowledge Base), abilities like transfers and SMS (Tools), automated emails about calls (Reports), and team logins with just-enough access (User Management).

Quick Start — from zero to a working agent

Five short steps: create an agent, start it, point a phone number at it, ring it, and try it from your browser.

⚠Before you start — the AI keys. Agents are powered by third-party AI services, and each service needs its API key saved in Settings → Integrations/API before an agent can use it. A brand-new system needs at least one key for an AI brain (e.g. OpenAI or Google), one for speech recognition (e.g. Deepgram), and one for a voice (e.g. ElevenLabs) — and it’s worth clicking each card’s Test button to prove the key works. If this hasn’t been done, your new agent will show a red health badge and stay silent. If you can already see green health badges on the Voice Agents page, you’re good to go.

1 Create your first agent

In the sidebar, click Voice Agents, then the green Create Agent button. The agent editor opens. You only need to fill in three things to get going — everything else has sensible defaults:

  • Name: what you’ll call this agent in the dashboard, e.g. “Reception” or “After Hours”. Callers never see this.
  • Initial Greeting: the first thing the agent says when it answers, e.g. “Thanks for calling Smith Plumbing, how can I help you today?”
  • System Prompt: the agent’s job description, written in plain English. Tell it who it works for, what it should do, and how it should behave. The more specific you are, the better it performs.

Click Create Agent at the bottom when you’re done (it reads Update Agent when you’re editing an existing one). The other tabs in the editor — voice, speech recognition, tools and so on — are all pre-set with good defaults; you can come back to them later.

2 Start the agent

Back on the Voice Agents page, find your new agent in the list and click its green Start button. After a few seconds the status changes to Running — the agent is now on duty and ready to answer.

⚠Important: a newly created agent does not run automatically. Until you press Start and see the status turn to Running, it cannot answer any calls — this is the single most common reason a new agent “doesn’t work”.

3 Point a phone number at it

Now tell the system which agent should answer incoming calls. In the sidebar, go to Telephony → Dispatch Rules and create a rule (or edit the existing one):

  • Agent: pick the agent you just created. Calls that match this rule will be answered by that agent.
  • Auto-Record (optional): tick this if you want every call handled by this rule to be recorded automatically. Recordings then appear on the Recording/Egress page.

Save the rule. From now on, calls arriving on your number are routed straight to your agent.

🔒Needs telephony set up: dispatch rules only work once your phone service is connected — that means a SIP trunk and at least one phone number. If the Telephony menu shows “disabled” or you haven’t done this yet, see the SIP Trunks section of this guide first.

4 Make a test call

Pick up your mobile and ring your number. You should hear your agent answer with the greeting you wrote in step 1. Have a short conversation, then hang up.

A minute or so later, open Call History in the sidebar — your test call will be there, complete with a full transcript and an AI-written summary of the conversation. Click the call to see all the detail.

5 Try it in the browser (no phone needed)

You don’t need a phone number at all to talk to your agent. In the sidebar, open Agent Tester (under Testing):

  • Select agent: choose the agent you want to test from the dropdown.
  • Text Mode: type messages back and forth, like a chat. Great for quickly checking what the agent knows and how it responds.
  • Voice Mode: speak to the agent through your computer’s microphone and hear it reply — just like a real call. Your browser will ask permission to use the microphone the first time.
  • Connect: starts the test session. When you’re finished, click Disconnect.
ℹNote: the Agent Tester talks to the real, running agent — so the agent must be Started (step 2) before you connect. Test sessions appear in Call History like any other call.
💡That’s it! You now have a working AI voice agent. The rest of this guide explains every other page in depth — dip in whenever you need it.

Voice Agents

The Voice Agents page is your home base — every phone-answering AI you build lives here.

A voice agent is an AI receptionist, salesperson, or assistant that talks to callers on the phone. Each agent has its own personality, voice, and abilities. The Voice Agents page lists all of them, shows whether each one is switched on, and gives you the buttons to create, copy, back up, and delete agents.

⚠Agents must be running to answer calls. A stopped agent will not pick up the phone, even if everything else is set up perfectly. If calls ring out or fail, check this page first — the agent needs the green “Running” badge.

1 Create an agent

Click the green Create Agent button at the top of the page. This opens the agent editor (covered in detail in the next section) where you give the agent a name, write its instructions, and pick its voice. When you save, the new agent appears in the list.

2 Create from a template

Next to Create Agent, the Templates button opens a gallery of nine ready-made agents — a healthcare appointment reminder, a clinic front desk receptionist, e-commerce support, real estate lead qualifier, hotel concierge, restaurant reservations, IT helpdesk, trades job booking, and a customer feedback survey. Each one arrives complete: a full set of instructions (including a shared block of phone-call delivery rules that keep the agent sounding natural — one question at a time, no “let me check” filler, no reading your details back at you), realistic business information, phone tools (hang up, transfer, date lookup) already attached, and sensible settings. Click Use This Template and you land in the editor, ready to swap in your own business details. The same gallery is also available as its own page at Agents → Templates.

  • Model badges: the coloured chips on each card show which AI models the agent will use (language model, speech recognition, and voice). These are chosen automatically to suit your installation.
  • Clinic Front Desk: an inbound receptionist for a medical practice — answers practice questions, collects booking and reschedule requests, takes messages, and directs possible emergencies to 000. It's deliberately tuned to speak with unhurried pacing (a longer listening pause before replying) so callers who pause mid-sentence aren't cut off — if you want it snappier, lower Response Delay on the Conversation tab. Each call's details (patient name, request type, preferred times, callback number) are captured as structured data fields when Auto-generate summaries is on.
  • Hotel Concierge: this template is the speech-to-speech showcase — it runs on Grok Voice (audio-to-audio) and needs an xAI API key under Settings → Integrations before it can take a call.
  • Customer Feedback Survey: designed for outbound campaigns. Each answer (satisfaction score, recommendation score, suggestions) is captured as a structured data field on the call record — automatic capture needs Auto-generate summaries switched on under Settings → AI Summary.
ℹTransfers need a destination. Templates that include call transfer create the agent with the transfer tool attached but no destination number. Add one under Tools → Blind Transfer after creating, or the agent will apologise instead of transferring.
ℹWhat happens automatically: the new agent gets a unique name (a number is added if the name is taken), the date-lookup tool is set to your dashboard’s timezone, and the first prompt version is saved to history. The agent only auto-starts if the API keys it needs are already configured — otherwise it’s created stopped with a note explaining what’s missing.

3 Start and stop agents

Each agent row has a Start / Stop button:

  • Start switches the agent on. It will now answer any calls routed to it.
  • Stop switches it off. Useful when you’re editing an agent and don’t want it taking calls mid-change.

The status badge next to the agent’s name shows the current state at a glance: green Running or grey Stopped. If any agent on the page is stopped, a yellow warning banner reminds you at the top.

4 Check agent health

The Health column tells you whether an agent has everything it needs to work:

  • A green Healthy badge means all the AI services the agent uses have valid keys and installed software.
  • A red badge means something is missing — usually an API key that hasn’t been entered yet, or a software package that isn’t installed. Click the red badge to open a popup listing exactly what’s wrong and where to fix it (almost always Settings → Integrations/API).
💡Tip: a red health badge is the number-one reason a brand-new agent stays silent. Fix the listed items before testing.

5 Duplicate, export, and import

  • Duplicate: makes an exact copy of an agent — perfect for creating a variation without starting from scratch. The copy gets a new name and starts stopped.
  • Copy to Chatbot Agent (the button): makes a website chatbot out of a phone agent in one click. A preview opens first — pick a name and the chat mode (Full voice is pre-selected), then read the three lists: Copied (prompt, knowledge text, tool instructions, data-extraction fields, memory settings, speech settings), Adapted (the language model and its fallbacks are rewritten into the chatbot shape, the greeting becomes the widget welcome message, fast-trip stall recovery is always off on chatbots, values outside the chatbot ranges are clamped) and Not carried over (phone transfers, hold, keypad input, voicemail and IVR detection, the routing slug, realtime audio-to-audio settings, resource limits, handoffs). Tools and knowledge-base collections are linked to the copy — a collection is shared, so editing it changes both agents. Warnings above the Copy button flag placeholders that will be blank on a website ({{user_number}} — a visitor has no phone number) and prompt variables the widget's embed page would have to supply. The chatbot is created switched off so you can review it before it answers anyone. It is a one-time snapshot: changing either agent later does not change the other. A realtime (audio-to-audio) agent copies without a recogniser or voice — tick the acknowledgement, then pick both on the chatbot's Voice tab.
  • Export: downloads the agent as a JSON file. Use this as a backup, or to move an agent to another system. The file carries everything the editor saves: prompt and greeting, the LLM with its fallback chain, every speech-recognition and voice setting (including per-provider extras), conversation dynamics, handoffs, tool assignments and the knowledge-base collections attached to the agent.
  • Import: upload a previously exported JSON file to recreate that agent here. Knowledge-base collections are re-attached by matching a collection with the same name on this dashboard; any that do not exist here are skipped, so open the editor and attach them by hand after importing to another system.
  • View Logs: opens that agent’s recent activity log — the first place to look when an agent answers but behaves oddly.
  • Move to folder: agents can be grouped into folders to keep a long list tidy; the folder button next to Create Agent manages the folders themselves.

6 Delete an agent

Open the agent, scroll to the bottom, and use Delete Agent. You’ll be asked to confirm. Deleting removes the agent’s configuration — its past calls stay in Call History.

ℹNote: before deleting, consider exporting the agent first. That gives you a one-click way back if you change your mind.

7 Prompt version history

Every time you save a change to an agent’s instructions, the previous version is kept automatically. In the editor, click the teal Versions button to:

  • See every saved version with a timestamp and a label showing where the change came from (a manual edit, the Enrich tool, AutoResearch, or an external API edit).
  • Click Diff on any version to see a colour-coded comparison — green lines were added, red lines removed.
  • Click Restore to load an older version back into the editor. You still need to press Update Agent to save it.

By default the last 20 versions are kept per agent (adjustable from 5 to 50). Older ones are removed automatically.

The Agent Editor

Six tabs that shape everything about how your agent sounds, thinks, and behaves.

Open any agent (or click Create Agent) and you’ll see the editor with these tabs across the top: Identity, Behavior, Speech Recognition, Voice, Advanced, and Memory. You can save at any time — you don’t have to fill in every tab. If the agent is running when you save, restart it (Stop then Start) so live calls pick up the change.

Identity tab — who the agent is

  • Agent Name: the display name you’ll see everywhere in the dashboard and in call history. Pick something meaningful like “Reception” or “After-Hours Support”.
  • Slug: a short, web-safe version of the name that the system uses internally for call routing. It’s generated automatically from the name — you rarely need to touch it.
  • Folder: optional grouping so a long agent list stays tidy.
  • System Prompt: the heart of the agent. Written instructions that define its personality, its job, what it should and shouldn’t say, and how it should handle situations. Write it like a briefing for a new employee: who they are, who they work for, what a good call looks like. Shorter, focused prompts respond faster than sprawling ones.
  • Initial Greeting: the exact sentence the agent speaks when it answers. Leave empty for no spoken greeting (the agent then waits for the caller to talk first).
  • Reference Information: facts the agent should always know — opening hours, address, prices, policies. Keeping facts here (rather than buried in the System Prompt) keeps the prompt clean and easy to maintain.
  • Tool Usage Instructions: tells the agent when to use each tool it has been given (tools are set up on the Tools page). Example: “If the caller asks for a human, use the transfer tool to send them to Reception.” You describe the when; the system handles the how.
  • RAG Knowledge Base Collections: attach one or more document collections from the Knowledge Base page. The agent will search them automatically when a caller asks something the documents can answer.

Writing a good System Prompt

The System Prompt is where most of an agent’s quality comes from — it’s worth ten minutes of care. Write it like a briefing for a brand-new employee, covering five things:

  • Who it is: a name and role — “You are Sarah, the friendly receptionist for Smith Plumbing in Brisbane.”
  • How it speaks: tone and length — “Be warm and professional. Keep answers to one or two short sentences — this is a phone call, not an essay.”
  • What its job is: the tasks, in priority order — “Your job is to find out what the caller needs, answer questions about our services and hours, and take a message if a plumber isn’t available.”
  • What it must never do: the guard rails — “Never quote exact prices — say a plumber will confirm the cost. Never make up information; if you don’t know, say so and offer to take a message.”
  • How calls should end: — “Before hanging up, confirm you have the caller’s name and phone number, and thank them for calling.”
💡Keep facts out of the prompt. Opening hours, prices, and policies belong in Reference Information (or a Knowledge Base collection for anything long) — and when to use tools belongs in Tool Usage Instructions. A short, focused prompt responds faster and is far easier to maintain. When in doubt, paste your rough notes into Enrich with AI and let it draft the structure for you.

Dynamic variables — personalising every call

You can put placeholders in the System Prompt and greeting that get replaced with real values when each call starts. The most useful ones:

  • {{user_number}}: the caller’s phone number on inbound calls, or the number being dialled on outbound calls.
  • {{current_datetime}}, {{current_date}}, {{current_time}}: the current date and time in your configured timezone — so the agent always knows what day it is.
  • {{time_greeting}}: becomes “morning”, “afternoon”, or “evening” — handy in greetings like “Good {{time_greeting}}, thanks for calling.”
  • Campaign variables: outbound campaigns add more, like {{Name}} and {{CompanyName}} — see the Campaigns section.

Enrich with AI & AutoResearch

  • Enrich with AI (blue button above the System Prompt): the AI rewrites and improves your prompt for you. Paste in rough notes and it turns them into a well-structured prompt. Nothing is saved until you accept the result and click Update Agent.
  • AutoResearch (purple button): opens the dedicated AutoResearch page (also in the left menu under Testing) with this agent pre-selected. It analyses your agent’s real call transcripts and suggests specific prompt improvements, each with a confidence score. You can run it on demand or schedule it to run overnight. Suggestions are never applied automatically — you review each one side-by-side and choose “Apply to Live Prompt”, and the previous prompt is always saved to Versions first.

Behavior tab — the agent’s brain

The first choice on this tab is the most important one:

  • Pipeline Mode — Standard (STT → LLM → TTS): three separate services work as a relay team. One converts the caller’s speech to text, one (the AI brain) decides what to say, and one converts the reply back into speech. This is the flexible choice: you can mix and match the best provider for each job, and it works with every feature in the editor.
  • Pipeline Mode — Realtime (audio-to-audio): a single AI model listens and speaks directly, with no separate speech-to-text or text-to-speech step. Conversations feel very natural and fast, but you’re limited to the voices and behaviours that the realtime provider offers. When you pick Realtime, the Speech Recognition and Voice tabs are mostly replaced by a notice, because the realtime model handles those jobs itself.

For Standard mode, configure the AI brain here:

  • LLM Provider: which AI company powers the agent’s thinking — OpenAI, Anthropic, Google, and others. The provider’s API key must be saved in Settings → Integrations/API first; models from providers without a key show as unavailable.
  • LLM Model: the specific model. Models in the list carry star ratings for speed — for live phone conversations, faster models feel dramatically better. Models not available in your configured region are greyed out with an explanation.
  • Temperature: how creative the agent is, from 0 to 1. Low values (0.1–0.3) give consistent, predictable answers — best for business use. Higher values make replies more varied but less controlled.
  • Reasoning effort on voice calls: this dropdown appears only when the selected model can “think” before answering — Claude, GPT (including GPT-OSS), Grok 4.6, Qwen, GLM, DeepSeek, Nemotron and Kimi models on AWS Bedrock, Gemini 3.x on Google / Vertex, Grok 4.5 on xAI, and DeepSeek V4 Flash on SCX (Au). Off (the default) keeps replies fastest and is the right choice for almost every phone agent. Low / Medium / High make the model reason progressively harder before each reply — smarter on complex questions, but the extra thinking is silence the caller has to sit through, so the dashboard asks you to confirm before saving anything above Off. The note under the dropdown explains exactly what each level does on the model you’ve chosen, because models differ: some always think a little even on Off, some don’t think at all unless you raise the level, and on a few Off actively switches thinking off. If you switch to a model that doesn’t support reasoning, the dropdown hides itself and quietly resets to Off — that’s expected, not a fault.
Where does your data go? (AWS Bedrock model names) Bedrock models carry a suffix that tells you where the AI actually runs: (AU) models process everything inside Australia (Sydney); (Global) models may be served from any AWS region worldwide; (Regional — uses API Settings) models run in whichever AWS region you configured on Settings → Integrations/API. If data residency matters to your business, pick an (AU) model. On Google Cloud Vertex the picture is different: the current Gemini 3.x models are not served from the Sydney region at all — when your configured Vertex region doesn’t offer a model, the dashboard automatically routes it through Google’s global endpoint so it still works, and the model list greys out anything genuinely unavailable with an explanation.
On a few older Claude models, AWS ignores your Temperature setting whenever reasoning is switched on — a warning appears under the Reasoning effort dropdown when that applies to your selected model.

For Realtime mode you instead pick:

  • Realtime Provider & Model: which audio-to-audio model to use.
  • Realtime Voice: the built-in voice offered by that provider.
  • Output Modalities: whether the model produces speech directly, or produces text that a separate voice (from the Voice tab) then reads out.
  • Provider-specific extras: depending on the model you’ll also see options like Temperature, Thinking Budget / Reasoning Effort (how much the model deliberates before answering — more thought, slower replies), Enable input noise reduction, and Enable context window compression (keeps very long calls from exceeding the model’s memory). The defaults are sensible — each option explains itself inline.

LLM fallback & auto-failover — staying up when a provider goes down

AI providers occasionally have outages or slow periods. Two layers of protection keep your agent talking:

  • Enable LLM Fallback: builds a backup chain — primary → backup 1 → backup 2. If the current provider doesn’t reply within the timeout during a live call, the next one takes over mid-conversation. Callers just hear a normal (if slightly delayed) reply.
  • Fallback Timeout: how long to wait for a reply before switching (default 4 seconds).
  • Fallback Provider / Model and 2nd Fallback: your backups. For best protection, pick a different company than your primary, so one provider’s outage can’t take out your whole chain.
  • Auto-failover with health checks: goes a step further — the dashboard quietly tests each provider in the background at your chosen interval. If the primary is struggling, new calls are routed to a healthy backup before anyone notices, and routed back automatically once the primary recovers. A status line under each provider shows its current health in plain language, and a Details button opens a 24-hour latency chart.
  • Check every: how often to test. Shorter intervals catch problems faster but use a few more AI tokens (a cost estimate is shown under the dropdown).

Conversation Dynamics — timing and interruptions (also on the Behavior tab)

Below the model settings, the Conversation Dynamics section controls how the agent waits and handles being talked over. The defaults suit most agents:

  • Response Delay: a deliberate pause before the agent replies (0 = fastest). Add a little if the agent feels like it’s pouncing on callers.
  • Endpointing Mode: how the agent decides the caller has finished a sentence — a fixed wait, or a dynamic one that adapts to each caller’s speaking rhythm.
  • Min Words to Interrupt: how many words a caller must say before the agent stops talking. Keeping it at 2 or higher stops coughs and background noise from cutting the agent off mid-sentence.
  • Barge-In Threshold: how long the caller must be speaking before it counts as an interruption at all.
  • Resume After False Interruptions: if an “interruption” turns out to be noise, the agent picks up where it left off (the False Interruption Timeout sets how long it waits before resuming).
  • Preemptive Response Generation (Advanced): the agent starts composing its answer while the caller is still finishing — faster replies, at a tiny risk of jumping the gun. On by default.
  • Filter Markdown from Speech: strips text formatting before speaking so the agent never says “star star” out loud. Leave on.

Speech Recognition tab — how the agent hears

  • STT Provider: the service that turns caller speech into text. Deepgram is the popular default; ElevenLabs, Google, OpenAI, and others are also available.
  • STT Model: the specific recognition model. Newer models are usually both faster and more accurate, and the list carries star ratings for real-world speed.
  • Language: the caller’s main language (e.g. en). Some providers offer a multilingual option, and an Automatic Language Detection switch lets the recogniser work it out itself.
  • Flux Multilingual (Deepgram): the conversational Flux recogniser in a version that understands ten languages (English, Spanish, French, German, Hindi, Russian, Portuguese, Japanese, Italian and Dutch), detects the language automatically, and keeps up even when a caller switches language mid-call. If you set a Language, it is used as a hint to bias recognition; otherwise detection is fully automatic. Standard Flux remains the pick for English-only lines.
  • Keywords / Custom Vocabulary / Key Terms: words the recogniser should listen out for — product names, brand names, industry jargon, unusual surnames. Adding them dramatically reduces mishearings of the words that matter most to your business. (The exact field name varies by provider.)
  • Smart Formatting (Dates & Currency) / Remove Filler Words: provider niceties — format numbers and dates properly in transcripts, and drop the “um”s and “uh”s so the AI reads cleaner text.

Audio Input Settings — voice detection, turn-taking, and noise (Speech Recognition tab)

Further down the same tab, this section decides when the agent believes someone is talking and when they’ve finished. Change one thing at a time and re-test:

  • Enable VAD (Voice Activity Detection): the ear that notices speech starting and stopping, filtering out silence and background noise. Leave on; the Speech Detection Engine dropdown picks which engine does it.
  • Microphone Sensitivity: lower picks up quiet speakers but also more background noise; higher ignores noise but can miss soft voices.
  • Min Speech Duration / Min Silence Duration: how long a sound must last to count as speech, and how long a pause must last before the agent decides the caller has finished. Raising Min Silence helps with slow, thoughtful callers who get talked over.
  • Turn Detector (Advanced): smarter end-of-sentence prediction beyond simple silence. Audio (v1-mini) — recommended — listens to tone and pacing to tell a mid-thought pause from a finished sentence, and runs entirely on your own server. Text is the older transcript-based method; Off uses silence only (cheapest, but the agent may jump in during thinking pauses). Turn Detection Sensitivity fine-tunes how confident it must be.
  • Noise Cancellation: cleans up the caller’s audio before the agent hears it — helpful for callers on speakerphone, in cars, or on noisy sites. Pick an engine and a Suppression Strength (higher removes more noise but can start eating quiet speech). Leave off if your callers are usually somewhere quiet.
  • Flux transcript options: with a Deepgram Flux model selected, the Speech Recognition tab also shows Spoken numbers as digits (“eight two seven four one” becomes 82741 — handy for order and phone numbers reaching tools intact), a Profanity filter, and Number redaction (Off / Numbers / Aggressive) which removes spoken numbers from the transcript the agent, its tools and Call History see. All three apply from the next call.
  • Secondary languages (ElevenLabs Scribe v2 realtime): a comma-separated list of language codes (for example es, fr) the caller may switch to in addition to the main Language. Leave blank to let Scribe choose from every language it supports.
  • Flux options: when a Deepgram Flux model is selected, extra switches appear (Flux Turn Detection, thresholds, Echo Guard). Their inline notes explain each; the defaults are the recommended setup.

STT Stall Recovery — when the speech-to-text provider has an outage

Occasionally a speech-to-text provider has a brief outage mid-call: the phone line is fine, but the words stop coming through — the agent effectively goes deaf without knowing it, and the caller ends up talking to silence. STT Stall Recovery (on the Speech Recognition tab) protects against exactly this. It is off by default; switch it on per agent to enable it.

  • What it does when on: the agent notices within a few seconds that speech has stopped converting to text while the caller is still talking. It first recovers any delayed words automatically; if the words are truly lost it politely asks the caller to repeat (with a hard limit so it can never nag); if the connection to the provider is dead it disconnects and redials it behind the scenes — the caller just hears a short pause.
  • Dead-from-the-start connections are fixed fast: when the provider connection is broken from the very first moment of the call (the caller speaks, but not a single word ever comes through), the agent no longer works through several “could you repeat that?” rounds first — it replaces the connection immediately, within roughly the first ten seconds, then apologises once and asks the caller to say it again. This rescues the short calls where a caller would otherwise have given up before recovery finished.
  • Recovery Threshold: how long to wait after the caller stops speaking before recovery kicks in. Leave blank for automatic — the system picks a safe value for the selected provider.
  • Goodbye Message: the last resort. If the provider cannot be revived at all, the agent speaks this message once and ends the call cleanly — far better than leaving the caller talking to a dead line. Word it however suits your business, but remember it is spoken once, right before the call ends: don’t promise transfers, callbacks, or menu options. Leave blank for the built-in default.
  • Backup Transcription Provider (optional): one more rescue attempt before the goodbye. If you pick a backup, then when the main provider can’t be revived the call quietly switches to the backup and keeps going — the caller just hears one “sorry, could you repeat that?” instead of the goodbye, and the backup handles the rest of the call. Pick a different company than your main provider (two services from the same company tend to fail together). If the backup fails too, the goodbye still fires — choosing a backup never removes the safety net. Backup minutes are billed at your main provider’s configured rate. Some providers can’t serve as backups and appear greyed out. Leave on None to go straight to the goodbye instead.
  • Turning it off: switch it off and the agent instantly returns to standard behaviour — nothing else about the agent changes.
ℹDeepgram Flux agents: agents using Deepgram Flux already include a basic built-in stall detector that runs regardless of this switch. The switch adds the full recovery ladder — repeat prompts, automatic reconnection, and the goodbye — for Flux and every other provider alike.
ℹRealtime mode: when the agent uses the Realtime pipeline, this tab shows a “Realtime Mode Active” notice instead — the realtime model does its own listening, so there’s nothing to configure here.

Voice tab — how the agent sounds

  • TTS Provider: the service that speaks the agent’s replies. ElevenLabs is known for the most natural voices; OpenAI, Google, Cartesia, and others each have their own character and price point.
  • Voice: the actual voice. Most providers offer a gallery of male and female voices in different accents; some (like ElevenLabs) support custom cloned voices via the TTS Voice ID field.
  • SLNG.ai Fish Audio voices: the list is a starter set of Fish voice IDs; any of the 338 voices on SLNG’s Fish Audio voice page can be pasted in via Custom Voice ID. Demo Voices — Voice ID changes on each turn sends no voice ID at all, so Fish picks a different voice every time the agent speaks — use it only to prove the connection works (for example when a pinned SLNG region can’t find a named voice and calls fail with “Reference not found”), never for a live agent.
  • Speech Speed: speaking rate. 1.0 is normal; a touch faster (1.05–1.1) can make agents feel snappier.
  • Provider extras: some providers add their own sliders — e.g. ElevenLabs’ Voice Stability (lower = more expressive, higher = more consistent) and Similarity Boost (how closely the voice sticks to its original character).
  • ElevenLabs V3 Conversational: ElevenLabs’ most expressive voice model. Instead of sliders, you direct the performance with audio tags written into your prompts and greetings — e.g. [whispers], [excited], [laughs], [sighs] — and only the Voice Stability slider applies (Similarity and Speed are controlled by the model, so those controls hide themselves). It takes noticeably longer to start speaking than Flash v2.5 and costs about twice as much per character, so choose it where expressiveness matters more than snappy response — storytelling, empathy-heavy lines — rather than fast-paced phone traffic.
  • Start speaking earlier (Advanced): begins generating the spoken reply during the brief pause while the agent confirms the caller has finished — shaves a few hundred milliseconds off response time, at a small extra TTS cost when it guesses wrong. Off by default.
ℹRealtime mode: this tab is also replaced by a notice in Realtime mode — unless the realtime model is set to text-only output, in which case the voice you pick here reads out the model’s text replies.

Advanced tab — conversation feel

The defaults here work well for most agents. (The fine-grained timing and hearing controls live on the Behavior and Speech Recognition tabs — see the Conversation Dynamics and Audio Input Settings groups above. This tab holds the operational settings.)

Silence behaviour — when both sides go quiet

  • Silence before agent re-engages: how many seconds of quiet before the agent speaks first (default 10).
  • Re-engage caller on silence: when the timer fires, choose what the agent does — ask “are you still there?”, say an exact custom phrase you write, or stay silent. The agent keeps checking in at the same interval until the caller responds or the attempt limit is reached.
  • Max re-engagement attempts before hanging up: after this many unanswered nudges the agent says a polite goodbye (played in full) and ends the call (default 2). Speaking at any point cancels the countdown instantly.
  • End Call on Silence & Silence Timeout (seconds): a harder backstop — end the call outright after a continuous stretch of total silence, so an abandoned line can’t stay open racking up cost.
When a call is handed off between agents (transfers and transitions), the silence settings of the agent currently handling the call apply — each agent’s own on/off switch, action and phrase take over as soon as it picks up the conversation. The re-engagement attempt count is shared across the whole call, so nudges used before a handoff count towards the limit afterwards.

Outbound Call Detection — voicemail and phone menus

These only apply to outbound calls (campaigns and manual dialling), where the agent may reach a machine instead of a person:

  • Voicemail Detection: the agent recognises it has hit voicemail. Action when voicemail is detected chooses what happens next — hang up, leave a spoken Voicemail message (written by you), or play an uploaded Recording to play at a chosen volume. Extra detection instructions lets you describe unusual voicemail greetings your callers’ carriers use.
  • IVR / Phone Menu Detection: recognises “press 1 for sales” phone menus. Action when IVR menu is detected is either Navigate the menu (the agent presses keys itself — tell it which options to pick in the System Prompt) or Hang up immediately.
Detection method — classic or LiveKit answering-machine detection

The Detection method select at the top of the card decides who does the recognising:

  • Ask the AI (classic): exactly what every agent did before this option existed, and what existing agents keep using until you change the setting. The agent’s own language model listens to the call and calls a tool when it believes it has reached voicemail or a phone menu. Your greeting is spoken as soon as dialling starts, so on a slow-to-answer number it can play into the ringing tone.
  • LiveKit answering-machine detection (the default for new agents): LiveKit listens to how the call is answered and decides in about a second whether a person, a voicemail greeting, a full or unset mailbox or a phone menu picked up. It then applies the voicemail and phone-menu settings you already have: a person gets your greeting, a voicemail gets your message or recording after the beep, a full mailbox is hung up on, and a phone menu is navigated or hung up on per your IVR setting. Your greeting is held until the callee has actually answered. Outbound calls only — inbound calls, chatbots and the Agent Tester are never affected, and the method only does anything when Voicemail Detection or IVR Detection is switched on.
  • Wait for the beep: (LiveKit mode) the detector fires when the greeting ends, but most beeps land a second or two later. Your message or recording starts after this pause (default 2 s) so it is not cut off.

Under Advanced detection settings (LiveKit mode):

  • Give up deciding after: counted from the moment the call is answered (default 20 s). When it runs out the result is “uncertain”.
  • Give up waiting for any speech after: a callee who answers and says nothing counts as “uncertain” after this long (default 10 s). If the call had already been answered by the time the detector started listening, this is shortened to 3 s so a person who already said hello is not left waiting.
  • Short greeting limit: speech shorter than this followed by silence (“Hello?”) is a person straight away; longer greetings are checked by the classifier model (default 2.5 s).
  • When the detector cannot decide: Continue as if a person answered (default) or Hang up. Pick Hang up for campaigns where a wrong greeting into a phone tree is worse than a missed person.
  • Classifier model: which language model reads the greeting transcript. Leave it on “this agent’s model” unless you want something faster or cheaper. It always runs as a separate copy, so a classifier hiccup can never end the call.
  • Detection recogniser: realtime (audio-to-audio) agents have no recogniser of their own, so the detector listens with this one (Deepgram Nova-3 by default). Standard agents reuse their own Speech Recognition setting.
  • Wait for the greeting to finish before deciding: on by default, so a voicemail is never talked over. Switch it off to make “Give up deciding after” a hard limit.
What happens automatically in LiveKit mode: while the detector is listening the agent stays silent (no greeting, no silence nudges); if the detector cannot be started for a call — for example the number was answered before the agent joined and nothing was heard — the classic method takes over for that call, and the agent log says AMD fallback: with the reason. Every result is written to the call’s record and shown on Call Detail as Answered by: Person / Voicemail / Mailbox unavailable / Phone menu / Unknown. Campaign counts keep working: voicemail, full mailboxes and hung-up phone menus all count as voicemail. Extra detection instructions apply to the classic method only.

Resource Limits — caps and safety valves

Also on the Advanced tab, the Resource Limits section sets sensible ceilings on each agent:

  • Max Call Duration (minutes): the agent politely ends the call when this limit is reached. New agents default to 10 minutes — if your calls seem to cut off at a fixed length, this is why. Raise it, or set it to 0 for no limit. It’s a useful cost guard against a caller (or a misbehaving conversation) keeping a line open for hours.
  • Max Tool Steps per Turn: how many tools the agent may use in a row before it must speak (default 3). Raise it only if the agent runs multi-step workflows — e.g. look up an order, then verify the caller, then send a confirmation — and you see it stopping partway through.
  • CPU Quota / Memory Max: how much of the server one agent may use. The defaults (80% of a CPU core, 512 MB) suit almost everyone — leave them alone unless support advises otherwise.

Agent Handoffs — passing the caller to another agent

Handoffs let one agent pass the live call to another agent mid-conversation. There are two very different ways to use them: a Transfer behaves like being put through to a different department (a new “person” takes over, and may say so), while a Transition builds one seamless receptionist out of several narrow specialist agents — the call silently moves between a router, a booking phase, a cancellation phase and so on, and the caller believes they spoke to one person the whole time. Picking the Type in the editor snaps the announce and context settings to that style’s recommended defaults. On silent transitions the destination agent’s Initial Greeting is spoken automatically as a short bridge over the changeover (a route’s Bridge Phrase replaces it if set); silent transfers stay quiet by default. For transitions to stay invisible, every agent in the chain needs the same persona wording and the same Voice settings — the editor warns you if any transition in the chain (even one configured on another agent’s page) would change the voice mid-call.

The full guide — including ready-to-copy example prompts for both styles and a worked multi-phase receptionist setup — is in the Transfers & Transitions section.

  • Transfer: an announced handoff. The caller knows it’s happening — “Let me put you through to our billing team.” Use the optional Sign-off Prompt to control the exact send-off line.
  • Transition: a silent handoff. The caller never notices — the conversation simply flows into a new phase handled by a different agent (useful for multi-step workflows like verify-then-book). An optional bridge phrase smooths the join.
  • Context Mode: how much of the conversation the receiving agent inherits — Full (everything), Summary (an AI-written handover brief — who is calling, what they want, and the exact details collected so far), or Fresh (clean slate).
  • Handoff Summary Model & Custom Summary Instructions: shown when Summary mode is selected. Pick which AI model writes the handover brief (default: the agent’s own model) and optionally replace the built-in instructions with your own. Writing the summary adds a short pause — typically 2–5 seconds — at the moment of transfer (an announced transfer’s sign-off line usually covers it; on silent transitions the pause is capped tighter). If the summary can’t be generated in time, the transfer still goes ahead with the most recent part of the conversation attached — it never gets stuck.
  • Greeting on handoff: the receiving agent’s Initial Greeting is spoken on announced handoffs; on silent ones it’s skipped automatically.
  • When to Transfer / When to Transition: a one-line description the AI reads to decide when this handoff applies — e.g. “Transfer when caller asks about billing or invoices”.

Data Extraction Fields — pulling details out of every call

Also on the Advanced tab: name the specific details you want captured from each call — a callback number, an order reference, a preferred appointment day — and the AI fills them in when it generates the call summary. Each field has a Field Name (short, lowercase), a Display Label (how it appears on the call detail page), and a Description (for LLM) telling the AI exactly what to look for. Extracted values show up on each call in Call History.

Memory tab — remembering repeat callers

  • Enable Memory: when on, the agent remembers useful facts from past conversations (names, preferences, unresolved issues) and recalls them automatically when the same phone number calls back. See the Knowledge Base & Memory section for how to browse and manage what’s remembered.
  • Extraction Provider / Model: which AI model distils each finished call into memories. This runs after the call, so it never slows the conversation — use a fast, cheap model.
  • Max Memories per Turn / Max Total Memories / Max Memories per Caller: caps on how many memories are recalled into a conversation, kept for the whole agent, and kept per caller. When a cap is hit the oldest are dropped first — the defaults are fine.
  • Score Threshold: how relevant a stored memory must be before the agent brings it up — raise it if the agent mentions stale or irrelevant facts.
  • Fact Extraction Prompt: the instructions the extracting AI follows. Edit it to steer what kinds of facts get remembered (e.g. always capture the caller’s preferred callback time).
ℹNote: memory needs two supporting pieces installed and running — the memory package (installable from Settings → Dependencies) and the vector database used by the Knowledge Base. The tab tells you if either is missing.

Walkthrough: build a production-ready voice agent, stage by stage

Work through the tabs in this order — and prove each stage works before moving to the next. That way, when something misbehaves you always know which stage caused it.

  • Stage 1 — Identity. Name the agent, write the System Prompt using the five-part briefing above (or paste rough notes into Enrich with AI), set an Initial Greeting, and put your facts in Reference Information. Save. Prove it: open the Agent Tester in Text mode and have a typed conversation — wrong tone or wrong facts get fixed here, before audio ever enters the picture.
  • Stage 2 — Behavior. Keep Standard pipeline unless you specifically want Realtime. Pick a fast LLM (the star ratings are speed), Temperature 0.2–0.3, and set up an LLM fallback with a different company as backup. Prove it: the agent list’s Health badge is green, and Text-mode replies in the Tester come back quickly.
  • Stage 3 — Speech Recognition. Pick the STT provider/model, set the language, and — important — add your business’s product names, brand names, and local suburbs to the Keywords/Custom Vocabulary field. Prove it: Agent Tester in Voice mode — say the tricky words and check the transcript panel got them right.
  • Stage 4 — Voice. Choose the voice and speed. Prove it: listen in the Tester — if it sounds robotic or too slow, adjust speed (1.05 is a nice nudge) or try another voice before you get attached.
  • Stage 5 — Tools & handoffs. On the Tools page assign what the agent needs (hangup at minimum; transfers, take-a-message, send-SMS as required), then come back to Identity → Tool Usage Instructions and write one line per tool about when to use it. Add Handoffs on the Advanced tab if another agent handles part of the job. Prove it: in the Tester, ask for a human / trigger each tool and watch the tool calls appear in the transcript.
  • Stage 6 — Safety rails. Advanced tab: check Max Call Duration suits you (new agents default to 10 minutes), set silence behaviour, and — for outbound work — voicemail detection. Speech Recognition tab: consider switching on STT Stall Recovery with a backup provider.
  • Stage 7 — real call. Start the agent, point a dispatch rule at it (see Dispatch Rules), and ring it from your mobile. Only a real call proves the trunk, caller ID, and true phone audio.
  • Stage 8 — lock in quality. Build a small Simulation suite for your critical scenarios and run it after every prompt change; once real calls flow, use the Improvement Lab to measure success and AutoResearch to keep the prompt improving.

Transfers & Transitions (Agent Handoffs)

One phone call, several specialist AI agents — handoffs let a call move between your agents without the caller ever being put on hold.

A handoff swaps which of your AI agents is speaking on a live call. The call never leaves the dashboard and never rings another phone — it’s the same call, with a different “brain” taking over. There are two styles, and they serve two very different designs:

The two styles — two different mental models

  • Transfer — separate departments. The caller is handed to what feels like a different person: “Let me put you through to our billing team.” The new agent has its own name, its own greeting, and may sound different. Use this when departments are part of the experience — reception → billing, sales → support.
  • Transition — one person, several phases. The caller never notices anything. Behind the scenes the call moves between narrow, single-job agents — a router that works out what the caller wants, then a booking agent, a cancellation agent, a question-taker — but to the caller it is one continuous conversation with one person. This is how you build a large, complex receptionist without one giant prompt: each phase gets a short, focused prompt and only the tools that phase needs.
ℹHandoffs are not phone transfers. To send a caller to a real human on another number, use the Blind Transfer or Attended Transfer tools on the Tools tab instead. Handoffs only ever swap between your own AI agents on the same call.

Setting one up

Open the source agent’s editor → Advanced tab → Agent Handoffs, enable handoffs, and add one row per destination. Choosing the Type sets the right defaults for that style automatically.

  • Type: Transfer or Transition (see above). Picking a type auto-sets the announce tickbox and context mode to that style’s recommended defaults — you can still change them.
  • Target Agent: which agent takes over.
  • Context Mode: what the new agent inherits. Full conversation history (everything said so far — the safe default for transitions), AI-generated summary (an AI writes a short handover brief at the moment of transfer: who’s calling, what they want, and the exact details collected so far), or Start fresh (nothing carried over).
  • Handoff Summary Model & Custom Summary Instructions: appear when Summary mode is selected. Pick which AI model writes the brief (default: this agent’s own model) and optionally replace the built-in instructions. Writing the summary adds a short pause — typically 2–5 seconds, up to 7 on announced transfers — at the moment of handoff. If it can’t be written in time, the handoff still goes ahead with the most recent part of the conversation attached; it never gets stuck.
  • Announce to caller: ticked, the AI is instructed to tell the caller about the handoff (and to say your Sign-off Prompt first, word for word, if you set one). Unticked, the AI is instructed to say nothing about it. This steers the AI’s speech — it doesn’t play a recording.
  • Sign-off Prompt / Bridge Phrase: an optional line spoken just before the handoff (“Let me get that sorted for you now”). On Summary mode this also usefully covers the summary-writing pause.
  • When to Transfer / When to Transition: the condition the AI reads to decide when this handoff applies. Be specific — “Transition when the caller has confirmed the Carnegie site and wants to book” works far better than “for bookings”.
ℹWhat happens automatically: agents reached by a handoff get their own onward handoff options, so chains work (router → booking → back to router). On a silent transition the destination agent’s Initial Greeting is spoken automatically as the changeover bridge (word-for-word, not paraphrased) — it covers the few seconds the new agent’s speech recognition needs to connect, and the caller can’t interrupt it during that window, so keep it to one short phrase (“One moment while I pull up your details.”). If the route has a Bridge Phrase, that is spoken automatically instead and the greeting stays silent on that route. Silent transfers stay quiet by default. The per-route “Speak this agent’s Initial Greeting on takeover” tick-box overrides any of these defaults. Announced handoffs speak their greeting as always. Each call allows up to 12 handoffs as a safety limit against accidental loops.

Writing the prompts — this is where handoffs succeed or fail

For a Transfer target, write a standalone person with their own identity and fill in an Initial Greeting:

<role>
You are Alex, the Billing Department agent for {{business_name}}. Callers
reach you when reception transfers billing questions to you. You are a
different person from the receptionist - introduce yourself as Alex from
Billing when you take over.
</role>

<job>
Handle invoice queries, payment issues, and account balances. Verify the
caller's identity (full name + date of birth) before discussing any
account details.
</job>

<style>
Professional and warm. Plain text only - no markdown, your words are
spoken aloud.
</style>

For a Transition target, write a phase of the same person — and give it a short, phase-appropriate Initial Greeting (“One moment while I pull up your details.”) to act as the spoken bridge; never a call-opening welcome:

<role>
You are Chloe, the AI receptionist for {{business_name}}. You are MID-WAY
through an ongoing call - the conversation so far is in your context.
This is the BOOKING phase of the call.
</role>

<critical_rules>
- Do NOT greet the caller or introduce yourself. You have already been
  speaking with them.
- Do NOT ask for anything the caller has already told you - check the
  conversation context first. If their name, phone number, or preferred
  clinic is already there, use it.
- Never mention being transferred, connected, or "a different agent".
  You are the same person the caller has been talking to.
- Continue naturally from wherever the conversation left off.
</critical_rules>

<job>
Book the caller's appointment: confirm the service and practitioner,
offer available times, capture any missing contact details, confirm the
booking back to them.
</job>

Example setup: a clinic receptionist built from phases

A proven pattern for a complex receptionist:

  • Intro Manager (the agent your phone number points at): greets, answers general questions, works out what the caller needs. Transitions to each specialist phase.
  • Booking / Reschedule / Cancel agents (one per site if locations differ): each does one job with only that job’s tools attached. Each can transition back to the Intro Manager or across to another phase (“actually, I also want to ask a question”).
  • All of them share the same identity block word-for-word (“You are Chloe…”), the same Voice settings, short bridge greetings, and full-context silent transitions.

Four rules that keep transitions invisible

  • Same identity everywhere: the name and persona wording must be identical in every agent of the chain. Any drift is what callers notice.
  • Same voice everywhere: a different voice on any hop instantly reveals the swap. The editor shows a warning listing every transition in the chain — including hops configured on other agents — where the voices don’t match.
  • Short bridge greetings on transition targets: the greeting is spoken on takeover and can’t be interrupted while the new agent’s hearing connects — one short phrase, never a call-opening welcome. Untick “Speak this agent’s Initial Greeting on takeover” on routes that loop back to the entry agent, or its full welcome would replay mid-call.
  • “Don’t re-ask” in every phase prompt: the number-one giveaway in real calls is a phase agent asking for a name the caller already gave. The critical-rules block above prevents it.
⚠Test the whole chain, not just the first hop. Use the Agent Tester on the entry agent and steer the conversation through every phase — including “take me back” paths — listening for re-greetings, re-asked questions, or a voice change.

Chatbot Agents

Text-chat versions of your AI agents — embed them on your website, or connect them to SMS and WhatsApp.

Where voice agents answer the phone, chatbot agents answer typed messages. The same AI brains, prompts, knowledge bases, and tools power both — a chatbot can look up your documents, remember returning visitors, and even speak out loud if you enable its voice mode. The most common use is the website widget: a small chat bubble in the corner of your site that visitors click to talk to your AI.

1 The list page

The Chatbot Agents page lists every chat agent with an Enabled / Disabled state. A disabled agent refuses new conversations — handy while you’re still building it. From the list you can create, create from a template, toggle on/off, duplicate, export, import, and delete agents, just like voice agents. Duplicate copies the chatbot’s tools and knowledge-base links along with its settings. Export downloads a JSON backup; Import restores one. The Usage Today column shows how many of today’s allowed sessions the agent has used (e.g. 12/50, from the daily limit on its Session tab) — it turns yellow at 80% and red when the limit is reached and new visitors are being turned away until midnight (UTC).

1b Copy to Voice Agent — and Copy to Chatbot Agent

The button on a chatbot row makes a phone agent from that chatbot in one click (the same button on the Voice Agents page goes the other way). Nothing is copied until you have seen a preview:

  • Copied: the system prompt, knowledge text, tool instructions, data-extraction fields, memory settings, and every speech setting from the Voice tab (recogniser, voice, conversation dynamics). Tools and knowledge-base collections are linked to the copy; a collection is shared, so editing it changes both agents.
  • Adapted: the language model and its fallback chain are rewritten into the voice-agent shape (the chatbot’s reply-length limit has no phone equivalent), the widget welcome message becomes the greeting, a phone routing slug is generated from the name, and two chatbot-only behaviours are reset to the phone defaults: fast-trip stall recovery is turned back on and the “reconnect the chat” speech-recovery message is cleared.
  • Not carried over: the widget look, avatar, SMS settings, allowed websites, session limits, error reply, automatic summaries and recording consent — none of them mean anything on a phone call. Going the other way, phone transfers, hold, keypad input, voicemail/IVR detection, realtime settings and handoffs stay behind. Human Handoff settings (and the handoff_to_human tool) are website/SMS features and are not copied to a phone agent.
  • Warnings: prompt placeholders are never rewritten, only flagged. A chatbot prompt that relies on a variable from the embed page comes out blank on a phone call unless a campaign supplies the same variable; {{user_number}} works on phones but is blank on a website.
  • Switched off on arrival: the copy is created stopped (voice) or disabled (chatbot) so it cannot answer a real caller or visitor until you have reviewed it. If the chatbot had no recogniser or voice selected, the preview says “Voice setup required” and asks you to tick an acknowledgement.
  • One-time snapshot: the two agents are not linked. Change one later and the other stays as it was. If a copy fails part-way, delete the half-made agent and try again.
  • Sub-users: a copy you make is added to your own agents automatically and counts towards your voice-agent or chatbot quota.

5 Voice tab — Chat Mode and every speech setting

The Voice tab (between LLM & Prompt and Avatar) owns the Chat Mode choice and every setting that only matters when a chat has sound.   • Voice with avatar: visitors still type, but the agent’s reply is spoken aloud (and lip-synced if an avatar is on). The browser never asks the visitor for microphone permission.

Speech recognition (how the agent hears — full voice only)

  • STT Provider / Model / Language: the recogniser and the language visitors speak.
  • Responsiveness, Custom vocabulary, Smart formatting, Remove filler words, Auto-detect language: tuning that most providers honour. Blank means the provider’s own default.
  • Provider extras: some recognisers have their own panel (AssemblyAI, Sarvam, Speechmatics, Deepgram Flux and ElevenLabs Scribe) that appears only while that provider is selected. The Deepgram panel carries the Flux transcript options (spoken numbers as digits, profanity filter, number redaction) and the ElevenLabs panel the Scribe v2 secondary languages, exactly as on voice agents. Azure OpenAI recognition needs a transcription deployment name (Azure OpenAI panel) and cannot be a backup recogniser.
  • Speechmatics turn detection: the Speechmatics recogniser decides end-of-turn itself (Adaptive by default). A long mid-sentence pause (about 1.5 s) can end the turn early and the rest of the sentence then interrupts the reply — raise its end-of-utterance silence if your visitors pause a lot. This is the same behaviour as on voice agents.
  • STT Stall Recovery: when the recogniser stops responding the session retries, then apologises with the Goodbye Message. Turn it on to reveal the Backup speech recognition provider used when retries are spent. Only providers that can take over a live stream are listed (Azure OpenAI and non-streaming models are hidden), and with a Deepgram Flux primary only the verified Flux-backup providers are selectable — the same rule the voice-agent editor applies.

Voice (how the agent speaks)

  • TTS Provider / Model / Voice ID / Language: the voice visitors hear.
  • Speaking speed: 1.0 is normal; not every provider supports it.
  • Provider extras: ElevenLabs stability and similarity, Deepgram Flux expressivity, Hume voice description and instant mode — each appears only for its provider. Chatbot voices now match voice agents — Cartesia, Deepgram (incl. Flux), ElevenLabs, OpenAI, Google Cloud, Google Gemini, Azure Speech, Azure OpenAI (needs a TTS deployment name), AWS Polly, Groq, SCX, Hume, MiniMax, xAI, Speechmatics (preview), Sarvam, SLNG.ai and Telnyx (Kokoro voices — Telnyx retired its NaturalHD voices in September 2026; saved NaturalHD voice ids are switched to the Kokoro default automatically).
  • Output Volume: louder or quieter agent audio without touching the visitor’s device volume.
  • Filter Markdown from Speech: strips formatting before speaking so the agent never says “star star” out loud — leave it on.

Conversation dynamics

  • Voice activity detection: whether and how sensitively the agent notices the visitor speaking. Lower sensitivity numbers hear softer speech; Min silence is the pause that ends a visitor’s turn.
  • Turn detection & endpointing: the Turn Detector engine is chosen at the top of the tab; here you tune its threshold, the audio detector’s patience (blank = automatic), fixed or dynamic endpointing, and the pause before the agent replies. Deepgram Flux users get the Flux end-of-turn controls.
  • Interruptions: how many words it takes to cut the agent off, how long a visitor must speak, and what happens after a false interruption.
  • Noise cancellation: Full voice only. Cleans the visitor’s microphone audio on the server before recognition. Browsers already suppress noise, so start with Off and only enable it for noisy environments. The echo-canceller warm-up and microphone input rate sit here too.
  • Silence re-engage: Full voice only. When a visitor goes quiet mid-conversation the agent nudges them — ask if they are still there, repeat itself, let the AI improvise, or say your custom text — up to the number of nudges you allow, then says goodbye. This already runs on every Full voice chatbot; the controls simply tune it. In Voice with avatar the visitor has no microphone, so the agent cannot tell silence from reading and these nudges are always off (a reading visitor is never interrupted or cut off). The separate inactivity auto-close on the Session tab still ends idle sessions in every mode.
  • Record full-voice sessions: Full voice only. Off unless you switch it on. When on, the visitor sees your Consent notice and must tap Agree before the microphone or the session is even requested — nothing is recorded without that tap, and text or avatar sessions are never recorded. Recording consent decides whether they are asked at all, and has four settings. The two that ask: Ask first — keep chatting unrecorded if they decline (recommended — they still get help, just no audio file) and Ask first — offer text chat instead (voice stays off until they agree; they can still type). The two that do not ask: Don’t ask — show the notice puts your wording on screen as a permanent line the visitor cannot dismiss, and records regardless; Don’t ask — show nothing records with the visitor told nothing at all. In both of those the chat window shows a small “Recording” marker in its header while audio is being captured — but the Voice Orb and Voice Button display modes have no header, so with show nothing those two tell the visitor nothing at all. Recordings appear on that chat’s page in Chat History (player, download, and a consent receipt showing when they agreed and the exact notice they saw) and on the Recording/Egress page behind the Include chat sessions switch. The text transcript is kept either way, exactly as for every chat today. Delete the audio with the chat using Delete with recording on the chat’s page.
  • Generation: pre-emptive generation and speech start the reply before the visitor’s turn is fully confirmed (faster, slightly more usage); prompt caching lets supporting LLM providers reuse the system prompt between turns.
Recording someone without asking is against the law in many places. The two “Don’t ask” settings exist because some operators need them, but the responsibility is entirely yours. Recording a visitor’s microphone with no notice is unlawful in much of Australia and in a great many other countries, and it is the site owner who answers for it, not the visitor. If you are unsure, use one of the two settings that ask, or at minimum the one that shows the notice. Sessions recorded without asking are still filed honestly: the consent receipt on that chat records that the visitor was never asked, rather than pretending they agreed.
Recording consent is yours to word. The default notice is neutral (“This voice conversation may be recorded for quality purposes. Your chat transcript is kept either way.”). Check what notice-and-consent your state or country requires for where the widget is embedded, and edit the text to match — the dashboard shows exactly what you type. A returning visitor is asked again every session; a short recorded chat is never dropped from Chat History by the minimum-duration filter, so its audio always stays reachable.

  • Avatar tab: adds a lip-synced talking-head video of the agent inside the widget. Seven avatar providers are supported (D-ID, Tavus, Beyond Presence, LiveAvatar, Anam, Simli, Avatario) — their API keys go in Settings → Integrations/API, then you enter the provider’s avatar / face / replica ID here. 6b Hand a chat to a person (Human Handoff)

Sometimes a visitor needs a human — they ask for one, they are upset, or the chatbot has run out of answers. Human Handoff lets the chatbot pause itself and pass the conversation to your team, then take back over when the person is done. It works on the website widget (text, voice-with-avatar and full voice), on SMS and WhatsApp, and on chats started through the REST API. Phone calls are not included: phone agents already have the transfer tools.

There is no inbox in the dashboard. The conversation is sent to a web address you choose — usually an n8n workflow that posts it to Slack, your CRM or a help desk — and your team member replies from there. The reply appears in the visitor's chat window (or their SMS / WhatsApp) with the person's name on it. Everything is recorded in Chat History afterwards.

Turn it on — the Human Handoff tab

Open the chatbot, go to the Human Handoff tab, and fill in the fields below. Saving with the switch on also turns on the handoff_to_human tool for this chatbot — you never need to visit the Tools page.

  • Enable Human Handoff: the master switch. It needs a Webhook URL. Switching it off (or changing the URL or secret) while someone is mid-handoff hands those chats straight back to the assistant.
  • Webhook URL: where the dashboard sends the conversation, and every visitor message after it. The address must be reachable from this server, and this server's own address (Settings → Server) must be reachable from there, because replies come back to it.
  • Signing secret: every event is signed with it so the receiving side can prove it came from your dashboard. It is created for you the first time you save. If you press Regenerate, update the secret in your n8n workflow or software too, or events will be rejected there.
  • Name shown when the person gives none: replies normally carry the person's own name; this is the fallback label.
  • While a person is being brought in: what the visitor is told the moment the handoff starts. On full-voice chats the assistant's voice reads it out.
  • When the assistant takes back over: what the visitor hears when the person closes the handoff or goes quiet for too long.
  • Show a “Talk to a person” button: puts a button in the widget's header so the visitor can ask directly, without waiting for the chatbot to decide. You can change the label. The button hides itself while a handoff is running.
  • If the button can't be honoured: shown when the daily limit is reached or the chat cannot be handed over right now.
  • Wait for a person / Then / Never wait longer than: if nobody answers within the first number of minutes, the assistant either carries on (with the message below) or keeps waiting — but never past the hard limit, after which the assistant always takes back over.
  • Person silent for: if the person stops replying for this long, the assistant takes back over.
  • Email me when a handoff starts: one email per handoff, using Settings → Email. Leave blank to skip.
  • Handoffs per day / Visitor messages per handoff / Forwarded messages per day: abuse limits. Reaching a message limit hands the chat back to the assistant.
  • Message when a person ends the chat: used only when the person chooses to end the chat instead of handing it back.

What the visitor sees

A banner across the top of the chat shows the state: Waiting for a person to join…, then You're chatting with Sam once the person replies, and it disappears when the assistant takes back over. Each of the person's replies carries their name above the bubble. If the visitor reloads the page while the chat is still open, the banner comes back; if they leave for longer than the chat's own timeout, the handoff ends and a returning visitor starts fresh with the assistant.

Set up the receiving side with n8n (recommended)

  1. Save the tab at least once, then press Build n8n workflow (Slack). A workflow file downloads.
  2. In n8n choose Workflows → Import from file and pick it. Open the three Slack nodes and select your Slack credential and channel.
  3. Open the Reply form node, copy its Production URL, and paste it into the Slack message text where it says HANDOFF_FORM_URL (the yellow note in the workflow shows exactly where).
  4. Activate the workflow, copy the address of its Handoff events webhook, paste it into Webhook URL on the tab and save.
  5. Press Send test event. You should see “Outbound: delivered” straight away and a message in Slack. Open the reply form from that message and send anything — within a minute the tab shows “Inbound: your side replied”. Both directions now work.

Day to day: a Slack message appears when a visitor asks for a person. Open its reply form link, type your reply, and send. Every further visitor message lands in the same channel. On your last reply tick hand back to the assistant and the chatbot resumes — it is told exactly what you and the visitor said.

Replying inside the Slack thread itself is included in the downloaded workflow as a switched-off node (Slack thread reply (advanced)). It needs a Slack app with Event Subscriptions pointed at n8n, which is a Slack-side setup rather than a dashboard one: create the app at api.slack.com, enable Event Subscriptions with the node's webhook address, subscribe to message.channels, give it the channels:history and chat:write scopes, add it to the channel, then pick your credential on the node and enable it. From then on a reply typed in the thread goes to the visitor, and typing done hands the chat back. The reply form keeps working alongside, and needs none of that — which is why it is the default. You can also swap the Slack nodes for email, GoHighLevel, Zendesk or anything else n8n can post to.

Use your own software instead (developers)

Any system that can receive a web request and send one back can be the receiving side. The dashboard sends three events to your Webhook URL as JSON: handoff.requested (the transcript so far, visitor details, and a reply URL + token), handoff.visitor_message (each later visitor message), and handoff.ended (why it ended). Each request carries X-Handoff-Timestamp and X-Handoff-Signature — an HMAC-SHA256 of <timestamp>.<raw body> with your signing secret; reject anything older than five minutes. Answer with any 2xx within ten seconds; anything else is retried three times, and a retried delivery repeats its X-Handoff-Delivery id so you can ignore duplicates.

To reply, call the reply URL with the token as a bearer token. The token only works for that one conversation and stops working when the handoff ends.

# Send a reply
curl -X POST "https://your-dashboard/api/handoff/<conversation_id>/message" \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"text": "Hi, Sam here - your order ships tomorrow.", "human_name": "Sam"}'

# Hand the chat back to the assistant (or end it with "resume_ai": false)
curl -X POST "https://your-dashboard/api/handoff/<conversation_id>/close" \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"resume_ai": true, "note": "Delivery question answered"}'

# Check state and recent messages (poll no faster than every 5 seconds)
curl "https://your-dashboard/api/handoff/<conversation_id>" -H "Authorization: Bearer <token>"
  • 401 invalid_token: wrong or expired token — or your system cannot reach the dashboard's public address.
  • 410 conversation_ended: the handoff already ended (the visitor left, a timeout fired, or someone else closed it). Safe to ignore.
  • 409 not_in_handoff: someone already handed the chat back.
  • 429: more than 60 calls a minute for one conversation.
  • 502 provider_rejected: the SMS / WhatsApp provider refused the message — on WhatsApp this usually means more than 24 hours passed since the visitor's last message, which needs an approved template message.
  • Each reply on SMS or WhatsApp is an outbound message billed by your provider like any other.

The full contract, including the MCP tools that let an assistant act as the person (list_human_handoffs, send_human_handoff_message, close_human_handoff), is in the built-in MCP documentation under get_admin_guide() → human_handoff.

What happens automatically

  • The assistant stops answering the moment a handoff starts and does not answer again until the person closes it or a timeout fires. It is then given a clearly marked record of what was said, so it can continue sensibly — and it treats that record as information, not as instructions.
  • If nobody picks up in time, the visitor gets the message you set and the assistant either carries on or keeps waiting up to the hard limit.
  • If the person goes quiet for the set time, the assistant takes back over.
  • If your webhook cannot be reached when a handoff starts, the visitor is not left hanging: after the retries they get the “nobody available” message and the assistant carries on. The tab shows the last delivery result.
  • If the visitor leaves the widget, the handoff ends and your side is told.
  • Daily and per-chat limits stop a runaway visitor from flooding your team.
  • On SMS, opt-out words like STOP end the handoff and are handled exactly as before.

  • Domains tab — Allowed Origins: the security list of website addresses allowed to use this chatbot. Only sites you list here can load the widget — always use https:// addresses on live sites.

8 Put it on your website — Embed Code

The Embed Code tab generates a single small script tag. Copy it and paste it just before the closing </body> tag of your website (or hand it to whoever manages the site). The chat bubble appears automatically. Use the Preview button first to see exactly how the widget will look and behave before it goes live.

ℹNote: the Preview opens the real widget — conversations there are recorded in Chat History, exactly like a real visitor’s.

9b Use a chatbot from your own software (REST API)

Your own systems (n8n, a CRM, a booking app, a custom website) can talk to a chatbot without the widget: start a chat, send a message and get the reply straight back, read the transcript, end the chat — and send a text message from the chatbot’s SMS number. It uses the same keys as outbound calls (Settings → Integrations → REST API) and is switched off until you turn it on.

  • Turning it on: on the REST API tab, switch on the REST API itself, then the Chatbot sessions API and/or Outbound SMS API switches in the Chatbot API card. Each has a per-key daily limit (chats per day; SMS segments per day; 0 = unlimited). Messages are limited to ten times the chat limit. A key needs Can Make Calls to use any of this.
  • Start a chat: POST /external/v1/chats with agent_id (the chatbot’s id from its editor URL). Optional: external_id (your own reference, up to 128 characters), dynamic_variables (fills {{placeholders}} you put in the prompt or welcome message — up to 50, 1 KB each, 8 KB in total; anything not in your prompt is ignored) and greeting (default true: the welcome message comes back as the first message, no AI cost). You get a chat_id. The chatbot must be enabled, and its daily session cap (Session tab) counts API chats together with widget chats.
  • Send a message: POST /external/v1/chats/{chat_id}/messages with text (up to 4,000 characters). The reply comes back in the same response, with token usage. Optional timeout_s (5–60, default 30). Tools and the knowledge base work exactly as in the widget; there is no memory between chats (same as SMS). One reply at a time per chat (a second request while one is running gets chat_busy). The chatbot’s message limit ends the chat when reached.
  • If a reply times out (reply_timeout, HTTP 504): your message was kept and a tool may already have run — do not resend blindly; read the chat (below) and continue. If your web server sits behind a proxy with a short timeout, keep timeout_s under it.
  • Read a chat: GET /external/v1/chats/{chat_id} — status, when it started and last had activity, why it ended, the number of turns and the transcript (limit = most recent messages, up to 1,000).
  • End a chat: POST /external/v1/chats/{chat_id}/end (optional reason). A chat nobody ends is closed automatically after the chatbot’s inactivity timeout (Session tab), so its record and cost are always completed.
  • Send an SMS: POST /external/v1/sms with agent_id, to (full international number — short codes are refused) and text (up to 1,600 characters; limits count 153-character segments). The sender is always the chatbot’s configured number; a from field is rejected. The chatbot’s SMS channel must be enabled with a working provider, its own SMS daily cap applies per destination, and the message is added to that number’s thread in Chat History so a reply continues the conversation. channel: "whatsapp" works with Sent.dm only.
  • Safe retries: send an Idempotency-Key header on any POST and a repeat returns the same answer instead of doing the work twice. The same key with a different body is refused (422).
  • Errors carry a plain-English detail and a stable error code (for example rest_chats_disabled, agent_disabled, chat_ended, chat_busy, reply_timeout, agent_daily_session_cap, key_daily_chats_cap, sms_not_enabled, sms_destination_daily_cap). Rate-limit and busy responses include a Retry-After header.
  • Where it shows up: every API chat appears in Chat History as a Web chat with its transcript and AI cost, named “Visitor api…”. Deleting it removes the transcript as well.
  • Keys are passwords: any key with Can Make Calls can use every enabled chatbot and send from every chatbot’s SMS number. Give each integration its own key, restrict it to that system’s IP address, and keep the daily limits realistic. The API is not available on hosted multi-tenant deployments yet.
Example — start a chat and send one message: 
curl -X POST https://<your-dashboard>/external/v1/chats \
  -H "Authorization: Bearer sk-rest-..." -H "Content-Type: application/json" \
  -d '{"agent_id":"<chatbot-id>","dynamic_variables":{"customer":"Jane"}}'

curl -X POST https://<your-dashboard>/external/v1/chats/<chat_id>/messages \
  -H "Authorization: Bearer sk-rest-..." -H "Content-Type: application/json" \
  -d '{"text":"What are your opening hours?"}'

9 Test it safely

Head to the Agent Tester page (covered later in this guide), pick your chatbot from the dropdown, and chat with it in a throwaway test session — nothing is saved to Chat History, but tools and knowledge lookups run for real. The chatbot must be Enabled to respond.

Ending a chat session from your own code (developer API)

The normal way needs nothing from you: when a visitor ends the chat or closes the page, the widget disconnects them immediately. The session’s room simply sits on the server for a few minutes before it is cleaned up automatically — harmless, though a visitor who reconnects inside that window can land back in the old session.

For websites with their own “End chat” button (or any custom integration), there is an API that closes the session instantly: the agent leaves on the spot, the room disappears from the Rooms page at once, and a reconnect is guaranteed to start a completely fresh session.

  • Endpoint: POST /api/widget/end on your dashboard’s address, with the JSON body {"room_name": "webchat-..."}.
  • Authentication — no API key needed: send the header Authorization: Bearer <session token> using the same token your page received from /api/widget/token when the chat session started. That token proves the caller owns that session, so a visitor can only ever end their own chat — never anyone else’s.
  • Response: {"success": true}. Safe to call twice, and safe to call after the session already ended — “the room is gone” counts as success either way, so your hang-up code never needs special error handling for it.
  • Errors: 401 — missing/wrong token, or a token for a different room; 400 — malformed body or a room name that doesn’t start with webchat-; 429 — called too rapidly for the same room (wait the number of seconds in the Retry-After header).
  • Typical flow: on your own End-chat button, disconnect the widget client first, then fire this call.

Walkthrough: launch a website chatbot, stage by stage

Same principle as building a voice agent — prove each stage before the next:

  • Stage 1 — brain and prompt. Create the agent; on General / LLM & Prompt pick a model (chat can afford a smarter, slower one than a phone agent), write the System Prompt, add facts to Reference Information, set two fallback models. Prove it: Agent Tester → pick the chatbot → have a conversation. Fix tone and facts here first.
  • Stage 2 — knowledge. Attach the Knowledge Base collections it should answer from. Prove it: in the Tester, ask a question only the documents can answer and check it comes back right.
  • Stage 3 — look and feel. Widget tab: brand colour, position, title, welcome message, display mode (start with Popup). Pick the Chat Mode on General — Voice with avatar is the sweet spot for websites (spoken replies, no microphone permission popup).
  • Stage 4 — guard rails. Session tab: set the daily session limit (abuse protection), inactivity timeout, and — if you want summaries — switch on AI Summary with a daily cap. Domains tab: add your website’s https:// address to Allowed Origins — the widget won’t load anywhere else.
  • Stage 5 — go live. Enable the agent, Embed Code tab → Preview to see it exactly as visitors will, then paste the script tag before </body> on your site. Prove it: open your website in a private/incognito window and have a real conversation — then find it in Chat History.
  • Stage 6 — optional channels. Add SMS/WhatsApp (Stage 5’s proof becomes: text the number from your phone), an avatar, or memory — one at a time, testing after each.

Knowledge Base & Memory

Give your agents your documents to answer from — and a memory for repeat callers.

Out of the box, an agent only knows what’s written in its prompt. The Knowledge Base changes that: upload your price lists, policies, FAQs, and manuals, and the agent searches them during the conversation to answer questions accurately — instead of guessing. This works for both voice agents and chatbot agents.

1 One-time setup

The Knowledge Base needs two supporting services before it can work — the page walks you through both with a setup wizard:

  • A search database (Qdrant): stores your documents in a searchable form. The wizard can set it up locally on your server, or connect to a hosted cloud version.
  • An embedding provider & model: the AI service that converts text into searchable form. Pick a provider whose API key you’ve saved in Settings → Integrations/API.

If either piece is missing, the page shows a “Not Configured” notice with a pointer to what’s needed.

2 Create a collection

A collection is a folder of related documents — for example “Product Info”, “Company Policies”, or “Pricing”. Keeping topics in separate collections lets you give each agent only the knowledge it needs. Click the create button, give the collection a name and description, and it’s ready for documents.

3 Add documents and web pages

  • Upload files: TXT, MD (Markdown), CSV, and PDF files up to 10 MB each. PDFs have their text extracted automatically.
  • Paste text: type or paste content directly — great for quick notes and FAQs.
  • URL sources: add a web page address, a Google Doc, or a Google Sheet. The content is fetched and indexed automatically, and you can set an auto-refresh interval (every 12 hours, 24 hours, 48 hours, or weekly) so the knowledge stays current when the page changes.

After you add a document, the system splits it into small chunks and processes them for search — you’ll see the processing status and chunk count next to each document. Within each collection you can view, download, add, or delete documents at any time. URL sources also show a refresh badge with a “Refresh now” button and a per-source interval picker, and turn red if the last fetch failed.

What the columns mean:

  • Collections table — Documents / Vectors / Embedding: how many documents the collection holds, how many searchable chunks they became (Vectors), and which embedding provider/model the collection was built with. A collection is tied to its embedding model — changing the model later means re-creating the collection.
  • Documents table — Size / Chunks / Status: the file size, how many search chunks it was split into, and whether processing finished. A document isn’t searchable until its Status shows complete.
  • KB Status card (top of page): Running (green) means the search database is up; Stopped (red) or Not Configured (grey) means no knowledge lookups will work until it’s fixed.

4 Attach a collection to an agent

  • Voice agents: open the agent’s editor, and on the Identity tab select the collections under RAG Knowledge Base Collections. An agent can search several collections at once.
  • Chatbot agents: same idea — the collections picker is on the LLM & Prompt tab.

That’s it — the agent now decides for itself when a caller’s question needs a document lookup. It fires on “what’s your returns policy?” but not on “hi there”.

💡Tip: use the built-in test search box on the Knowledge Base page to try real questions against a collection before attaching it to a live agent. If the right chunks don’t come back, refine the documents first. The Include AI Synthesis toggle under the box lets you test the full synthesised answer, not just the raw matches.

Fine-tuning the search (optional)

The Configuration panel controls how searching behaves. The defaults are sensible — only change these if results aren’t what you expect:

  • Results per Search: how many matching text chunks come back per lookup (default 5).
  • Chunk Size & Chunk Overlap: how documents are split. Smaller chunks are more precise; larger chunks carry more context. Overlap stops important sentences being cut in half at chunk boundaries.
  • Context Chunks: include neighbouring chunks around each match for extra context.
  • Score Threshold: the minimum match quality (0–1) a result needs. Raise it to keep only highly relevant results; lower it to be more permissive.
  • AI Answer Synthesis: when on, raw search results are first passed through an AI model that writes a clean, concise answer before handing it to the agent. Replies sound more natural, at the cost of a moment’s extra latency and a small AI charge per lookup.
  • Synthesis Provider / Model / Prompt: which AI does the synthesising and the instructions it follows. Leave on the defaults to reuse your AI Summary settings.

The Memory tab — remembering repeat callers

The page has two tabs: Knowledge Base (everything above) and Memory, which manages the long-term memory feature (switched on per agent in the agent editor’s Memory tab). When it’s enabled, the agent quietly remembers useful facts from each conversation — the caller’s name, their preferences, an unresolved issue — and brings them up naturally next time the same person gets in touch.

  • Memory Configuration — Embedding Provider / Embedding Model: the AI service that converts remembered facts into searchable form (separate from the Knowledge Base’s embedding setting, but the same idea). Set once and leave alone — changing it later resets stored memories.
  • How people are recognised: phone callers by their phone number; website chat visitors by a persistent browser ID. SMS users by their phone number.
  • Agent Memories — browse: the table lists each agent with memory enabled and its Type (Voice or Chat). View shows everything that agent remembers, filtered by individual caller.
  • Delete: remove a single memory, or clear all memories for an agent.
  • Forget User: deletes every memory of one phone number across all agents — your one-click answer to a privacy (“right to be forgotten”) request.

Bulk import memories — pre-loading caller facts

Instead of waiting for the agent to learn about callers one conversation at a time, the Bulk import memories panel lets you load facts in advance — say, from your CRM export. The agent already looks up memories by phone number at the start of every call, so imported facts are used automatically.

  • CSV file / Google Sheet URL: upload a CSV (a Download template link shows the format; max 10 MB, 2,000 facts per upload), or paste a link to a Google Sheet shared as “anyone with the link”. The first column must be the phone number; every other column becomes one remembered fact per caller (e.g. “Plan Tier: Premium”).
  • Pin all uploaded memories: pinned memories are permanent — the agent can’t overwrite or delete them, and they survive the automatic pruning that trims older conversation memories. Leave this ticked for imported CRM facts; pinned entries show a badge in the memory browser.
ℹNote: memory uses the same search database as the Knowledge Base, plus a memory package installable from Settings → Dependencies. The page tells you if either is missing.

Walkthrough: give an agent your price list in five minutes

  • Step 1: run the setup wizard if the status card doesn’t say Running (one-time).
  • Step 2: create a collection called “Pricing”.
  • Step 3: upload your price list (PDF or CSV) — wait for Status to show complete.
  • Step 4: in the test search box, ask a real question a caller would ask (“how much is the premium plan?”). If the right chunk comes back, you’re ready; if not, simplify the document (tables with clear headings work better than dense prose).
  • Step 5: open the agent’s editor → Identity tab → tick “Pricing” under RAG Knowledge Base Collections → save.
  • Step 6: prove it in the Agent Tester: ask the price question and watch the transcript show the knowledge lookup happening before the answer.

Tools

Tools are the things your agents can do — transfer calls, send messages, look things up, take action.

Without tools, an agent can only talk. With tools, it can hang up politely, put callers on hold, transfer them to a human, text them a booking link, check an order in your CRM, and much more. The Tools page is where you switch tools on per agent and configure how each one behaves.

1 Assign tools to an agent

The Agent Tool Assignments section at the top lists your agents. Click Configure next to an agent to open its assignment panel, then flip the toggle for each tool you want that agent to have. Configurable tools (like transfers) show a settings panel under their toggle where you can override the defaults just for this agent.

ℹTwo levels of settings: the Configure button on a tool’s own card sets the global defaults shared by every agent. The per-agent panel overrides those defaults for one agent only — leave a per-agent field empty and the global default applies.

2 Tell the agent when to use its tools

Giving an agent a tool isn’t quite enough — it also needs to know when to reach for it. That happens in the agent editor, in the Tool Usage Instructions box on the Identity tab. Example: “If the caller asks to speak to a person, use the transfer tool and send them to Reception. If nobody answers, offer to take a message.” You describe the when in plain English; the system automatically supplies the technical details and the list of available destinations.

Built-in tools at a glance

  • hangup: lets the agent end the call gracefully when the conversation is done.
  • handoff_to_human: chatbot agents only — hands a website, SMS or WhatsApp conversation to a person via the chatbot's webhook. It is switched on and off from the chatbot's Human Handoff tab, not here; the only thing to edit on this page is its usage instruction.
  • hold: puts the caller on hold with hold music. Upload your own music in the tool’s configuration.
  • blind_transfer: forwards the caller straight to another destination — a phone number or a phone-system extension — without checking first. You define named destinations (“Reception”, “Sales”) and the agent picks by name.
  • attended_transfer: the polite version — the caller waits on hold with music while the agent dials the destination, briefs them privately, then connects the two. If the destination doesn’t answer or voicemail picks up, the agent automatically comes back to the caller and offers to take a message instead.
  • take_a_message: captures a message from the caller and delivers it to the right staff member by email and/or SMS. Works on its own or as the fallback when a transfer fails.
  • collect_dtmf: collects keypad input (account numbers, PINs) — callers can press keys or say the digits. Configure how many digits, the timeout, and whether the agent reads them back to confirm.
  • play_audio: plays a pre-recorded audio file — legal disclaimers, announcements, standard messages. Upload MP3, WAV, or OGG files up to 10 MB.
  • get_datetime: gives the agent the current date and time, in your chosen format and timezone.
  • send_sms: texts the caller (booking links, addresses, confirmations). Pick a messaging provider in the tool’s configuration — several are supported, including a WhatsApp-capable option and a custom workflow route. A Test button sends a real test message.
  • send_email: sends an email via your configured mail service.
  • schedule_callback, record_note, lookup_caller: shown on the Tools page as Coming Soon — these are preview placeholders and can’t be configured or used yet.

Configuring the transfer tools, field by field

The two transfer tools carry the most options of any built-in tool. What each field in their Configure popups means:

  • Default Outbound SIP Trunk: which of your outbound trunks dials the destination. Individual destinations can override it.
  • Transfer Destinations: the named places the agent can send callers. Each destination has a name the agent refers to (“Reception”, “Sales”), a type (a phone number, or a SIP address for phone-system extensions like 3CX), and the number/address itself. The agent only ever picks from this list — it can’t invent destinations.
  • Play Dial Tone (blind transfer): what the caller hears during the connection moment.
  • Transfer Mode (Advanced) (blind transfer): how the handover is executed — leave on the default unless your phone system needs the alternative.
  • Play Hold Music / Hold Music File / Volume (attended transfer): what the caller hears while the agent talks to the destination privately. Upload your own file or use the built-in music.
  • Consultation Timeout / Ring-out timeout (seconds) (attended): how long the private briefing may last, and how long to let the destination ring before giving up.
  • Detect voicemail and pivot automatically (attended): if the destination’s voicemail answers instead of a person, the agent notices and treats it as no-answer instead of briefing a machine. The two advanced fields tune how long it listens and how confident it must be.
  • When transfer fails, the agent should: the fallback — apologise and continue (default), take a message (needs the take_a_message tool enabled on the same agent), or apologise and end the call.
  • Stop Recording at Transfer: stops the call recording the moment the transfer succeeds — so the human-to-human part of the call isn’t recorded (often a privacy requirement). On by default.
  • Auto-Hang-Up … When Caller Leaves: if the caller hangs up mid-transfer, the dialled destination is hung up too instead of being left saying “hello?” to no one.
  • Minimum Consultation Time Before Merge (seconds) (attended): a brief guaranteed private moment with the destination before the caller can be merged in.
  • Hold tool extras: the hold tool shares the hold-music fields and adds Max Hold Time (seconds) so nobody can be left on hold forever.

Walkthrough: set up “transfer to a human” that can’t dead-end

  • Step 1: on the attended_transfer card, click Configure: pick your outbound trunk, add a destination named “Reception” with the real phone number, leave hold music and voicemail-pivot on.
  • Step 2: set When transfer fails to Take a message.
  • Step 3: in Agent Tool Assignments, enable attended_transfer AND take_a_message on your agent (configure take_a_message’s delivery email/SMS so messages actually reach someone).
  • Step 4: agent editor → Tool Usage Instructions: “If the caller asks for a person, use the attended transfer to Reception. If nobody answers, take a message.”
  • Step 5: prove both paths with real calls: one where Reception answers (you’ll hear the agent’s private briefing before the merge), and one where you let it ring out — the agent should come back and take a message. Check the message arrived.

Webhook tools — connect anything with an internet address

Webhook tools are custom tools you create that call an external system — your CRM, your booking system, or an automation platform like n8n, Make, or Zapier. During a call, the agent gathers what it needs from the caller and fires the request; the answer comes back into the conversation.

The easy way — the n8n Wizard. If your automation lives in n8n, the blue n8n Wizard button on the Webhooks tab does the whole job in four steps: pick a recipe (capture a lead into your CRM, look up live information the agent speaks back, send the caller a follow-up message, log a support ticket and read back its reference, silently ping your team on Slack or Teams, append call details to a Google Sheet, a Cal.com calendar pair that checks availability and books appointments, a GoHighLevel pair that books appointments and manages your sales pipeline, a website demo funnel that rings visitors who fill in your web form, a GoHighLevel outbound caller that rings new opportunities, or a custom one with your own fields), enter your n8n address, tick the agents that should use it, and click Create. The wizard builds the webhook tool and hands you a matching n8n workflow file to import — the address, security key, and field names are baked into both sides so they always fit. In n8n you just activate the imported workflow and swap the red REPLACE ME node for your real action (your CRM, your email sender, your database). You can re-download the file any time from the n8n button on the tool’s card. The manual form below is still there for everything else.

ℹBuilt-in guardrails (on by default): wizard tools are protected against the classic AI slip-ups without any setup. A booking tool refuses to book until an availability check has actually run in the same call; one-shot actions (booking a slot, sending a follow-up, saving a lead, logging a ticket) won’t silently fire twice with the same details — the agent is told it’s already handled; and if a required field is still blank the tool doesn’t fire at all — the agent is coached to ask the caller for it first. These guards apply to voice calls, website chats, and SMS alike. The blank-field guard is controlled by each parameter’s Required tickbox — required means enforced, so only tick it on fields the call genuinely can’t proceed without.
  • Function Name: what the agent calls the tool (e.g. lookup_order) — lowercase letters, numbers, and underscores. Keep it short and descriptive.
  • Description: a plain-English sentence about what the tool does — this is how the AI decides when to use it, so make it clear.
  • Webhook URL: the web address to call (an n8n, Make, or Zapier webhook, or your own API endpoint).
  • HTTP Method: POST, GET, PUT, PATCH, or DELETE — whichever your endpoint expects (your integration platform will tell you).
  • Custom Headers: extra request headers, typically for authentication keys.
  • Parameters: the pieces of information the agent should collect and pass along — each with a name, a type (String for text, Number, Boolean for yes/no, Array for a list, or Object for structured data), a description, and whether it’s required. Required is enforced, not just a hint: if a required field is still blank, the tool won’t fire at all — the agent is coached to ask the caller for it and only sends once it has an answer. Leave fields the call can proceed without as not required, or the agent will hold the conversation until it collects them. Example: a required order_number guarantees the agent gets the caller’s order number before the request ever fires.
  • System Parameters: toggles that automatically attach call context to every request — the caller’s number (caller_phone), the number they dialled, call direction and duration, the agent’s name, the conversation transcript or just the last message, and the date/time. Turn on only what your endpoint actually needs.
  • Timeout (seconds) & the “Allow agent to speak while waiting for response” option: how long to wait for the endpoint before giving up (default 30), and whether the agent may keep talking naturally while it waits instead of going silent.

Webhook tools — the advanced sections

The rest of the webhook popup is optional polish. The defaults are fine to start with; come back when you want tighter control:

  • Response Handling: Response Path picks out just the useful part of the endpoint’s reply (e.g. $.data.message) instead of dumping the whole response on the agent; Error Message Path does the same for error replies; Success Condition defines what counts as success (e.g. $.status == 'success') so the agent knows whether the action worked.
  • Error Handling: Speak On Error is the exact sentence the agent says if the tool fails; Speak On Delay plus Delay Threshold (seconds) give the caller a “bear with me…” line when the endpoint is slow; Retry Count, Retry Delay (ms), and Retry On Status Codes quietly retry temporary failures before giving up.
  • Rate Limiting: Max Calls Per Minute (across all calls) and Max Calls Per Session (per call) stop a confused agent — or a malicious caller — from hammering your endpoint. Empty means no limit.
  • Authentication: the Auth Type dropdown handles the common login styles — Bearer Token, Basic Auth, or an API key in a header or query parameter — without you hand-crafting headers.
  • Availability: restrict when the tool exists at all — Available From / Until (Time) with a Timezone makes a tool office-hours-only (outside those hours the agent simply doesn’t have it), and Available When (Condition) can gate it on call context.
  • Testing / Mock Mode: tick Enable Mock Mode and fill in Mock Response (JSON) to have the tool return a canned answer instead of calling the real endpoint — perfect for testing the conversation before the real system is ready. The Test button at the bottom of the popup fires a real (or mock) request immediately so you can check the plumbing.

Walkthrough: GoHighLevel appointments & sales (wizard)

The GoHighLevel appointments & sales tile creates two tools from one name prefix (e.g. ghl_check and ghl_book) and hands you two matching n8n workflow files. The check tool tells the caller which times are free in your GHL calendar; the book tool creates the contact, books the appointment, and creates a new sales opportunity in your pipeline — or advances an existing one to your “booked” stage.

  • Step 1 — run the wizard: Tools → Webhooks → n8n Wizard → GoHighLevel appointments & sales. Enter a name prefix (e.g. ghl), your n8n address, tick your agents, click Create, and download both workflow files.
  • Step 2 — import into n8n: import each file as its own workflow (three dots → Import from File…).
  • Step 3 — connect your GHL account: in each workflow, open the GoHighLevel nodes and pick (or create once) your HighLevel account credential. n8n’s HighLevel credential uses a GHL Marketplace app — n8n’s credential screen links to the exact setup steps.
  • Step 4 — paste your IDs: each workflow’s sticky note lists exactly which placeholders to replace and where to find each value in GHL — the Calendar ID (use the SAME calendar in both workflows), and in the booking workflow the Location ID (Settings → Business Profile), Pipeline ID and booked Stage ID (Opportunities → Pipelines).
  • Step 5 — activate both workflows (top-right toggle in n8n), then use the wizard’s Test connection buttons and make a test call: ask for a time, hear the real availability, and book it. Check the appointment and the opportunity appeared in GHL.

What happens automatically: appointments are booked for 30 minutes (the sticky note shows the one line to change for longer slots); every booking creates the opportunity under your pipeline’s booked stage, or advances an existing opportunity for that phone number; and the agent only ever says “booked” when GHL really returned an appointment — if anything is mis-configured the caller hears an honest “let me take your details and have the team finalise it” instead. The optional Customize Opportunity Fields node can also stamp your GHL custom fields on each opportunity; until you configure it (field IDs + a Private Integration Token credential) it is simply skipped and bookings still work.

Don’t rename the workflows’ nodes or the tools’ parameters — the pieces reference each other by name and renaming breaks every call. And keep the same Calendar ID in both workflows, or the agent will check one calendar and book into another.

Walkthrough: GoHighLevel outbound caller (wizard)

The GoHighLevel outbound caller tile is a downloadable recipe — no dashboard tool is created, because GHL (not a caller) is what sets it off. When a new opportunity appears in GHL, the workflow looks up the contact, waits five minutes so your other GHL automations finish first, and then has your chosen agent ring them.

  • Step 1 — run the wizard: pick the tile, choose which agent makes the calls and which SIP trunk they go out on, click Create, and download the workflow. Copy the secret shown on the finish page — you’ll need it inside GHL.
  • Step 2 — in n8n: import the file, connect your HighLevel credential on the Get a GHL contact node, create a dashboard REST API key (Settings → Integrations → REST API) and paste it into the workflow’s Config node, then activate and copy the webhook node’s Production URL.
  • Step 3 — in GoHighLevel: Automation → new workflow → trigger Opportunity Created (or a specific stage change) → add a Webhook action that POSTs to the Production URL, with a custom header X-Webhook-Secret set to the secret from Step 1, and a JSON body containing contactId (and opportunityId, so repeat fires for the same opportunity only ever place one call).
  • Step 4 — test on yourself: create a test opportunity with your own mobile as the contact. Five minutes later your phone should ring with the agent on the line.
Every opportunity that matches your GHL trigger gets a real phone call. Start with a narrow trigger (one pipeline stage) and test on your own number before letting it loose. If calls don’t happen, open n8n’s Executions list — failed runs show in red with the step that failed, and the workflow’s sticky note explains the common causes.

MCP servers — plug in whole toolkits

MCP (Model Context Protocol) is a standard way to connect AI agents to external tool servers. Instead of building webhook tools one by one, you connect an MCP server and it brings its entire toolbox with it — web search, file access, and more.

  • Server ID & Display Name: a short internal identifier (lowercase, underscores) and the friendly name shown in the dashboard.
  • Transport Type: how the dashboard talks to the server. SSE and Streamable HTTP are for servers with a web address — fill in the Server URL. Stdio (Local Process) runs the server as a program on your own machine — fill in the Command (e.g. npx) and its Arguments. If the server’s instructions give you a URL, use SSE or Streamable HTTP; if they give you a command line, use Stdio.
  • Environment Variables & HTTP Headers: where API keys go — environment variables for Stdio servers, headers (e.g. Authorization) for URL-based ones.
  • Timeout (seconds) & Enabled: how long tool calls may take, and a master switch to take the whole server offline without deleting it.
  • Templates: pre-configured setups for popular servers — pick one, paste in the required key, done. The gallery includes GoHighLevel CRM and n8n Tools (MCP), both walked through below.
  • Sync: after adding a server, click Sync to connect and discover its tools. They then appear in the tool list and can be assigned to agents exactly like built-in tools.
You stay in control of what each agent can do, on three levels: the account you connect decides what the connection could do (e.g. the scopes you tick on a GHL token); the per-agent tool assignments decide which discovered tools each agent actually gets; and during a call the agent only ever sends a tool’s own defined inputs (say, a phone number to search) — MCP tools never attach the transcript or call details unless a tool explicitly asks for them. Every tool call an agent makes is visible afterwards on the call’s detail page.

Walkthrough: GoHighLevel CRM over MCP

GoHighLevel runs its own MCP server, so your agents can look things up and update records mid-call: find the caller’s contact record, read recent conversations, check where a deal sits in your pipeline, update opportunities, add tags, and see calendar events.

  • Step 1 — create the token in GHL: Settings → Private Integrations → create a token (it starts with pit-). Tick only the scopes you want your agents to have — e.g. Contacts and Opportunities in View/Edit, everything else View only (or leave write scopes off entirely for a read-only agent).
  • Step 2 — find your Location ID: GHL → Settings → Business Profile (the sub-account ID).
  • Step 3 — add the template: Tools → MCP Servers → Browse Templates → GoHighLevel CRM → Add. Paste the token and Location ID into the two fields and save — the connection details are pre-filled.
  • Step 4 — Sync, then assign: click Sync Tools to pull in GHL’s tool list, then assign just the tools each agent needs — a reception agent might get only “search contact” and “get opportunity”.
GHL’s MCP server is for looking up and updating records — it cannot book appointments. For booking (and for creating opportunities on each booking), use the GoHighLevel appointments & sales wizard recipe above. The two work well together, and the same Private Integration Token can serve both.

Walkthrough: n8n as a tool box (n8n Tools MCP)

Instead of creating webhook tools one at a time, you can turn one n8n workflow into a whole tool box: every tool you attach to it in n8n automatically becomes a tool your agents can use. Great when you keep adding automations — add a tool in n8n, press Sync on the dashboard, done.

  • Step 1 — download the starter: Tools → MCP Servers → Browse Templates → n8n Tools (MCP) → Download starter workflow, and import it into n8n. It comes with two example tools and a sticky note with these same steps.
  • Step 2 — secure it: open the MCP Server node and create a Bearer Auth credential with a long random token (25+ characters). Anyone with the URL and this token can run your tools — treat both like passwords.
  • Step 3 — activate & copy: activate the workflow and copy the MCP Server node’s Production URL.
  • Step 4 — connect the dashboard: back in the templates gallery click Add on n8n Tools (MCP), paste the Production URL as the Server URL and the bearer token into the token field, save, then Sync Tools and assign the discovered tools to your agents.
  • Step 5 — make it yours: in n8n, replace the two example tools with real ones — click the + under the MCP Server node and attach any app node (Google Sheets, your CRM, HTTP Request, another workflow). Give every tool a clear name and a one-sentence description: that description is how the AI decides when to use it. After adding or renaming tools, press Sync Tools on the dashboard again so agents see the change.
Keep what each n8n tool returns short and speakable — the agent reads the answer to a live caller. Webhook-wizard tools remain the better choice when you want fine control over the spoken experience (waiting lines, exact error sentences); the MCP route wins on convenience once you have more than a handful of tools. Your n8n must be reachable at a public address (n8n Cloud or a hosted n8n is perfect) — a dashboard can’t connect to an n8n that only exists on a private home or office network.

Walkthrough: your first webhook tool (order lookup)

  • Step 1: in your automation platform (n8n, Make, Zapier) create a workflow that starts with a webhook and looks up an order in your system. Copy its webhook URL.
  • Step 2: Tools page → create a webhook tool: Function Name lookup_order, Description “Looks up the status of a customer’s order by order number”, paste the URL, method POST.
  • Step 3: add one Parameter: order_number, type String, required, description “the customer’s order number”. Turn on the caller_phone system parameter if your workflow wants it.
  • Step 4: set Speak On Error (“I’m having trouble reaching our order system…”) and click Test — fix any plumbing now, not during a live call.
  • Step 5: assign the tool to your agent, and add a line to its Tool Usage Instructions: “When a caller asks about an order, ask for their order number and use lookup_order.”
  • Step 6: prove it in the Agent Tester — ask about an order and watch the tool call and its response appear in the transcript.

SIP Trunks

Your connection to the telephone network — the plumbing that carries real phone calls in and out.

🔒Optional feature. This section only appears in your dashboard if it has been enabled on your system. If you don’t see it, it isn’t part of your installation.

A SIP trunk is the digital equivalent of a phone line: it connects your system to a telephone carrier (like Twilio or Telnyx) so your agents can receive and make real phone calls. You’ll usually have two:

  • Inbound trunk: lets calls in. It tells your system which carrier is allowed to deliver calls and which of your phone numbers to expect.
  • Outbound trunk: lets calls out — needed for outbound campaigns, transfers, and agent-initiated calls. It holds your carrier’s address and login details.

Trunks can also point at an existing office phone system (a PBX like 3CX) instead of a public carrier — useful for transferring callers to internal extensions and queues. You pick the trunk type when creating it.

1 Use the Setup Wizard (recommended)

Click the Setup Wizard button at the top of the Inbound or Outbound page. The wizard knows the correct settings for the common carriers — it walks you through picking your provider, entering your account credentials and phone numbers, and then creates the inbound trunk, outbound trunk, and a dispatch rule for you in one pass. For most people this is the only trunk setup they’ll ever do.

2 Or create a trunk manually

If your provider isn’t in the wizard, create the trunk by hand. The fields in plain words:

  • Trunk Name: a friendly label so you recognise it later (e.g. “Twilio Production”).
  • Address (outbound): your carrier’s server address, from their documentation (e.g. sip.twilio.com). Including the port (like :5060) is recommended.
  • Username & Password: the SIP login your carrier gave you. These prove to the carrier that outgoing calls really come from your account.
  • Phone Numbers: the numbers you’ve purchased from the carrier. Always enter them without the + prefix (e.g. 61400123123).
  • Number Format: whether your carrier expects numbers with or without the + prefix. Twilio and most carriers want “WITH +”. This setting adds the + automatically — that’s why you never type it yourself.
  • Allowed IP Addresses (inbound): which internet addresses may deliver calls to you. Restricting this to your carrier’s published addresses is an important security measure — it stops strangers from injecting calls. Addresses added here are automatically excluded from the security ban system.
  • Allowed Phone Numbers (inbound, optional): only accept calls from these caller numbers — useful for a private line that should only ever receive calls from known numbers. Leave empty to accept any caller.
  • Auth Username / Password (inbound, optional): an alternative to IP restrictions — incoming calls must log in with these credentials instead.
  • Transport: the connection style — UDP (fastest, the usual choice), TCP (more reliable on some networks), or TLS (encrypted).

3 Test it

After creating an outbound trunk, use the Create Outbound Call button to place a real test call to your own mobile: pick the SIP Trunk, enter the Phone Number to dial, and leave the Room Name and Participant Identity fields on their suggested values (they just name the test session internally). Check that it rings, the caller ID looks right, and you can hear audio both ways. For inbound, ring one of your numbers after you’ve set up a dispatch rule (next section). Trunk configurations can also be exported and imported as JSON for backup (passwords are excluded for safety).

Audio codecs and media timeout (advanced)

Every trunk has an Audio Codecs section near the bottom of its form. You can safely ignore it — the defaults match how trunks have always behaved, and saving without touching it changes nothing.

A codec is the format your phone calls travel in. Two matter here:

  • G.711 (listed as PCMU and PCMA) — the standard telephone format. Almost every carrier in the world supports it. Normal phone-call quality.
  • G.722 — “HD Voice”. Carries roughly twice the audio detail, which can make your agent understand callers more accurately — if your carrier offers it. Many do not.

By default all three are ticked and your carrier picks whichever it prefers. Ticking Only allow the codecs ticked above forces your choice instead.

Restricting codecs can take your phone line down. If your carrier cannot offer a codec you have ticked, it refuses the call outright — inbound calls stop arriving and outbound calls stop connecting. There is no warning beforehand, because the dashboard has no way to know what your carrier supports until a call is attempted.

If you want to try G.722 for better accuracy: tick it, untick the others, save, then immediately make a test call. If the call fails, tick all three codecs again and save — that puts everything back exactly as it was.

Media timeout sits just below. It hangs up a call whose audio has stopped flowing, rather than leaving a silent line open indefinitely. Leave it blank unless stuck silent calls are a problem you actually have. If you do set one, 60 seconds is a sensible starting point; the minimum allowed is 30.

Do not set the media timeout low. Some carriers stop sending audio while nobody is speaking. On those carriers, a caller who goes quiet for a moment can be hung up on mid-conversation. Too long is harmless; too short drops live calls.

This is not the same as an agent’s maximum call length — that limits a healthy call, while this one ends a call that has already gone dead.

Step-by-step provider guides (downloadable)

Written walkthroughs with screenshots exist for each supported carrier — they cover the provider’s own control panel as well as the dashboard side. Find them under Settings → Notes → Guides (admins), or click the Guide button inside the SIP Setup Wizard to get the one matching your chosen provider:

  • Tronic Cloud (recommended — IPs and outbound host pre-filled), Twilio, Telnyx, Vonage, Plivo, Cloudonix, and Vobiz — one guide each for creating the trunk on the provider’s side and connecting it here.
  • 3CX (SIP URI Transfer): let voice agents transfer callers to your 3CX phone system’s extensions.
  • 3CX SMS Chat: route customer SMS conversations into 3CX chat.

Dispatch Rules

The switchboard — dispatch rules decide which agent answers which phone number.

A trunk brings a call into your system; a dispatch rule decides what happens next. Without a matching rule, an incoming call has nowhere to go. Each rule says: “calls arriving on these trunks (and optionally these specific numbers) get answered by this agent”. Rules are checked in order and the first match wins.

1 Create a rule

  • Name: a friendly label like “Sales Line”.
  • Dispatch Rule Type: how calls are grouped into conversations. Individual — each caller gets their own private conversation with the agent; this is the normal choice for AI agents. Direct — every call lands in one shared room. Multi-Line — conversations are grouped by the number that was dialled.
  • Trunk IDs: which inbound trunk(s) the rule applies to.
  • Phone Numbers: match only these specific numbers — or leave empty to match every number on the selected trunks (a handy catch-all).
  • Agent Name: the agent that answers matching calls. Remember: it must be running on the Voice Agents page. (If the rule uses a Time Profile, this becomes the fallback — see below.)
  • Auto-Record Calls: tick to automatically record every call this rule routes. Recordings appear on the Recording page.
  • Time Profile (Optional): hand routing over to a named weekly schedule — see below.
  • Room Name / Room Prefix: what the conversation’s internal session is called. Individual rules use a Room Prefix (each caller gets a unique name like caller-123); Direct rules use one fixed Room Name. The defaults are fine — you’d only change them to make sessions easier to recognise on the Rooms page.
  • PIN (Optional): callers must key in this PIN before they’re connected — a simple gate for private lines.
  • Hide Phone Number: a privacy option that keeps the caller’s number out of the session details. Leave it off if your agents use caller-number features like memory or the {{user_number}} variable.
  • Agent Metadata / Rule Metadata / JSON tab: advanced extras for custom integrations — safe to ignore. The JSON tab lets technical users paste a complete rule definition directly.

2 Route different numbers to different agents

Create one rule per line: your sales number → the Sales agent, your support number → the Support agent. Add a final catch-all rule (no phone numbers specified) so any unmatched call still gets answered by a default agent instead of ringing out.

3 Time Profiles — business-hours routing

The Time Profiles tab lets you define a named weekly schedule where each time slot picks its own agent — e.g. Mon–Fri 9–5 goes to your day agent, evenings and weekends to your after-hours agent. Attach the profile to a dispatch rule and one rule handles the whole week.

  • Profile Name & Timezone: the label, and the timezone all the slot times are read in — set this to your business’s timezone, not the server’s.
  • Weekly schedule: per-day time slots, each with its own agent.
  • Fallback Agent: who answers at times no slot covers. Important: if this is empty and the dispatch rule has no default agent, calls arriving outside every slot won’t be answered at all — always set one or the other.

Phone Numbers

One page that shows every phone number your system knows about.

The Phone Numbers page is a consolidated inventory: every number from every trunk, in one list, with the trunk it belongs to and whether it’s used for inbound calls, outbound caller ID, or both. Use it to answer “which agent answers this number?” and “which trunk does this number live on?” at a glance.

  • Adding a number: numbers aren’t created here — you buy them from your carrier, then add them to the relevant trunk (inbound trunk to receive calls on it, outbound trunk to present it as caller ID). This page reflects what’s on your trunks.
  • Format: numbers are shown in international format — country code followed by the number (e.g. +61412345678).
  • Making a number live: a number receives calls once it’s (1) on an inbound trunk, (2) matched by a dispatch rule, and (3) that rule’s agent is running. If a number isn’t answering, walk that checklist in order.

Campaigns

Outbound auto-dialing — give an agent a contact list and it calls everyone for you.

A campaign automatically dials a list of contacts using a chosen outbound trunk and agent. The system paces the calls, tracks the outcome of every number, and lets you retry the ones that didn’t answer. Typical uses: appointment reminders, follow-ups, surveys, and sales outreach.

1 Create the campaign

  • Campaign Name: a descriptive label (e.g. “March Reminder Calls”).
  • SIP Trunk: the outbound trunk to dial through. It must have a valid caller ID number configured.
  • Agent: the agent that handles every call in this campaign.
  • Concurrent Calls: how many calls run at once (choose 1, 2, 3, 5 or 10). More is faster but harder on your system and your carrier.
  • Delay Between Calls: the pause before each new call starts — anywhere from 3 seconds up to 15 minutes.
  • Operating Hours — Restrict calls to specific hours: tick this and set a Start Time, End Time, and Timezone (your contacts’ timezone, not yours!) and the campaign only dials inside that window — it pauses itself outside the hours and resumes the next day until the list is finished. Strongly recommended: it’s what stops a big campaign from ringing people at 9 pm.
💡Start small. Run your first campaign with 1–2 concurrent calls and a short test list. Listen to the first few calls in Call History, tune the agent, then scale up.

2 Add contacts — by hand or CSV

Manual entry: add contacts one at a time. Only the phone number is required — enter it with the country code and no + sign (e.g. 61412345678). The optional fields (Name, Company, Description, Job Title, and two custom fields) feed the personalisation variables below.

CSV import: upload a .csv file (not Excel .xlsx) for big lists. With a header row, columns can be in any order using these exact names: phone, name, company_name, company_description, job_title, custom_field_1, custom_field_2. Without a header row, the columns must appear in exactly that left-to-right order. Only phone is required.

3 Personalise every call with variables

Put these placeholders anywhere in the agent’s System Prompt and each call fills them with that contact’s real data:

  • {{Name}}: the contact’s name — “Hi {{Name}}, how are you?”
  • {{CompanyName}} and {{CompanyDescription}}: their company and a line of context about it.
  • {{JobTitle}}: their role.
  • {{CustomField1}} and {{CustomField2}}: anything you like — account numbers, appointment dates, product interest.
  • {{user_number}}: the number being dialled.

4 Schedule and run

  • Start Immediately: dialing begins as soon as you save.
  • Save as Draft: the campaign sits in Idle until you press Start.
  • Schedule for Later: pick a date and time; the campaign starts itself.

Status badges tell you where things stand: Idle (created, not started), Scheduled, Running, Paused (can resume), Completed, or Cancelled (permanently stopped).

5 Track results and retry

The progress bar colours each contact’s outcome: green (answered/completed), red (failed), yellow (no answer). Click the eye icon for the detailed per-contact call log. After a campaign finishes:

  • Retry Failed: redials only the numbers that failed or didn’t answer.
  • Export Results: downloads a CSV with every contact’s details, outcome, timestamp, and call duration.
  • Delete: removes a completed or cancelled campaign and its data.
⚠Call responsibly. Schedule campaigns during appropriate hours for your region, and make sure your list and message comply with local telemarketing rules.

Agent Tester

Talk to your agents right in the browser — no phone call, no cost of a real line.

The Agent Tester is the quickest way to try out an agent while you build it. Chat with it by text, or hold a full voice conversation through your computer’s microphone. It works for both voice agents and chatbot agents.

⚠Voice agents must be started first. The tester talks to the live agent, so a voice agent needs the green “Running” badge on the Voice Agents page before it will respond here. Chatbot agents need to be Enabled on the Chatbot Agents page. If you connect and hear nothing, that’s the first thing to check.

1 Select an agent

The Select Agent dropdown lists your agents in two groups — Voice Agents and Chatbot Agents. Pick the one you want to test.

2 Choose Text or Voice mode

  • Text Mode: type messages and read the agent’s replies. Fast, silent, and great for testing prompts, tools, and knowledge lookups without saying a word.
  • Voice Mode: a real spoken conversation through your microphone — the agent replies in its configured voice. Your browser will ask for microphone permission the first time. Voice mode is available for voice agents and full-voice chatbots; text-only and avatar chatbots test in Text mode only (the Voice toggle greys out for them).
⚠Text mode does not test your speech settings. When you test by typing, the agent never listens and never speaks — so your speech-to-text provider, voice, VAD, turn detection and noise cancellation are not used at all. This catches people out: if you have just switched to a new speech-to-text engine or a new voice, testing by typing will tell you nothing about it, and hearing no audio does not mean the new provider is broken. Switch to Voice Mode to test anything on the speech side. The tester shows a yellow reminder above the chat whenever you are in text mode.

3 Connect and talk

Click Connect. The connection status changes as the test session starts, and the agent greets you just like it would a real caller. Everything you say (or type) and every reply appears in the transcript, including when the agent uses a tool — so you can see exactly what it did and why. Click Disconnect when you’re done.

A few small controls on the left panel are worth knowing:

  • Connection status: the dot-and-text indicator below the Connect button — it moves from Disconnected through connecting to connected, so you can tell a slow start from a failed one.
  • Voice Settings — Microphone / Speaker: in Voice mode, pick which of your computer’s microphones and speakers the test uses (handy with headsets). Default uses whatever your browser prefers; your choice is remembered for next time.
  • Mute button & connection quality bars: while connected in Voice mode you can mute your own mic mid-test, and the signal bars show the connection quality between your browser and the server — if the agent sounds choppy but the bars say Excellent, the problem is the agent, not your network.
  • Connected to / Room: shows which agent you’re actually connected to and the internal session name — useful when cross-checking against the Rooms page or logs.

4 The per-test LLM override (voice agents, Text mode)

When testing a voice agent in Text mode, a Text Chat Settings panel lets you pick which LLM Provider and Model processes your messages for this test only — without changing the agent’s saved configuration. It’s a cheap way to answer “would this agent behave better on a different brain?” before committing.

ℹChatbot agents are different: they always use the model configured in their own editor (including their fallbacks). Instead of an override, the tester simply shows you which model that is.

5 Testing chatbot agents

Chatbot test sessions run the exact same pipeline as the website widget — same prompt, tools, knowledge base, memory, and welcome message — but in a throwaway session: nothing is saved to Chat History. Be aware that the chatbot’s tools (webhooks, SMS sends) do run for real during a test, exactly as they would for a website visitor.

6 The Debug Panel

The panel on the right shows a live feed of technical events — connection status, participants joining, audio tracks, data messages, and transcriptions. You can ignore it day to day, but when an agent misbehaves it’s a goldmine: it shows whether your words were heard correctly and whether the agent actually responded. Voice mode also shows a live Microphone level meter so you can confirm your mic is working.

Which testing tool, when?

  • Agent Tester (this page): while you’re building — make a change in the editor, talk to the agent, adjust, repeat. Instant and interactive.
  • Simulation: when you want coverage — twenty scenarios, difficult personas, and an AI judge, run as a batch. Use it before launch and after every prompt change.
  • A real phone call: the final check — only a real call exercises your SIP trunk, caller ID, and true phone audio quality. Always make one before going live.

Simulation

Batch-test your agents with AI-played customers — and get a pass/fail report card.

The Agent Tester lets you talk to an agent one conversation at a time. Simulation scales that up: an AI plays the customer, runs whole conversations against your agent automatically, and an AI judge scores each one against your success criteria. Run twenty scenarios overnight and read the report card in the morning.

Why this matters: the most expensive way to find out your agent mishandles angry callers is to let it mishandle a real one. Simulation lets you discover and fix those problems in private, before a customer ever hears them — and re-check every time you change something.

The page has three tabs, left to right:

  • Test Suites: bundles of test cases you run together as one batch, with pass-rate history and a “what changed since last run” comparison.
  • Test Cases: the individual scenarios — one imaginary caller each, with a script and a checklist for success. This is where you’ll spend most of your setup time.
  • Results: the history of every run — verdicts, scores, judge feedback, and full transcripts.

1 Create test cases

On the Test Cases tab, click New Test. Each test case describes one kind of caller and what a successful conversation looks like. Field by field:

  • Name: what this scenario tests (e.g. “Angry customer wants a refund”). Make it descriptive — it’s what you’ll see in results lists later.
  • Agent: which of your agents the test runs against.
  • Simulation Mode: Text (fast — recommended) runs the same agent with all its tools and knowledge as a text conversation — a full test finishes in seconds. Voice — full audio pipeline runs a real two-agent audio call: much slower, but it also exercises speech recognition, the voice, and turn-taking. Use text for everyday checks and voice when you specifically want to test how the agent sounds and listens.
  • User Prompt: the scenario script the simulated caller follows — who they are, what they want, and any details they should volunteer (name, phone number, preferred day). This is where the substance of the test lives. Write it like stage directions for an actor: “You are Sarah. Your dishwasher was repaired last week and it’s leaking again. You want someone out today. If offered tomorrow, push back once, then accept.”
  • Caller Persona: optional. A dropdown of twelve prebuilt difficult-caller personalities layered on top of your User Prompt — Angry Customer, Rambler, Off-Topic Drifter, Adversarial / Jailbreaker, Confused Caller, In a Hurry, Non-Native Speaker, Vague Caller, Prankster, Hesitant Caller, Interrupter, and Mumbler / Noisy Line. The Hesitant Caller recalls details slowly and pauses mid-sentence — use it to check your agent waits for slow answers instead of cutting the caller off or re-asking. The last two are marked (voice only) because interrupting and mumbling only exist in audio. Personas are the quickest way to harden an agent: the same booking scenario becomes a very different test when the caller is furious or rambling.
  • Success Criteria: the checklist the judge marks against — e.g. “the agent apologised”, “the agent offered a refund or escalation”, “the agent did not invent policy”. Write one criterion per line, each independently checkable. Vague criteria (“the agent was good”) produce vague verdicts; specific criteria produce actionable ones.
  • Evaluation Judges: tick which dimensions get graded. The Success Criteria judge scores the conversation 0–10 against your checklist (7+ = pass); the others are specialist pass/fail checks: Task Completion (did the caller get what they came for), Accuracy (were factual answers right), Tool Use (were the right tools called with the right inputs), Safety (nothing harmful or off-policy), Relevancy, Coherence, Conciseness, and Handoff (transfers done properly). Accuracy and Tool Use need tool-call data, which only text-mode transcripts capture — the UI notes this. A judge marking fail fails the run; a judge marking maybe doesn’t.
  • Tool Assertions: hard rules about tools, checked against the tools the agent actually called with no AI opinion involved — Must call a tool (optionally with specific argument values, e.g. date=2026-09-10), Must NOT call a tool, or Call in order. Any broken rule fails the run outright and shows as a tool assertions verdict with a tick or cross per rule. Text mode only: voice runs record no tool calls, so there the rules report “maybe” and never fail the run.
  • Test Variables: key-value pairs available as context during the simulation (like an account number or booking reference), so scenarios that rely on caller data work realistically.
  • Tester LLM Override / STT / TTS / Voice: which AI plays the customer. Leave on Use default normally. In voice mode the tester also gets its own ears (Tester STT Provider) and voice (Tester TTS Provider / Voice) — handy if you want the simulated caller to sound different from your agent.
  • Max Turns / Max Duration (seconds): caps on conversation length and wall-clock time so a stuck test can’t run forever (defaults 20 turns / 300 seconds).
  • Enable schedule: tick to re-run this test automatically — pick a Frequency (daily or weekly), a Day of Week for weekly, and a Time. Scheduled tests quietly keep watch so drift shows up in your Results tab, not in customer calls.
💡Let the AI write your tests. The AI Generate Test Scenarios button reads your agent’s prompt and drafts realistic test cases for you — personas, goals, and success criteria included. Pick how many to draft and which Drafting LLM Provider / Model to use (the default is fine), then edit anything you’d phrase differently before saving. This is the fastest way from zero to a useful test set.

2 Group tests into suites

The Test Suites tab groups related test cases so you can run them as one batch — for example a “Pre-launch checks” suite containing your ten most important scenarios. A suite run executes every test inside it and reports a combined score.

  • Suite Name & Agent: the suite’s label, and the agent whose test cases it can contain.
  • Tests in this Suite: tick the test cases to include.
  • Attempts per Test: each test repeats this many times (up to 5) to catch flaky behaviour — an agent that passes 1 of 3 attempts has a problem worth seeing. Start with 1 for speed; use 3 before a launch.
  • Parallel Text Tests: how many text tests run at once (up to 5). Voice tests always run one at a time, after the text batch.
  • Suite card badge: after a run, each suite shows its latest pass rate — green at 80%+, yellow from 50%, red below — plus the average judge score out of 10.
  • History & compare buttons: the clock icon opens the suite’s run history; the arrows icon opens Regression Compare, showing which tests changed verdict between the latest run and the one before — improved, regressed, same, new or removed, per test. This is the fastest way to spot what a prompt change broke.
ℹPrompt versions are tracked for you. Every suite run records which version of the agent’s prompt it ran against, so Regression Compare can say “pass rate fell from 90% to 60% between prompt v4 and v5” — pointing straight at the change that caused it.

3 Read the results

While a test runs, a live panel shows the conversation as it happens; the Test Cases list also shows each test’s Text/Voice badge, its schedule, when it last ran, and its last Passed/Failed result. The Results tab keeps a history of every run. Open any run and read it in this order:

  • Passed / Failed: the headline verdict. Failed doesn’t always mean broken — read on before reacting.
  • Score & Criteria Results: the 0–10 score and a per-criterion breakdown showing exactly which checklist items the agent met and which it missed. A 6/10 that missed “offered a callback” is a very different problem from a 2/10 that never understood the request.
  • Judge Verdicts & Feedback: each ticked judge’s verdict with its reasoning in plain language — usually the fastest pointer to what needs fixing in the prompt.
  • Tool Assertions: one line per rule with a tick or cross and what actually happened (“called 2× but arguments did not match”). These come from the recorded tool calls, so they are the one part of the verdict that cannot be argued with.
  • Transcript: the full simulated conversation, including any tool calls the agent made and what they returned. When a judge says something went wrong, find the exact turn here.

4 The Replay Workbench (test prompt changes against a real call)

From any completed run (and from a real call’s detail page), you can open the Workbench — a side-by-side replay tool. It takes the caller’s side of an existing conversation and replays it, turn by turn, against a modified version of your agent, so you can see exactly how a prompt change would have altered a conversation that actually happened.

  • Select a run: pick the recorded conversation to replay.
  • Prompt to test: start from the agent’s current (live) prompt, load any saved prompt version (v1, v2… from the agent’s version history), or type an experiment directly — experiments are not saved, so you can try ideas freely.
  • Tool handling: choose Recorded tools (replay the tool results from the source call — the safest, most faithful option), Fake tools (safe placeholders), or Real tools (⚠ executes for real — only if you understand the side effects, e.g. it may actually send an SMS or book a job).
  • Continue naturally after script: when the recorded caller turns run out, let the AI keep playing the caller so the conversation finishes naturally instead of stopping mid-flow.

The output is a per-turn comparison: what the agent said originally versus what the new prompt says. This is the safest way to answer “would my change have fixed that call?” before shipping it.

Walkthrough: your first simulation, start to finish

  • Step 1 — generate scenarios. Test Cases tab → AI Generate Test Scenarios → pick your agent, draft 5 scenarios. Skim each one; tighten the success criteria to things you genuinely care about.
  • Step 2 — run one test. Click Run on a single text-mode test. Watch the live panel: you’ll see the AI caller and your agent talking within seconds.
  • Step 3 — read the result. When it finishes, open it in the Results tab. Read the verdict, then the criteria breakdown, then the judge feedback, then skim the transcript to see the moment things went right or wrong.
  • Step 4 — fix and re-run. If it failed for a real reason, adjust the agent’s prompt in the editor (or test the fix in the Workbench first), then re-run the same test. Repeat until it passes.
  • Step 5 — build your suite. Suites tab → New Suite → name it “Pre-launch checks”, tick your tests, set Attempts to 3 → run it. Green badge at 80%+ means you’re in good shape.
  • Step 6 — automate. Put your most important test on a weekly schedule. From now on, every prompt change gets the same treatment: run the suite, open Regression Compare, ship only when nothing regressed.

When to use Simulation

  • Before going live: run a suite covering your critical scenarios and don’t launch until they pass.
  • After every prompt change: re-run the suite to make sure the fix for one problem didn’t break something else.
  • After a bad real call: open it in the Workbench, replay it against a candidate fix, and prove the fix before shipping it.
  • On a schedule: a weekly automatic run quietly confirms nothing has drifted.
ℹNote: simulations use your AI providers, so each run costs a small amount of AI usage — typically far less than the cost of discovering a broken agent through real customers.

Improvement Lab

Find out why calls fail — and stop the same problem coming back.

🔒Optional feature. This section only appears in your dashboard if it has been enabled on your system. If you don’t see it, it isn’t part of your installation.

The Improvement Lab is the workbench for turning real recorded calls into concrete improvements. It has three tabs — STT Lab, Scoring, and Improve — that form a loop: measure how calls really went, find out what caused the failures, and lock in fixes as permanent tests so regressions get caught automatically.

1 STT Lab — find out what the agent misheard

Pick a recorded call and replay its audio through different speech-recognition engines and noise-cancellation settings, side by side, next to a “best possible transcription” reference. You can literally see which words the agent misheard and which setup hears your callers best. Spot a misheard word (a product name, a suburb)? Adding it to the agent’s vocabulary is one click, saved through the normal versioned agent save.

Picking a call

The picker lists your recent recorded calls with when they happened (in your dashboard timezone), which agent took them, and the caller’s number. A call is only eligible if its recording still exists and it ran the standard pipeline — ineligible rows say why. Two preset buttons build the comparison for you:

  • Live config vs no noise cancellation: replays the call twice — exactly as the agent was configured on the day, and again with noise cancellation turned off — so you can see whether noise cancellation is helping or hurting. (Needs a call recent enough that its live settings were recorded.)
  • Engine shoot-out (best possible): one row per configured provider, each in “best possible” mode — a straight accuracy contest on your real audio.
  • Add row: build any custom combination yourself.

The comparison table — what each column means

  • Label: a name for the row, only used in the results (e.g. “Deepgram no NC”).
  • Engine / Model: the speech-recognition provider and which of its models to test. Providers without a configured API key show as “not configured” and can’t be selected.
  • Noise cancellation: which noise-cancellation processor to apply to the audio before recognition, plus a strength (0.1–1.0 — higher removes more noise but can start eating quiet speech).
  • Mode — the most important choice on the row:
    • What the agent actually heard: the audio is streamed in real time through the same live pipeline your agent uses — the streaming model, the noise cancellation, the pressure to finalise words quickly so the agent can reply. This answers: “if my agent were configured this way, what would it have heard on this call?”
    • Best possible transcription: the whole recording is sent to the provider’s offline service in one go — no time pressure, and it can look at the entire call at once. This is that provider’s accuracy ceiling on your audio: “how good could the transcript possibly be?”
    The gap between the two is the diagnosis: if “best possible” is excellent but “what the agent heard” is poor, your losses come from the live setup (model choice, noise cancellation, finalisation speed) — all fixable in the agent’s config. If even “best possible” is bad, the audio itself is the problem (line quality, background noise) and no setting will fully fix it. Some models are streaming-only (for example Deepgram Flux) and can only run as “What the agent actually heard” — the Mode box tells you when that’s the case.

Reading the results

  • Setup / How it ran: the row’s label and which mode it used. Rows that failed show the reason here instead of numbers.
  • Caller words missed: how much of what your caller said came out wrong — lower is better. This is the fair, headline comparison column.
  • Whole call: the same measure over both speakers mixed together. Only use it to compare rows against each other, not as an absolute score.
  • “—” in a column: the Lab wasn’t confident enough about which speaker was which on that row, so it withholds the number rather than show a misleading one (such rows are also left out of the ranking).
  • The best row is highlighted, and misheard words in the transcripts offer a one-click add to vocabulary button.

Running it later — scheduled runs

Replays are heavy work, so you can schedule them for after hours instead of running them on the spot. In the cost-estimate popup, choose Schedule for later… instead of Run it:

  • How often: Once (pick a date), Daily, or Weekly (pick a weekday).
  • Time: when it fires, in your dashboard’s configured timezone (shown next to the fields). If the server is busy at that moment — a live call in progress, another Lab run, or low memory — it quietly retries for up to 4 hours, then reports why it couldn’t run.
  • Stop after (runs): optional, for repeating schedules — pauses the schedule after that many runs. Each run is charged the estimated cost, whether or not it succeeds, so this is your spending cap.

A Scheduled runs card then appears on the page showing each schedule’s call, cadence, Next run time, Cost / run, how many Runs it has done (and its stop-after limit), and a Status badge: scheduled (waiting for its time), waiting (its time arrived but the server was busy — it will keep trying), problem (it couldn’t run — hover or read the note for why), or stopped. After a run fires you’ll also see how the last run ended — including a “not billed” note if the charge couldn’t be recorded — with an open link to the results. Cancel removes a schedule at any time. Overnight results appear in Past experiments like any other run. Repeating schedules pause themselves automatically after three failed runs in a row, so an unattended schedule can’t keep spending on a broken setup. If the cost of the run changes (for example you change pricing or the agent’s settings), the schedule stops and asks you to re-create it rather than charging an amount you never agreed to.

2 Scoring — measure real calls against a checklist

The Scoring tab answers the question every agent owner should be able to answer but usually can’t: “what percentage of my real calls actually succeed?” It works in three stages, each needing your approval:

Stage 1 — approve the success checklist

  • Agent: pick the agent to measure. Each agent gets its own checklist.
  • Success checklist: click the draft button and the AI reads the agent’s own prompt and tools, then proposes what a successful call looks like for this agent (e.g. “caller’s issue identified”, “booking created or callback arranged”). Nothing is scored until you review this list — edit any line, add your own criteria, remove ones you don’t care about, then Save draft / approve. The checklist is the yardstick, so it’s worth two minutes of care here.

Stage 2 — score a batch of calls

  • From (window): how far back to score (in days). Calls from the last half hour are excluded — they may still be getting their summaries.
  • Re-score calls already scored: normally off, so repeat runs only pay for new calls. Turn it on after changing the checklist so old calls are re-judged by the new yardstick.
  • Spot-check % of passed calls: the AI double-checks a random slice of the calls it passed, guarding against a too-generous judge.
  • Cost estimate: before anything runs you see an itemised estimate (“Score them” confirms it). Scoring uses your AI summary model, so a batch of 100 calls costs roughly 100 short AI reads.

Stage 3 — read the numbers, then triage the failures

  • Success rate: the headline percentage, shown per agent with its trend. Verdicts are three-state — pass, fail, or unknown — so ambiguous calls abstain rather than polluting your numbers. (“Not enough data yet” means too few scored calls to trust a percentage.)
  • Recent scoring runs: each batch with how many calls it scored and what it found — open any run to see per-call verdicts with reasoning.
  • Failures to triage: every failed call lands here with the AI’s best guess at the cause (mishearing, prompt gap, tool failure, caller hung up early…) and the supporting evidence quoted inline. Your job is one click per row: confirm the cause if the evidence supports it, or dismiss it. Confirming records the cause on the call and feeds the Improve tab. When the AI can’t tell, it says so (“Could not determine the cause with confidence”) instead of guessing.

3 Improve — turn failures into permanent tests

The Improve tab is where confirmed failures become regression tests — permanent guards that re-check the exact thing that went wrong, forever. Two kinds are created depending on the confirmed cause:

  • Conversation tests: for prompt/behaviour failures. The AI drafts a Simulation test case from the failed call — Test name, Caller scenario (what the tester will do), and Success criteria — and shows it to you under Review the drafted test. Edit anything, then keep it. It becomes a normal test on the Simulation page, and Add to suite puts it straight into one of your suites so it runs with every batch.
  • Audio regression tests: for mishearing failures. The call’s audio is pinned and automatically re-checked against a fixed reference transcription whenever you change speech settings — so the caller who was misheard once can never be silently misheard again by a “better” configuration.
  • Expand with AI → Generate variations: writes extra variations of a conversation test (same failure, different phrasings and caller moods). Tick the ones worth keeping — Keep ticked variations saves them.
  • Ready to promote / Run all ready: the queue of drafted tests awaiting your review, and a one-click way to execute every audio test back-to-back with a single upfront cost confirmation.

4 Noise Cancellation — find the setting that hears your callers best

The STT Lab compares one call at a time. The Noise Cancellation tab asks the bigger question: across several calls, which noise-cancellation setting lets the speech engine hear your callers best? Pick an agent and a handful of its recorded calls, tick the settings to try, and the Lab replays every call through every setting with the agent’s current speech engine held fixed — same audio, different treatment — then ranks the settings and lets you apply the winner in one click.

Picking calls and settings

  • Agent: only voice agents with a speech engine are listed. The engine the sweep holds fixed is shown above the call list.
  • Calls: the agent’s recent recorded calls, newest first, with the newest five pre-ticked (tick up to ten). Greyed rows say why they can’t be replayed (no recording, realtime pipeline, over the 30-minute limit). For the fairest test pick calls that sound like your real traffic — a few noisy ones included.
  • Settings: No noise cancellation, WebRTC APM, DTLN and ai.coustics (with its model and a strength each). Settings that aren’t installed or have no key are greyed out with the reason. The setting the agent uses today is marked current and its strength is pre-filled, so the comparison always includes what you run now.
  • Estimate cost → Start sweep: the estimate covers the reference transcripts and the speech-engine minutes (one per call per setting). Tick the acknowledgement to enable Start.
ai.coustics minutes are not in the estimate. ai.coustics bills processed minutes on your ai.coustics account, and the dashboard has no rate for it. A sweep with an ai.coustics setting processes every ticked call once through it.

What happens while it runs

The sweep works through the calls one at a time in the background, and each call is charged when it starts. You can leave the page; the Results panel keeps updating and the sweep appears under Recent sweeps so you can reopen it later. If the server is busy (a live call, another Lab run, low memory) the sweep pauses and shows a Resume button rather than retrying blindly. If the dashboard restarts mid-sweep the sweep shows as Interrupted; Resume picks up where it left off without re-charging calls that already finished. Resume and re-run failed calls replays the ones that failed — and those are charged again. Stop after this call ends the sweep cleanly.

Reading the results

  • The grid: one row per call, one column per setting. Each box is the share of the caller’s words that came out wrong under that setting (missed, misheard or added) — lower is better; the best box in each row is highlighted. A row marked not compared means the Lab couldn’t tell the caller apart from the agent confidently enough on that recording, so it is shown but kept out of the ranking. Dual-channel recordings (Settings → Storage → Audio options) avoid this entirely.
  • The verdict: the ranking is paired — settings are compared only on the calls every setting completed, so each setting is judged on identical audio. A winner needs at least three such calls and a lead of at least one point over the runner-up; otherwise you see Too close to call (the difference is noise at this sample size) or Not enough data. The sentence under the trophy states the winner’s number and, when you included No noise cancellation, what it improved on.
  • Ranking table: Caller words wrong is pooled over the compared calls (long calls weigh more than short ones); Wins counts calls where the setting beat the runner-up by at least a point (closer results count as ties); Coverage is how many calls the setting completed. A setting that failed on any call is shown greyed with the reason and can’t win — a noise canceller that crashes is not a candidate, however well it did elsewhere.
  • Apply to agent: writes that setting (provider, strength, ai.coustics model) to the agent. It takes effect on the agent’s next call; nothing restarts. The row is then marked applied.

Listening to what the agent heard

Every box has a play button, and each row has a Raw button for the untreated audio. The Lab keeps the exact audio it fed to the speech engine under each setting, so you can hear for yourself whether a setting is cleaning up the line or eating the caller’s voice. The player sits above the results and keeps playing while the sweep updates. Saved audio is compressed, kept for the newest twenty sweeps (up to 400 MB), removed with the sweep, and never touched by recording retention.

The diagnostics (never used for ranking)

  • Voice kept: how much of the caller’s speech energy survived the noise cancellation (100% = untouched). A low number on a setting that also scores badly is the classic sign of a noise canceller damaging speech.
  • Noise kept: how much of the between-speech background survived — lower means more noise removed.
  • Dropouts: the share of the caller’s speech frames where the level dropped by more than half — localised damage that an average can hide.
  • ms/frame: processing time per audio frame — the CPU cost of the setting on this server.
Word accuracy is the verdict; the diagnostics explain it. A setting can remove a lot of noise and still lose (it also removed consonants), or keep everything and still lose (the noise was confusing the engine). Trust the words-wrong number, use the diagnostics to understand why.
Audio geometry. The tab states the sample rate and frame size it replays at — the same as live calls, so what you hear and measure is what the agent gets. If this install has opted into 16 kHz input (Settings → Storage → Call Audio Processing) the tab warns that the replay geometry differs; the settings are still comparable with each other.
Audio regression tests and this fix. Before this release the Lab’s “current agent config” ignored the agent’s noise-cancellation choice, so audio regression baselines were recorded without it. Such tests now show a re-baseline recommended badge on the Improve tab: press Re-baseline before trusting their next result.

Walkthrough: from “how are we doing?” to a guarded fix

  • Step 1 — set the yardstick. Scoring tab → pick your agent → draft the success checklist → edit until it says what you mean by a good call → approve.
  • Step 2 — score a week. Set From to 7 days, leave re-score off, accept the estimate. A few minutes later you have an honest success rate.
  • Step 3 — triage the failures. Open Failures to triage. For each row, read the quoted evidence and confirm or dismiss the suggested cause. Ten minutes of this tells you more about your agent than a month of gut feel.
  • Step 4 — fix the top cause. Mishearing a product name? STT Lab: replay one of those calls, compare engines/noise settings, add the word to the vocabulary, or change the speech setup. Prompt gap? Fix the prompt in the agent editor (test it in the Simulation Workbench first if you like).
  • Step 5 — lock it in. Improve tab: promote the confirmed failures to tests — review each draft, keep it, add conversation tests to your suite. Now the failure mode is guarded: if it ever comes back, a test goes red before a customer notices.
  • Step 6 — repeat monthly. Re-run scoring on the latest window and watch the success rate trend. The loop — measure, triage, fix, guard — is the whole point of the Lab.

Costs — nothing runs without your say-so

Nothing in the Lab spends money unless you click it (or schedule it after seeing the estimate), and every run shows an itemised cost estimate first. What the Lab spends is added to the original call’s cost breakdown as an “Improvement Lab” line, so it appears in your normal cost reports rather than hiding. Lab runs never create call-history entries of their own — results live in Past experiments on this page.

Good to know

  • Audio replays queue politely: they run one at a time and pause while a real call is active, so testing never degrades live calls.
  • Backups: your tests, checklists, and results are included in system backups — but the pinned audio copies are not. A restored audio test on a new server will ask to be re-created from the original call.
  • Access control: sub-user access is governed by the Improvement Lab permission in Settings → User Management.

AutoResearch

Let the AI study your real calls and propose a better prompt — you stay in charge of what goes live.

Your agent’s system prompt is its job description — and the best evidence for improving it is sitting in your own call history. AutoResearch reads batches of real transcripts, finds the patterns (questions the agent fumbles, moments callers give up, policies it explains badly), and drafts improved versions of the prompt with an explanation of every change. Nothing is ever applied automatically: you read the suggestion, compare it side-by-side with the current prompt, edit it if you like, and click Apply only when you’re happy. Every applied change lands in the prompt version history, so you can roll back any time.

ℹWhere to find it: AutoResearch has its own page in the sidebar, and the agent editor’s System Prompt field also has three related buttons — Enrich with AI (a quick one-shot improvement), AutoResearch (this page’s pipeline), and Versions (the prompt’s full history with restore).

1 The four-step pipeline

Pick an Agent at the top of the page — everything below is per-agent. A full run walks four steps, and Steps to Run lets you run them individually or all together:

  • Harvest Transcripts: collects a batch of your agent’s real conversations to study.
  • Analyze Patterns: the AI reads the batch alongside the current prompt and writes up what’s going well and what keeps going wrong.
  • Generate Suggestions: drafts one to three improved prompts, each with a plain-language explanation of what changed and why.
  • Score Suggestions: grades each draft against your Reference Calls (Golden Set) — calls you’ve marked as examples of how conversations should go — so suggestions are judged by your standard, not the AI’s.

2 The settings, field by field

Engine & model

  • Engine: Built-in (OPRO) works out of the box using your configured AI providers — use this. DSPy Advanced is an optional research-grade optimiser that needs an extra package installed under Settings → Dependencies; try it only after the built-in engine stops finding improvements.
  • Provider / Model: which AI does the analysing. A thinking-class model gives noticeably better analysis than a fast voice model — this runs offline, so speed doesn’t matter here.

Call Selection — what gets studied

  • Most recent calls vs Prioritise problem calls: recent gives a representative sample; problem mode deliberately fills most of the batch with calls that look like failures (errors, abandoned outcomes, negative sentiment, very short calls, and any call a quality judge marked FAIL when Call quality judges is on in Settings → AI Summary) plus a few normal ones for contrast. Problem mode usually finds fixable issues faster.
  • Direction / From Date / To Date / Min Duration (sec): narrow the batch — e.g. only inbound calls from last week longer than 30 seconds, so hang-ups and wrong numbers don’t pollute the analysis.
  • Transcripts (count) & Token Budget: how many conversations to study and a hard cap on how much AI reading you’ll pay for. You see a cost estimate before anything runs.

Reference Calls (Golden Set)

Mark a handful of your best real calls as the golden set. The Score step compares each suggested prompt against these — “would this new prompt have handled our best calls at least as well?” A small, carefully chosen set (3–8 calls) beats a big careless one.

Methodology (advanced, optional)

The Analysis Prompt, Suggestion Prompt and Scoring Prompt boxes let you steer how the AI studies your calls — for example “focus on compliance wording” or “never suggest removing the greeting”. Leave them at the defaults until you have a specific steer to give.

Scheduling

  • Enable scheduled analysis: run the pipeline automatically — Frequency (Daily/Weekly), Day of Week, and Time. Scheduled runs only prepare suggestions; applying one always stays a human decision.
  • Safety rails: manual runs have a 5-minute cooldown per agent, and a schedule that fails three times in a row pauses itself (a Re-enable button brings it back).

3 Reading results & applying a suggestion

  • Suggestions: each result shows the drafted prompt, its Score against your golden set, and “what this version changed, and why” in plain language. Read the why first — it’s the AI telling you what it found in your calls.
  • Suggested prompt (editable): the draft is yours to edit before applying — keep the good ideas, strike anything off-brand.
  • Apply to Live Prompt: opens a full side-by-side comparison of the current live prompt and the new one, with a final editable text box. Confirming makes it the agent’s live prompt and records a new version in the history.
  • Test in Simulation: before applying, send the suggestion to the Simulation Workbench and replay a real conversation against it — the safest possible preview.
  • Versions & rollback: the Versions button in the agent editor lists every prompt version (manual saves, Enrich, AutoResearch applies) with a diff view and one-click restore. Nothing AutoResearch does is irreversible.

Walkthrough: your first AutoResearch cycle

  • Step 1 — build a golden set. Find 3–5 genuinely good calls in Call History and add them as Reference Calls.
  • Step 2 — run the pipeline. Pick the agent, choose Prioritise problem calls, ~20 transcripts, leave the rest at defaults, run all four steps. Accept the cost estimate.
  • Step 3 — read the analysis. Open the result. The pattern write-up alone is usually worth the run — it names the recurring problems in your real calls.
  • Step 4 — pick a suggestion. Compare the drafts and their scores. Edit your favourite until every line is something you’d stand behind.
  • Step 5 — prove it, then apply. Test it in Simulation (run your suite, or replay a bad call in the Workbench). If it holds up, Apply to Live Prompt.
  • Step 6 — watch and repeat. Your suite’s Regression Compare and the Improvement Lab’s success rate tell you whether the new prompt is genuinely better. If not — restore the previous version and try the next idea. Monthly cycles of this loop compound quickly.
💡How the three testing pages fit together: Simulation checks your agent against scenarios you define. Improvement Lab measures and diagnoses your real calls. AutoResearch turns what the real calls reveal into a better prompt — which you then prove in Simulation before it goes live. Measure → improve → verify, in a loop.

The first page you see after logging in: charts and figures for everything your agents have been doing, across ten tabs.

The Analytics page (click Analytics in the sidebar, or the logo) shows your call volumes, costs, response speeds, AI insights and server health. Everything on the page respects the date range you pick at the top.

The controls at the top

  • Date Range dropdown: choose the period the whole page reports on — Today (the default, and the fastest to load), Last 2 days, or the last 7 / 14 / 30 / 60 / 90 days.
  • Custom range…: the last item in the dropdown. A small picker appears with From and To date boxes — pick any two dates up to 90 days apart and click Apply. Click Cancel, press Escape, or click outside the picker to close it without changing anything. Once applied, every chart and the Export button use exactly those dates.
  • Auto-refresh toggle: turn this on to have the page update itself automatically every 30 seconds, 60 seconds or 2 minutes — handy on a wall screen in the office.

Overview tab

The at-a-glance summary. Below the cards you’ll find a Success Status Breakdown pie chart and a Call Trends graph. If something looks off anywhere in the system, this tab usually shows it first.

Everything about call volume and outcomes:

  • Direction: inbound vs outbound split.
  • When calls happen: hourly distribution, Busiest Day/Hour, and a Call Distribution Heatmap — a day-by-hour grid where darker squares mean more calls. Great for deciding staffing or opening hours.

Latency tab

How quickly your agents respond. The key measure is TTFB (“time to first byte”) — in plain terms, the pause between the caller finishing a sentence and the agent starting to speak. The tab shows the average and the P50 / P90 / P99 percentiles, a breakdown of where the time goes (speech recognition, the AI “thinking”, and voice generation), an hourly trend, and a per-agent comparison.

  • Under 500 ms: feels natural — like talking to a person. This is the target.
  • 500–1000 ms: a noticeable but acceptable pause.
  • Over 1000 ms: feels slow — callers start saying “hello? are you there?”. Worth investigating (often the AI model choice — see the FAQ).

Phone-line analytics: total trunks, connection success rate, trunk status, how many dispatch rules you have, and call volume over your trunks, with quick links to manage trunks and dispatch rules.

  • Monthly Usage Summary: Minutes Used, Total Calls and Avg per Call for the current month, plus a Resets date showing when the monthly counters start again.
  • Quota: if your account has a monthly minutes allowance, a gauge shows the percentage used (green, turning amber from 80% and red once over) and the minutes remaining. Unlimited accounts don’t show this card.
  • Resource Caps: sub-users who have limits on how many Voice Agents, Chatbot Agents or Knowledge Bases they may create see a small used-vs-maximum bar for each capped resource.
  • Monthly Usage: a month picker with that month’s Total Minutes, Total Calls, Avg Minutes / Call and Avg Minutes / Day, plus a Minutes-per-Day chart — pick any past month to compare periods.

Server Stats tab

The health of the machine your dashboard runs on: total CPU load (1/5/15-minute averages), memory, swap and disk usage, uptime, network traffic and process count. Service Status cards show CPU and memory for each part of the system (the dashboard, the media server, the agent, the database, SIP and recording services), and a CPU Usage History chart shows each service over the last 24 hours.

⚠Watch the disk: if disk usage creeps towards full, recordings are usually the culprit — see the Recording / Egress section for how to clean up or set automatic retention.

Walkthrough: a five-minute weekly health check

  • Step 1 — Overview tab, range set to 7 days. Call volume trending the right way? Any day with a sudden dip (an outage?) or spike (something viral, or abuse)?
  • Step 2 — Calls & Rooms tab. Scan end reasons: a rise in errors or abandoned calls is the earliest sign something changed for the worse.
  • Step 3 — Latency tab. Response speed still mostly green (<500ms)? If it drifted up, the breakdown shows whether hearing (S), thinking (L) or speaking (T) got slower — that tells you which provider or setting to look at.
  • Step 4 — Price/Cost tab. Cost per call roughly stable? A jump usually means longer calls, a pricier model got selected somewhere, or summaries/memory got switched on for a busy agent.
  • Step 5 — Media/System. Disk not filling, services green. Done — anything odd, drill into Call History for the affected day and read a few calls.

Rooms — watching live calls

Every call happens inside a “room”. This page shows the rooms that are live right now, and lets you peek inside them.

You don’t create rooms for normal calls — the system does it for you. When a call arrives, your dispatch rules automatically create a room, connect the caller, and bring the agent in. One call = one room. When the call ends, the room closes. So the Rooms page is really a live view of calls in progress.

What the list shows

  • Room Name: the room’s automatic name. Click it to open the room’s detail view.
  • Status: Active while the call is running; recently ended rooms appear dimmed with the time since they closed.
  • Participants: how many people (and agents) are connected — a normal call shows the caller plus the agent.
  • Live TTFB: the agent’s live response speed for that call, updated every 5 seconds. Colour-coded: green under 500 ms (natural), yellow 500–1000 ms (noticeable), red over 1000 ms (slow). When available it also shows a small breakdown — S (speech recognition), L (the AI model) and T (voice generation) — so you can see which part is taking the time.
  • Created: when the room (i.e. the call) started.
  • Empty Timeout: how long the room will wait with nobody in it before closing itself automatically.
  • Node: which server is handling the call — only meaningful on Multi-Cluster installations with extra capacity servers. A single-server system always shows Main.
  • Search box: type to filter the list by room name.

Retain Room — keeping ended calls visible

By default, ended rooms disappear from the list. The Retain Room dropdown controls how long they stay visible after finishing: Hide, 30s, 60s, 2min, 5min or 10min. Pick your preference, then click the green tick to save it permanently. A short retain time is handy for confirming a call really ended; a longer one is useful when you’re testing.

Creating a room manually

You’ll rarely need this — but the Create Room button lets you make a room by hand:

  • Room Name: required, and must be unique — two rooms can’t share a name.
  • Empty Timeout (seconds): how long the room waits with nobody in it before deleting itself automatically.
  • Max Participants: an optional cap on how many people can join.
  • Metadata (optional): a technical field for attaching extra information to the room — safe to leave empty.

Room details

Click a room name to open its detail view. For a live call you’ll see:

  • Call cards: the Agent handling the call, the Caller, the Direction, the running Duration, Turns (how many back-and-forth exchanges so far) and the call’s live Health score.
  • Live Performance: the call’s response-speed figures (the same measure as the Live TTFB column), updating while the call runs.
  • RTC Connection Stats: technical connection-quality numbers — click Refresh Stats to load them, or flick the Auto-refresh switch. Useful when a caller reports choppy audio.
  • Participants: everyone in the room, with their Identity, Name, connection State, audio/video Tracks (a struck-through icon means muted) and when they Joined. A Kick button removes a participant from the call — use with the same care as deleting a room.
  • Generate Join Token: a technical option that creates a temporary pass for joining the room from another app. Most operators never need it.

A room that has already ended shows a Session Summary instead — live stats and participant management aren’t available once the call closes.

⚠Careful with Delete: deleting a room immediately closes it and disconnects everyone in it — if it’s a live call, you are hanging up on the caller. Only delete a room if you genuinely need to force a call to end.
ℹLooking for past calls? The Rooms page is only about right now. For anything that already finished — transcripts, summaries, recordings — use Call History.

Call History — every call, kept and analysed

The full record of every call your agents have handled, with AI summaries, transcripts and response-speed stats.

Open Call History in the sidebar. Every finished call appears here automatically — phone calls, browser test calls, everything — usually within a minute of hanging up, once the AI has written its summary.

Finding a call — the filters

  • From Date / To Date: limit the list to calls between two dates.
  • Agent: show only calls handled by one agent (or All Agents).
  • Direction: Inbound (someone called you), Outbound (your system called them), or All Directions.
  • Status: filter by the review status on each call — e.g. Needs Review, Reviewed, Resolved, Flagged, Escalated, Callback, Agent Issue or In Progress.
  • Health: filter by the call’s health score (Excellent / Good / Fair / Poor / Critical / Not Scored) — a quick way to jump straight to the calls that went badly.
  • LLM Model: show only calls answered using a particular AI model.
  • Sort by: Newest first (default), or by cost — high to low or low to high.
  • Search: type a phone number or Call ID to find a specific call.

What each row shows

  • Time / Duration: when the call started and how long it lasted.
  • Call ID: the call’s unique reference — click it to copy the full ID to your clipboard (handy when reporting a problem).
  • From / To / Direction: the two phone numbers and whether the call was inbound or outbound.
  • Agent: which agent answered, with a small badge underneath showing the AI model that was used. A purple Test badge marks browser test sessions (billed, but excluded from analytics totals); a red Failed badge appears if the call failed its success checklist (Improvement Lab scoring).
  • Cost: the call’s estimated cost, with a small badge explaining how it was worked out — actual (computed from real usage figures), est. (estimated from per-minute averages), or Legacy pricing (an older call whose cost was stored under the previous pricing model and is preserved unchanged). Click the column’s arrows to sort by cost.
  • TTFB: the call’s average response speed (see the Latency Metrics card below).
  • Health: the call’s health rating — Excellent / Good / Fair / Poor / Critical — a quick quality score based on response speed and technical warning signs during the call.
  • Transcript / Summary: small indicator icons that light up when the call has a transcript and an AI summary. If your system includes the Improvement Lab, recorded calls also show a shortcut next to the transcript icon to replay the call there.
  • Status: the review status badge you (or your team) have set on the call — new calls show Needs Review.

Bulk actions & export

  • Checkboxes: tick individual calls, or use the header checkbox to select everything visible on the page.
  • Delete Selected: permanently removes the ticked call records (any recordings are left in place). There is no undo, so double-check before confirming.
  • Delete with Recordings: removes the ticked call records and their audio recordings in one go — also permanent.
  • Export Selected / Export Recent (CSV / JSON): download the ticked calls, or your recent calls, as a spreadsheet-friendly CSV or a JSON file.
ℹFor reporting integrations: every new call record now includes transfer information — how many transfer attempts the agent made, the destination, and whether the transfer tool reported completing the handoff. Systems reading calls through the dashboard’s API (MCP list_calls) can build a “which calls transferred where” report from one request instead of opening every call individually. Older calls made before this feature simply don’t carry the fields.

The Latency Metrics card

Near the top of the page is a collapsible Latency Metrics card — click it to expand (the data loads when you open it). It shows how fast your agents have been responding across all calls:

  • Avg TTFB: the average pause between the caller finishing a sentence and the agent starting to speak.
  • P50: the middle value — half your calls responded faster than this, half slower. A good “typical” number.
  • P90: 90% of calls were faster than this — shows what your slower calls look like.
  • P99: 99% of calls were faster than this — catches the worst-case outliers.

The card also includes a doughnut chart splitting the delay between speech recognition, the AI model and voice generation, an hourly trend chart (with 24-hour / 7-day / 30-day views), and a per-agent comparison table. If calls slower than 1000 ms are detected, a warning appears — the target is under 500 ms for natural conversation.

ℹHow long is history kept? Forever, by default — nothing is deleted unless you set a retention period in Settings → Storage. There you can choose to delete call records after a number of days, separately for this server and for cloud storage.

Call detail — inside a single call

Click any call in the list to open its detail page: summary, transcript, recording, costs and more.

The page is split into tabs: Overview (details, recording, costs, health, status and notes), Conversation (the full transcript, with a message count on the tab), Summary (the AI’s analysis — a “Not generated” badge appears if it hasn’t been written yet, with a button to generate it), and Memory (only shown when the agent used long-term memory during the call).

What you’ll find on the page

  • AI Call Summary: a plain-English write-up of the conversation — what the caller wanted, what happened, the caller’s intent, key information captured, action items, and an outcome classification.
  • Key topics: the subjects discussed, extracted automatically.
  • Reasoning tokens: when the agent’s model does hidden “thinking” (reasoning models), the LLM cost line shows how many of the output tokens were spent on it. It is informational — those tokens are already inside the output line, so nothing is charged twice.
  • Answered by: on outbound calls made by an agent whose Outbound Call Detection uses LiveKit answering-machine detection, a badge next to the direction says who picked up — Person, Voicemail, Mailbox unavailable, Phone menu or Unknown. Hover it for the detail: how the verdict was reached, how long after the answer it was decided, and which action the agent took. Calls that used the classic method, and inbound calls, have no badge.
  • Caller Sentiment Journey: a small sparkline chart tracking the caller’s mood from the start of the call to the end, with a trend indicator (improving / stable / declining). A call that starts angry and ends happy is a win.
  • Conversation quality: appears under the outcome and sentiment badges once Call quality judges is switched on in Settings → AI Summary. Each judge (safety, relevancy, task completion…) gives a PASS / MAYBE / FAIL with a one-line reason, produced by LiveKit’s evaluation judges reading the transcript a few minutes after the summary. A FAIL here also puts the call at the top of AutoResearch’s problem list.
  • Interruption Analysis: estimates how often people talked over each other — “User interrupted AI” vs “AI interrupted User” counts, with a warning if the rate is high.
  • Transcript: the full conversation with speaker labels and timestamps, colour-hinted by sentiment. Long calls can be expanded and collapsed.
  • Tool calls (purple): when the agent used a tool during the call — hanging up, transferring, sending an SMS, checking the time — it appears inline in the transcript with purple styling, showing the tool’s name, what it was asked to do, and the result.
  • Recording playback: if the call was recorded (Auto-Record on the dispatch rule), a player appears so you can listen right on the page.
  • Latency Breakdown: this call’s own response-speed figures — a visual bar splitting the delay between speech recognition, the AI model and voice generation, with percentiles and turn count.
  • SIP codec: for phone calls, the audio codec negotiated with your phone provider (e.g. G.711 µ-law, G.722 HD) — useful when diagnosing audio quality.
  • Agent Configuration: the Voice Pipeline the call actually ran — which speech-recognition, AI-model and voice providers were in play — useful when comparing calls made before and after a settings change.
  • Call Cost: what this call cost, broken down by service, including any auxiliary costs (the AI summary, knowledge-base lookups and so on). The Effective rate line shows the cost per minute, and View per-model breakdown opens an itemised list of every model the call used and what each one cost. Calls from before per-model pricing was introduced carry a Legacy pricing badge — their stored cost is preserved unchanged.
  • Call Health: a score out of 100 with a rating (Excellent / Good / Fair / Poor / Critical) and a table comparing each component — response speed and other technical checks — against its threshold, so you can see exactly which check dragged the score down. Warning flags (e.g. slow responses) appear as small badges.
  • Call Status: set a review status on the call — Needs Review, In Progress, Reviewed, Flagged, Agent Issue, Callback Requested (with fields for the phone number, preferred time and notes), Escalated or Resolved. The page records who set it and when, and the Status filter on the list page uses these values.
  • Notes: add your own notes to the call — e.g. “followed up by phone 2pm” — so the team knows it’s been dealt with.
  • Agent Observability: where enabled, a technical timeline of everything the agent did during the call — each listening, thinking and speaking step with its timing. Mostly useful when diagnosing a slow or misbehaving call.
  • Memory tab: when the agent uses long-term memory, this tab lists the memories it recalled at the start of the call and any new memories it saved from the conversation.
💡Tip: the detail page is the best place to understand why an agent behaved the way it did. Read the transcript, check the tool calls, then adjust the agent’s System Prompt if needed.

Walkthrough: investigate a bad call in five minutes

Someone says “the agent messed up my call this morning”. Here’s the routine:

  • Step 1 — find it. Filter by the agent and this morning’s date, or search the caller’s number. A red/unusual End Reason often flags the right row instantly.
  • Step 2 — read the summary first. The AI summary and sentiment give you the 20-second version of what happened before you commit to the full transcript.
  • Step 3 — read the transcript at the failure point. Find the turn where it went wrong. Was the caller misheard (the transcript shows wrong words)? Did the agent say something wrong (prompt problem)? Did a tool fail (check the tool calls and their results)?
  • Step 4 — listen if it’s a hearing problem. Play the recording next to the transcript. If the caller clearly said “Broadbeach” and the transcript says “broad bench”, that’s a speech-recognition fix: add the word to the agent’s vocabulary, or take the call into the Improvement Lab’s STT Lab to test better settings on this exact audio.
  • Step 5 — fix in the right place. Wrong words → Speech Recognition tab (vocabulary). Wrong behaviour → System Prompt (prove the fix by replaying this call in the Simulation Workbench). Tool error → the tool’s configuration or the external system it calls. Slow replies → check the call’s latency numbers and consider a faster model.
  • Step 6 — guard it. One click on Create simulation test from this call turns the failure into a permanent regression test.

Recordings stored on your own server. Each row shows the filename, agent, date, duration and file size, with per-recording actions:

Reports — automatic emails about your calls

Have the system email you (or your team) automatically — after every call, or as a daily/weekly digest.

Open Reports in the sidebar. A report is a rule that says: when this happens, send an email (or webhook) with this information to these people. Once set up, it runs by itself.

ℹEmail must be set up first: reports send through the email service configured in Settings → Email. If email isn’t configured yet, the page shows an “Email not configured” warning and no reports can be sent. Also set the Dashboard Public URL in Settings so links inside the emails work.

The reports list

  • Name / Trigger / Agents / Recipients: what the report is, what sets it off (Post-Call, Post-Analysis or Scheduled), which agents it covers, and who receives it.
  • Active toggle: switch a report on or off without deleting it — handy for pausing a noisy report.
  • Delivery: whether it goes out by email or webhook.
  • Last Sent / Runs: when it last fired, and a history of what’s been sent (with sent/failed status) so you can confirm it’s working.
  • Actions: edit or delete the report. Deleting cannot be undone.
  • Recent Executions: below the list, a log of every send attempt — the Report, its sent/failed Status, the Agent and Trigger involved, the Recipients, any Error message (why a send failed), and the Time. Your first stop when a report doesn’t arrive.

Creating a report

1 Name it and pick a trigger

  • Report Name: anything that helps you recognise it later, e.g. “Daily summary to management”.
  • Trigger Type: what makes the report send. Post-Call Summary sends an email after each call ends, with call details, the transcript and a cost breakdown. AI Conversation Analysis sends once the AI has finished analysing a call, including the summary, sentiment, caller intent and any extracted data (you can choose Data Extraction Fields to include). Scheduled Summary sends a digest of aggregate call statistics on a schedule instead of per call. You may also see event-driven types: Campaign Completion Report (sends when an outbound campaign finishes, with its results), AutoResearch Complete (sends when an AutoResearch run on an agent finishes), LLM Auto-Failover Alert (warns you when the dashboard switches to a backup AI provider because the primary is unhealthy), and Widget Abuse — Daily Limit Reached (warns you when a website chat visitor hits the daily message cap).

2 Choose which calls it covers

  • Agent Filter: All Agents, or Specific Agents — then tick the voice agents and/or chatbot agents to include.
  • Direction Filter: All Directions, Inbound Only or Outbound Only. (Chatbot conversations count as inbound.)

3 Set the schedule (Scheduled Summary only)

  • Frequency: Daily or Weekly.
  • Day of Week: for weekly reports, which day it goes out.
  • Time (UTC): the send time. Note this is in UTC (world time), not your local time zone — adjust accordingly.

4 Choose how it’s delivered

  • Delivery Method: Email (the usual choice) or Webhook (sends the report data as JSON to a web address — for connecting to other systems).
  • Recipients: the email addresses that receive the report — add as many as you like.
  • Email Template: which email design to use. Templates are customised in Settings → Email.
  • Webhook options: if you chose Webhook — the Webhook URL, the authentication type (None, Basic Auth, Bearer Token or API Key Header), any custom headers, and which fields to include in the payload.

Save the report and make sure its Active toggle is on. Done — it now sends itself.

💡How it works behind the scenes: when a call ends (or its AI analysis finishes), the system checks your report rules within about 30 seconds and sends any that match. Scheduled reports fire when their set time comes around. If a report doesn’t arrive, check the Runs history for a failed status, and confirm email works in Settings → Email.

What arrives in each email type

  • Post-Call Summary: one email per call — who called, which agent answered, direction, duration, the end reason, the full transcript, and the call’s cost breakdown. Best sent to whoever follows up on calls.
  • AI Conversation Analysis: arrives a little after the call, once the AI has analysed it — the summary, sentiment, the caller’s intent, the success/failure assessment, and any Data Extraction Fields you selected (the callback number, the order reference…). This is usually the more useful per-call email.
  • Scheduled Summary: the digest — call volumes, durations, cost totals and per-agent activity for the period since the last one. Best for managers who want the shape of the day, not every call.
  • Event alerts (Campaign Completion, AutoResearch Complete, LLM Auto-Failover, Widget Abuse): short notifications that the named thing happened, with a link into the dashboard for the detail.

Walkthrough: a daily management digest in two minutes

  • Step 1: confirm Settings → Email shows a working sender (send the test email there if unsure).
  • Step 2: Reports → New Report → name it “Daily summary”, Trigger Type Scheduled Summary.
  • Step 3: Agent Filter All Agents, Frequency Daily, pick a Time (remember it’s UTC — e.g. 21:00 UTC for a 7am AEST inbox).
  • Step 4: Delivery Email, add the recipients, save, check the Active toggle is on.
  • Step 5: next morning, confirm it arrived; if not, the Recent Executions log’s Error column tells you why.

Walkthrough: feed call results into another system (webhook)

  • Step 1: in your other system (CRM, n8n, Make, Zapier, a spreadsheet automation), create an incoming-webhook and copy its URL.
  • Step 2: New Report → Trigger AI Conversation Analysis (so the payload includes the summary and extracted data), pick the agents it covers.
  • Step 3: Delivery Webhook → paste the URL, set the authentication your endpoint expects (None / Basic / Bearer / API Key Header), and tick which fields to include in the payload — fewer fields = simpler to handle on the other side.
  • Step 4: save, make a test call to the agent, and watch the Recent Executions log — a green sent status means your other system received the data; a failed one shows the exact error the endpoint returned.

n8n Failsafe Wizard

The Failsafe Wizard button (top of the Reports page) builds a safety net for lost leads: when a caller hangs up before their booking or enquiry is completed — the line drops, they give up mid-way, the tool never runs — an n8n workflow emails your team the caller’s details so someone can ring them back. If the booking or cancellation tool did run successfully, or the caller was transferred to a person, nothing is sent. The wizard creates both sides in one pass: a post-call report with webhook delivery already configured (address, security key, field list), and a matching n8n workflow file you download and import — guaranteed to fit together.

  • Failsafe (tool check): rule-based. You tick which of your tools mean “the call was handled” (your booking / cancellation / enquiry tools). An alert goes out only when none of them completed successfully — a tool that ran but failed still alerts, because that lead is still lost. Optionally, AI reads the transcript and puts the caller’s name, spoken phone number and request into the email.
  • Failsafe (AI classify): an AI reads each missed call and decides whether the request was completed before emailing. When in doubt it emails — better a duplicate alert than a lost lead. Needs an AI (OpenRouter) credential in n8n.
  • Enquiry keywords: optional comma-separated words (booking, quote, hire …). If set, only calls mentioning one of them alert — keeps wrong numbers out of your inbox.
  • Handoffs: by default a hand-over to another AI agent does NOT count as handled — the second agent still has to complete the booking, so the alert still fires if it doesn’t. A checkbox flips this if you prefer. Transfers to a human always count as handled.
  • Withheld numbers: a caller with a hidden caller ID who says their number out loud is still alerted on — the AI pulls the spoken number from the transcript.
What happens automatically: the report is enabled the moment you click Create, so until you import and activate the workflow in n8n, Recent Executions shows failed rows — that’s expected, not broken. Once active, alerts arrive about 1–2 minutes after a call ends (the dashboard checks for finished calls every 30 seconds). Use the Send test event button on the wizard’s finish page, then look at n8n → Executions.
Changing things later: alert recipients live in the workflow’s Config node — edit them directly in n8n. To rotate the security key, edit the report’s API Key value, save, then re-download the file (the button on the report’s row) and re-import it in n8n. To change the wizard’s other settings (tools, keywords, thresholds), re-run the wizard — then delete the old report here and deactivate the old workflow in n8n, or you’ll get two alert emails per missed call. Renaming the report renames the workflow in the next downloaded file. Leave the report’s webhook field list as the wizard set it — the workflow reads exactly those fields.
Privacy: with AI extraction on, the call transcript is sent to OpenRouter through your own n8n credential. The downloaded file contains only the values you typed into the wizard plus the report’s security key — treat the file itself as confidential.

CDN & Access sub-tab

Only relevant if you put something in front of your dashboard — a CDN such as Amazon CloudFront or Cloudflare, or a load balancer. If you haven’t, leave everything on this sub-tab alone. Both switches are off by default and change nothing until you turn them on.

Behind a CDN or load balancer

When a CDN sits in front, every visitor arrives wearing the CDN’s address instead of their own. Your dashboard then sees thousands of people as one visitor — which breaks IP allow-lists, makes the audit log name the wrong person, and can get the CDN itself blocked, locking out everybody at once. Turning this on makes the dashboard read each visitor’s real address instead.

  • Read visitor addresses from forwarded headers: the main switch. Off means the dashboard uses the address the connection came from (correct when nothing is in front of it). On means it reads the real visitor address that your CDN passes along.
  • Service in front: choose Amazon CloudFront or Cloudflare and the dashboard fetches that service’s current address ranges for you when you save, filling in the box below. Choose Enter ranges manually if you use something else.
  • Trusted IP ranges: the addresses your CDN sends traffic from, one per line. Only list ranges belonging to your own service — anything listed here is trusted to say who the visitor is. The dashboard refuses ranges that are too broad, because a wide-open list would let anyone claim to be anyone.
  • “Your address is currently seen as…”: what the dashboard thinks your address is right now. If that isn’t your real address, the ranges above aren’t matching yet. Note this is a hint, not proof — it can look correct even when the ranges are wrong, which is why saving runs its own checks.
ℹTwo things happen automatically when you save. Any blocks previously placed on your CDN’s own addresses are cleared — they were wrong by definition — and the dashboard refuses the save outright if it would lock you out of your own IP Lock list.
Block direct access to this server

Your server has its own public address, and it cannot be hidden — it appears in public certificate records, in historical address lookups, and in internet-wide scans. Anyone who finds it can go straight to your server and skip the CDN, along with every protection the CDN was providing. This makes your CDN add a secret code to every request it passes on, and the dashboard refuses anything that arrives without it.

  • Direct access: the mode. Off — everything is allowed, as today. Log only — nothing is refused, but requests arriving without the code are counted for you. Always start here and leave it a day. Block — requests without the code are refused.
  • Header name: the name of the secret code your CDN adds. The default (X-Origin-Verify) suits almost everyone. Letters, numbers and hyphens only — never underscores, because web servers quietly discard those. The dashboard also rejects names that CDNs refuse to add, so you can’t pick one that would silently never arrive.
  • Secret value: the code itself. Press Generate for a strong one, Copy to put it on your clipboard, and the eye icon to show or hide it. Paste this exact value into your CDN.
  • “This request arrived with the header”: tells you whether the page you’re looking at right now came in carrying the code. This is your green light — when it says yes, your CDN is genuinely configured correctly.
  • Counters: while in Log only mode, how many requests arrived without the code — split into those that came through your CDN (which would mean your CDN stopped adding it) and those that reached the server directly (the traffic this feature exists to stop). It also lists a few recent examples so you can check each one before switching to Block.
  • Recovery code: your way back in if blocking ever shuts you out. Save it somewhere outside the dashboard — a password manager, or written down. To switch blocking on you must paste it back into the confirmation box, which is simply proof that you have a copy.
  • How to add the header to your CDN: click to expand step-by-step instructions for CloudFront and Cloudflare.
ℹYou cannot switch Block on by accident. The dashboard refuses to arm it until the page you’re on has itself arrived carrying the code — so it can only be turned on once it demonstrably works. And while it’s on, the dashboard quietly checks itself every ten minutes; if the code ever stops arriving — say someone edits the CDN settings months from now — blocking switches itself back to Log only and you get an email. Your dashboard stays reachable.
⚠Before switching to Block, check what breaks. Anything that reaches your server without going through your CDN stops working — an uptime monitor pointed at the raw server address, or an integration using it instead of your web address. Log only mode lists them for you, which is exactly why it exists. Also note most plain load balancers, including Amazon’s ALB, cannot add a header at all, so this option won’t work behind one.
ℹIf you ever get locked out. Go to /origin-recovery on your dashboard address, enter the recovery code, and blocking drops back to Log only immediately. Only the main administrator can switch blocking on in the first place.

AWS Bedrock Service Tier (inside the AWS card)

Amazon offers three processing tiers for its Bedrock AI models, and this dropdown picks which one your dashboard asks for on every Bedrock call:

  • Standard (default): normal price, normal speed. The right choice for almost everyone.
  • Priority: roughly 1.75× the cost for up to ~25% faster responses — worth considering if your Bedrock-powered agents feel slow and the extra spend is acceptable.
  • Flex: roughly half the cost with slower, variable response times — suits background work more than live phone calls.
  • Applies per model, automatically: Amazon only offers Priority/Flex on some models. The dashboard quietly checks each Bedrock model you use and applies the tier only where Amazon supports it — models that don’t support it simply run on Standard. Your calls can never fail because of this setting.
  • The first call after changing it: when you switch tiers, the very first call on each Bedrock model runs on Standard while the dashboard verifies that model’s support in the background; the tier kicks in from the next call. This happens once per model and you won’t notice it.
  • Realtime models are excluded: Amazon doesn’t support tiers on Nova Sonic realtime — it always runs Standard regardless of this setting.
As of mid-2026, Amazon offers Priority/Flex mainly on the open-weight models (Qwen, Kimi, DeepSeek and friends) — the Claude and GPT models on Bedrock don’t support tiers yet, so they keep running on Standard even with Priority selected. Amazon is expected to expand support over time, and the dashboard picks that up automatically — no update needed. In the rare case a warning appears under the dropdown saying the setting is being ignored, your install’s AWS software can’t express tiers at all — everything still works normally on Standard.
SLNG.ai Regions (inside the SLNG.ai card)

SLNG.ai is a speech gateway — one API key that fronts many transcription and voice engines (Deepgram, Rime, Cartesia, Soniox, Sarvam and more). The two dropdowns on its card pin where your audio is processed:

  • STT Region: where speech recognition runs. Australian installs should pick Sydney (GCP); Indian installs Mumbai (GCP).
  • TTS Region: where the agent’s voice is generated. Australian installs should pick Sydney (AWS); Indian installs Mumbai (GCP). The two Sydney entries are different data centres — follow the recommendation next to each option.
  • Auto (nearest): leaves routing to SLNG. Everything works, but audio may be processed overseas and answers arrive a little slower.
  • Only some models live in your region. SLNG runs its flagship models (Deepgram Nova 3 EN and Rime Arcana 3 EN — the defaults) in Sydney and Mumbai; most other models are hosted centrally. When you pin a region, the agent editor shows a note next to any model that would be processed elsewhere — e.g. “routes within Asia-Pacific” or “routes via nearest overseas region” — before you pick it.
  • Calls never fail because of the pin. If a chosen model isn’t hosted in your pinned region, the dashboard automatically lets SLNG serve it from its nearest hosting location (staying on your continent where possible) instead of failing the call. Models that ARE hosted in your region always stay there.
  • Some region options host nothing: entries marked “currently hosts no SLNG models” are valid choices but every model will route elsewhere until SLNG adds capacity there.
The green Test button on the SLNG card only checks your API key — it can’t tell whether a particular model is available in your pinned region. Trust the notes in the agent editor’s model dropdowns for that.
ℹSaving restarts the agent service automatically. When you save changed provider keys, the background agent service restarts itself so calls use the new keys. This takes a few seconds — avoid saving in the middle of an important live call.

Settings → Security

An automatic bouncer for your dashboard — repeat offenders get banned without you lifting a finger.

Because your dashboard is reachable from the internet, bots will occasionally probe it. The Security tab runs an industry-standard protection system that watches for suspicious behaviour — repeated wrong passwords, made-up email addresses, vulnerability scans, request floods — and temporarily bans the offending internet address (IP) automatically.

Account Security

  • Authentication Security: enable or disable Two-Factor Authentication for your login. Strongly recommended: even a leaked password is useless without the authenticator-app code.
  • Widget Abuse Protection: caps how many website-widget chat sessions a single visitor can start per day (0 = no cap). Stops a bot or a bored visitor running up your AI bill through the public chat widget.

Dashboard Access Lock (IP allowlist)

  • What it does: when it is on, only the internet addresses you list can open the dashboard at all — including the login page. Everyone else sees a plain “access restricted” message.
  • Adding addresses: enter an IP address, a range, or a hostname with an optional label, or click Use My IP to add the connection you are on right now. Save with Save Access Lock.
⚠Read this before turning it on. If your internet address changes (many home and small-office connections change theirs periodically) you will be locked out, and the same applies after restoring a backup onto a different server. Getting back in then needs someone with SSH access to the server. Add a stable address, or a whole range, before you switch it on.

IP Protection (Fail2ban)

  • Protection Status: confirms the protection system is installed and running, and how many addresses are currently banned.
  • Banned IPs: the current ban list, with the reason each address was banned. You can unban an address manually, or use Manual Ban to block one immediately.
  • Whitelisted IPs: addresses that will never be banned. Add your own office/home IP here so you can’t lock yourself out during testing. Addresses added automatically from your phone-carrier trunks are marked “SIP only” — they’re exempt from phone-traffic bans but still subject to login protection.
  • Protection thresholds: how many failed attempts trigger a ban and for how long — separate rules for wrong passwords, invalid emails, vulnerability scanners, request flooding, and repeat offenders (who get much longer bans). The defaults are sensible; only tune them if you have a reason.
  • Security logs: a record of security events for review.
⚠Locked yourself out? It happens — usually from mistyping your own password a few times before whitelisting your IP. Bans are temporary (most expire in 30 minutes), so the simplest fix is to wait, or connect from a different network (e.g. your phone’s hotspot) and unban yourself from this tab.

Settings → System

  • Suggested Resource Allocation: the dashboard looks at your server’s actual CPU and memory and recommends how much to allocate to each service — the dashboard, the LiveKit media server, the agent worker, and the rest. Services marked editable let you adjust their CPU and memory limits right here. Applying the suggestions on a fresh install stops one busy service from starving the others; revisit them if you upsize the server or your call volume grows.
  • Gauges: CPU, memory, and disk usage for the whole server. If memory or disk run consistently near full, it’s time to tidy up recordings or upsize the server.

  • Log Files — Delete logs after: how long the server keeps its own diagnostic logs. The default is 60 days, and you can choose anything from 7 days up to a year. Longer is useful if problems tend to get reported to you days after they happen.
ⓘLog files are not your call history. This setting only affects the server’s own technical logs — the behind-the-scenes record used for troubleshooting. Your calls, chat conversations, transcripts and recordings are controlled separately on the Storage tab, and are kept forever unless you choose otherwise there. Changing the log setting never deletes a call.
⚠Why there is no “keep forever” option for logs. Logs are written constantly, so with no limit they would eventually fill the server’s disk — which takes the whole dashboard down and is not something you could fix yourself. Each log file is also capped in size on top of the time limit, so a very busy server may keep less than the period you pick. Because of that, the page shows you the oldest log entry you actually have right now rather than just repeating the number you chose — that figure is the real answer. Old logs are tidied up once a day in the early morning, in the timezone you set under Time & Date.
  • Per-service logs: pick a service and read its recent log output right in the browser — the first place to look when something behaves oddly.
  • Download: save a log file to send to support.

During installation the dashboard downloads the update, applies it, and restarts itself — your browser shows progress and reconnects automatically when it’s back (typically a minute or two). Calls in progress on the agent service are the only thing to be mindful of: pick a quiet moment.

Settings → Finance → Pricing

The rates behind every cost figure in your analytics.

Every call’s cost shown in Analytics and Call History is calculated from the rates on this tab. Each AI model has its own row — a call using a budget model is priced at the budget model’s rate, not a blended average — so your reports track closely to the real provider invoices.

  • Provider Pricing table: every model the dashboard knows, grouped by provider, with its rate — per million tokens for AI brains, per minute for speech recognition and realtime models, per million characters for voices, and per minute of avatar video for the chatbot Avatar Providers group. A note on each row shows whether it’s the system default or your own override.
  • Avatar Providers group: one row per chatbot avatar service (D-ID, Tavus, Beyond Presence, LiveAvatar, Anam, Simli, Avatario), billed per minute from the moment the avatar’s video appears until the chat ends or the avatar drops. The rows arrive at each provider’s entry-level plan rate so costs are never under-stated; Edit a row if you are on a bigger plan. Rows marked unverified (Simli, Avatario) have no public price list — set them from your own provider dashboard. The cost shows as an Avatar line in each session’s breakdown and in the pricing charts, reports and invoices. To stop billing a provider use the row’s Disable toggle rather than Delete — a deleted default row is re-created at the next restart.
  • Search: filter the table by model name, provider, or service type.
  • Edit: click Edit on a row to enter your own negotiated rate; Reset returns it to the system default. Rates ship pre-filled with approximate public pricing.
  • Margin settings: if you resell to clients through sub-user accounts, set a markup percentage — sub-users then see prices with your margin applied, while you see the raw cost. Different margins can be set per sub-user.
  • SIP Trunk Pricing: what your phone carrier charges you — an Inbound Rate and an Outbound Rate, both in USD per minute — so the phone-line leg of each call is included in the cost figures alongside the AI services. The rate is applied to the call’s duration and matched to its direction: incoming calls use the Inbound Rate, outgoing calls (including campaign calls) use the Outbound Rate. Leave a rate at 0 if your carrier doesn’t charge you for that direction — many plans include incoming calls free. Once set, the phone cost appears as its own SIP line in each call’s cost breakdown and fills in the SIP series on the pricing charts, which stay empty while both rates are 0.
  • Conversion Factors: the averages used to estimate a cost when a provider doesn’t report exact usage — LLM input/output tokens per minute of conversation, TTS characters per minute of call, and realtime audio tokens per minute. The defaults suit typical calls; only adjust them if your estimated costs consistently drift from your provider invoices.
  • Display Currency & Exchange Rates: rates are stored in USD, but the costs shown around the dashboard can be converted to your own currency. Pick a Display currency, then choose the FX rate source: Always 1.0 (no conversion) or Manual rates — with manual rates, the Fetch latest rates button fills in current exchange rates for you (review them, then Save).
  • Auxiliary Costs in Reports: auxiliary costs are the AI summary, memory extraction and knowledge-base lookups that happen around a call. Choose Roll into call total (the default — one combined figure per call) or Separate “AI Overhead” bucket (they’re reported as their own line, keeping the call figure to just the conversation itself).
  • Three sub-tabs: General holds SIP Trunk Pricing, the Conversion Factors and the margin settings; Provider Pricing is the per-model rate table; Currency & Reports holds the display currency, exchange rates and the auxiliary-cost reporting options.
ℹNote: these figures are for reporting — the AI providers bill you directly on their own invoices. Keeping the rates accurate here just makes your dashboards match those invoices.

Settings → Finance → Invoicing

Email each of your customers a monthly invoice for the calls their agents made — automatically.

If you resell to clients through sub-user accounts, this turns the margin you set on the Pricing tab beside it into an actual monthly bill. Once a month the dashboard adds up every call made by the agents assigned to each customer, applies that customer’s margin, adds your tax, and emails them an invoice. You do nothing.

What you need to set up

  • Enable monthly invoicing: the master switch. While it’s off nothing is collected and nothing is sent — you can fill everything else in first and switch it on when you’re ready.
  • Your business: business name, address, billing email, phone, and your tax registration. The label is free text — ABN, VAT No., GST No., EIN, whatever your country uses — so the invoice reads correctly wherever you are. Most countries require the business name and address on a tax invoice, which is why the checklist insists on them.
  • Tax: switch it on, name it (GST, VAT, Sales Tax…), set the percentage, and choose whether your prices are exclusive of tax (tax is added on top) or inclusive (tax is already inside the amounts).
  • Invoice numbers: a prefix and a starting number. Numbers run in one continuous sequence across all your customers, which is what an auditor expects. Once the first invoice is issued the starting number locks — you can’t rewind a sequence that customers already hold copies of.
  • Payment: your terms in days (used to print a due date), any wording you want under it, and your payment details — bank account, payment link, whatever your customers need to pay you.
  • Readiness: the panel on the right. Every row must be green before an invoice can go out. It checks the things that would otherwise fail quietly — most importantly that an exchange rate exists if you invoice in a currency other than USD.

How a customer gets invoiced

Three things have to be true for a customer to be billed, and all three live on the Users tab, not here:

  • They are a sub-user with an email address.
  • They have agents assigned to them — those agents’ calls are what they pay for.
  • Their margin is switched on. A customer whose margin is off is deliberately skipped rather than invoiced, because billing them with no margin would charge them exactly what the AI providers charge you.
ℹA wrong invoice is worse than a late one. If anything is unclear — a missing exchange rate, a day that hasn’t finished totalling, two agents sharing a name, or usage from an agent that isn’t assigned to anybody — the dashboard stops and tells you rather than guessing. A warning strip appears at the top of every page explaining what it needs, in plain English. Fix it and the next night’s run picks up where it left off; nothing is lost.

Once an invoice is sent

An issued invoice is frozen. The amounts, the exchange rate, your tax settings, your business details and the customer’s — all of it is copied into the invoice at the moment it’s issued. Change your prices, your tax rate, an agent’s name or even your timezone afterwards and the invoice your customer holds stays exactly as it was sent. To correct one, issue a credit note; you never edit something already in someone else’s inbox.

Costs that arrive after an invoice has gone out — a summary that finished late, for instance — are absorbed rather than added to the next bill.

⚠Your customers never see your costs. An invoice shows only the marked-up amount. Your margin percentage is deliberately kept off the document, because printing it next to the amount would let anyone work back to what you pay your providers.

Preview and Invoice History sub-tabs

  • Preview a period: pick a month and click Preview to see exactly what would be invoiced to whom — and what would be blocked and why — before anything is sent. It only looks: no invoice number is used, no email goes out, nothing changes.
  • Invoice History: every invoice that has been issued, with its number, customer, period, amount and status, so you can re-open or re-send one and see what a customer was actually charged.

When it runs

The work happens overnight in the quiet hours and pauses while calls are in progress, so it can never slow a live call. Invoices for a month go out once that month is completely settled — usually in the first days of the following month. If something is blocking it, the run simply tries again the next night, so a problem you fix on the 3rd is invoiced on the 4th.

Settings → Email

Connect a mail service so the dashboard can send reports, password resets, and notifications.

Several features quietly depend on email being configured: automated Reports, password resets for sub-users, and the take-a-message and email tools your agents use. Set it up once here.

  • Provider: SMTP (works with virtually any mail service — your host will give you the server, port, username, and password) or AWS SES (Amazon’s mail service; needs a region and access keys, and the sender address must be verified in your AWS account).
  • From Email / From Name / Reply-To: who your emails appear to come from, and where replies go.
  • Test Email: sends a real test message to prove the configuration works — always do this before relying on reports.
  • Notifications: which system events email you. The important ones: Service Down Alerts (a core service has stopped — switch this on), and the host and per-service resource alerts that warn you when the whole server, or one individual service, runs unusually hot on CPU or memory for a sustained period. Each alert has sensible thresholds and a cooldown so you get one useful email, not a flood.
  • Templates: the look and wording of system emails. System templates (password reset, test email) can be edited but not deleted; you can also create your own custom templates for reports and notifications. Templates support {{variable}} placeholders for dynamic content — the available variables are listed next to each template — and {{#variable}}...{{/variable}} blocks that only appear when a value is present.
  • Email Log: the last 100 emails the system sent, each marked sent or failed — your first stop when someone says “I never got the report”.

Settings → Storage & Backup

Where your call data and recordings live, how long they’re kept — and your safety net.

Storage sub-tab — the at-a-glance panel

The top of the tab shows the whole picture before you scroll: three badges showing which backend each storage area currently uses (Call & Chat History, Recordings, Observability — each reading Local (disk), AWS S3 or Google Cloud), and six counters showing how many records each area holds locally and in the cloud. Cloud counters are cached and refresh roughly every five minutes, so a just-finished sync can take a moment to show up.

Call & Chat History Storage

Controls where call and chat session records (summaries, transcriptions, call details) live.

  • Storage Location: Local (Redis) keeps records in the server’s own database; AWS S3 / Google Cloud store them permanently in your own bucket. The cloud options show a “Not Configured” badge and can’t be selected until you add cloud credentials on the Integrations/API tab.
  • Daily clean-up time: when this section’s daily deletion run happens, in the time zone from Settings → Time & Date. Only matters once a retention rule is set — nothing is ever deleted while retention is “Keep forever”.
  • Call History Retention — on this server: (shown when Local is selected) “Keep forever” (the default) or “Delete after…” a number of days (1–3650) after the call. Covers voice call records and transcripts on this server; chatbot & SMS history has its own rule in the Chat History card below.
  • Call History Retention — in the cloud: (shown when S3/GCS is selected) the same choice for records archived in your bucket, counted from the archive date. Deletion from the bucket is permanent and asks for confirmation before saving; it works on whole days, so the boundary can differ from the local rule by up to a day. Backups and diagnostics data are never touched.
  • Cloud Sync buttons: Sync to S3 / Sync to GCS copy the server’s history into your bucket; Restore from S3 / Restore from GCS copy it back. Useful for one-off archiving or after moving to a new server.
  • Browse bucket: opens your cloud provider’s console at the right folder, so you can see the archived files yourself (appears once cloud storage is configured).

AI Summary Settings (inside the Call & Chat History card)

  • Auto-generate summaries: writes an AI summary automatically every time a call completes.
  • Call quality judges: after each voice call’s summary, runs LiveKit’s evaluation judges over the transcript and stores a PASS / MAYBE / FAIL per judge (Safety, Relevancy, Task Completion by default; Coherence and Conciseness optional). Verdicts show on the call page under “Conversation quality” and feed AutoResearch’s Prioritise problem calls mode. Needs Auto-generate on; uses the same provider and model; costs roughly one summary’s worth of tokens per judge per call, shown as a separate “Call Quality Judges” line in the call’s cost breakdown (the summary Max Tokens setting does not cap judges). Only calls summarised after you switch it on are judged — history is never re-processed. Chat and SMS conversations are not judged yet.
  • Lock summaries: hides the Regenerate and model-selection controls on each call’s Summary tab, making summaries view-only — handy when staff shouldn’t re-run them.
  • Default Provider / Default Model: which AI service and model write the summaries. Only providers with an API key configured on the Integrations tab appear here. Summaries aren’t live phone calls, so a slower “thinking” model is fine here — and if Australian data residency matters, the AWS Bedrock provider includes Claude Opus 5 (AU) and Claude Opus 4.8 (AU), top-tier summary models that run entirely in Sydney.
  • Generate Now: creates summaries for any past calls that don’t have one yet.
  • Advanced Summary Settings (admins only, collapsible): Summary Instructions (how to analyse the call — language, format, focus), System Prompt (the AI’s role and tone), Max Tokens (500–8000 — raise it for very long calls whose summaries get cut off), and Temperature (0–1 — lower is more consistent, higher more creative). Each prompt has a Reset to Default button.

Minimum Duration Filter (history)

  • Filter short calls from history: when on, calls shorter than the set duration (1–300 seconds) are never added to call or chat history — keeps wrong numbers and instant hang-ups from cluttering the list.

Cloud Backups (appears when history storage is Local and cloud credentials are configured)

  • Create Backup: exports call records and transcriptions to your bucket — optionally limited to a date range (leave the dates empty to back up everything).
  • The backup list: each backup shows its filename, size and date, with Restore and Delete buttons, plus a Refresh button on the card header.

Chat History

One rule covers everything on the chat page: chatbot conversation records & transcripts, website widget messages, and SMS conversations. Widget and SMS messages always live on this server (they are never sent to cloud storage). Chat history lives in server memory, so keeping everything forever grows memory use over time on busy widgets.

  • Daily clean-up time: when chatbot conversation records are cleaned up. Widget and SMS messages ignore this time — they expire exactly N days after the last message.
  • Chat History Retention — on this server: “Keep forever” or “Delete after…” days. This is a sliding rule — a conversation is removed that many days after its latest message, so active conversations are never cut off (calls use a fixed “days after the call” rule instead).
  • Chat History Retention — in the cloud: (when history storage is S3/GCS) the same choice for chatbot conversation archives in your bucket. Permanent, asks for confirmation.
  • Maximum messages per conversation: blank = keep every message (the default). If set, each widget/SMS conversation keeps only its newest messages — trimming is irreversible.

Recording Storage

Controls where call recordings (the audio files) go — the biggest storage users on the system.

  • Recording Destination: Local Server, AWS S3 or Google Cloud (cloud options need credentials on the Integrations tab first).
  • Delete local after cloud upload: with a cloud destination, removes the local copy once the upload succeeds, so recordings stop consuming server disk. Leave it off to keep a local copy as well.
  • Daily clean-up time: when this section’s retention run happens.
  • Recordings on this server: “Keep forever” or “Delete after…” days after the recording was made. Applies whichever destination is selected — local copies can still accumulate with cloud storage when “Delete local after cloud upload” is off.
  • Recordings in the cloud: the same choice for audio files in your bucket. Permanent, asks for confirmation.
  • Minimum Duration Filter — Auto-delete short recordings: when on, recordings shorter than the set duration (1–300 seconds) are deleted automatically when the call ends.

Observability Storage

Where each call’s diagnostic bundle — the event timeline, traces and correlated logs you see on the call detail page — is archived. Recent calls stay in server memory for instant loading; older calls are compressed and moved to the archive.

  • Storage Location: Local disk, AWS S3 or Google Cloud (the cloud options reuse the recording storage credentials).
  • Keep in Redis (memory): how many days of recent calls (1–90) open instantly from memory. Older calls still open — they just load from the archive with a small delay. Nothing is lost at this boundary.
  • Redis size limit: a hard cap (in MB) on the memory used. If call volume grows past it, the oldest already-archived calls are evicted from memory first.
  • Keep local files: the window for the on-disk copies. With no cloud storage, this is the archive window.
  • Keep on cloud storage: the long archive window in your bucket. After this many days a call’s diagnostics are deleted everywhere.
  • Disk Cap: a local-only safety limit (50–95% of the disk) that stops the archive from filling the server.
  • Archive Usage / Redis Usage: live gauges showing the archive’s total size (local + cloud) and current memory use against the limit, each with a refresh button.
  • Skip local fallback when cloud is configured: on by default with a cloud backend — the archive lives only in your bucket. Untick it to also keep a small (~30 KB per call) local copy of every bundle, which gives disaster recovery if cloud access is ever lost.
  • Prompts in traces: off by default — traces keep timing, token counts, model and tool names only. Switch it on to also store each LLM turn’s full system prompt, conversation and tool definitions (useful for prompt debugging; contains caller details and makes each call’s bundle much larger; each field is capped at 32 KB). Applies from the next call.
  • Pending Uploads: if any call’s archive upload fails, a warning appears here with a “Retry all” button — the data waits safely in memory until the retry succeeds.

Call Audio Processing

  • What it is: how the server processes the caller’s voice during calls. Changes apply from the next call — no restart needed.
  • 24 kHz — standard: how the system always worked before the 16 kHz option existed. Installs upgraded from earlier versions stay here until you change it; new installs start on 16 kHz for all agents.
  • 16 kHz for all agents: lighter on the server for phone calls — phone lines carry narrow-band audio, so callers hear no difference. AI providers that need 24 kHz are detected automatically and keep it, so nothing can break by choosing this.
  • Caller volume levelling (noise-cancelled calls): whether the server also levels the caller’s volume after noise cancellation. On (default) is how every call has always run; Off skips that stage, which is LiveKit’s own default since Agents 1.8.0. Our tests found no difference in recognition accuracy either way. Applies from the next call.
  • Choose per agent: adds an “Audio Processing Rate” choice to each voice agent’s editor (Speech Recognition tab → Audio Input Settings). Agents without their own choice — including chatbot and realtime agents — follow the server default shown on the option.

Call Recording Audio

  • What it is: how call recordings are made. All settings apply to new recordings only — each recording keeps the format, layout and quality it was made with, and you can switch back at any time. Changes apply from the next call — no restart needed.
  • Recording Format: OGG (recommended) is about half the size of MP4 for voice calls, and the quality tiers’ full size savings apply only to OGG; MP4 plays everywhere, including older tools.
  • Recording Channels — Mixed: everyone’s voices blended together on both channels, the way recordings were always made before Dual Channel existed.
  • Recording Channels — Dual Channel: the agent’s voice on the left channel and the caller’s on the right, in the same single file. Makes transcription diagnostics and telling speakers apart far more accurate. On headphones each party plays in one ear (a single earbud plays only one party). Needs a recent recording component — very old installs simply keep recording mixed, and the save message explains how to spot that.
  • Recording Quality: Standard keeps full quality. Efficient and Compact trade quality for smaller files — useful when recordings live on the server’s own disk. The size savings apply fully with the OGG recording format (roughly half and a quarter respectively); MP4 recordings currently shrink only slightly, a limitation of the recording component. Lower tiers also reduce Improvement Lab replay fidelity, and with Dual Channel on each party gets half the tier’s bitrate.
  • Defaults: new installs start with OGG + Dual Channel + Efficient (small files, no audible loss for phone calls). Installs upgraded from earlier versions keep MP4 / Mixed / Standard — exactly as they always recorded — until you change them here.
⚠Deletion is permanent. Once a retention rule (or a manual delete) removes a recording or call record, it cannot be recovered — there’s no recycle bin. If in doubt, leave retention on “keep forever” and rely on cloud sync for disk space instead.

Backup sub-tab

  • Download Backup: creates a timestamped ZIP containing your entire configuration — agents, users, settings, call history, credentials. Store it somewhere safe: it contains your API keys.
  • Automatic cloud backups: with cloud storage configured, schedule backups daily or weekly, choose the provider, and cap how many old backups to keep (the oldest are pruned automatically).
  • Backup Now / Restore from Cloud / Delete: run an immediate cloud backup, restore from a previous one, or clean up old ones.
  • Restore from File: upload a backup ZIP to restore it.
⚠Restore with care. Restoring a backup overwrites everything currently on the system with the backup’s contents, and the system restarts afterwards. Only restore when you mean it — ideally after downloading a fresh backup of the current state first.

Frequently asked questions

The questions everyone asks — and the quick answers.

My agent doesn’t answer calls. What do I check?

Work through these three, in order. First: is the agent started? Go to Voice Agents — the agent must show Running, not Stopped. A newly created agent never starts itself. Second: is a dispatch rule pointing at it? Go to Telephony → Dispatch Rules and check the rule for your number has this agent selected. Third: is your trunk registered? Check Telephony → SIP Trunks (and the Telephony tab on the Analytics page) — if the trunk isn’t connected to your phone provider, calls never reach the system at all.

I can’t see a page this guide mentions.

Your administrator controls which pages each user can see, in Settings → User Management. If a menu item is missing for you, you almost certainly don’t have permission for it — ask your administrator to switch it on. (Some sections, like Telephony, also only appear once the underlying feature is set up.)

My calls have no recording.

Recording is off unless you turn it on. Edit your rule in Telephony → Dispatch Rules and tick Auto-Record — every call through that rule is then recorded. Also check Settings → Storage: the storage location (Local Server, AWS S3, or Google Cloud Storage) decides where recordings land, and a retention rule may be deleting old ones.

The agent is slow to respond — there’s a long pause before it speaks.

Open the Latency tab on the Analytics page. Under 500 ms feels natural; 500–1000 ms is a noticeable pause; over 1000 ms feels broken. The breakdown chart shows where the time goes — most often it’s the AI model “thinking”. The usual fix is switching the agent to a faster model in the agent editor (smaller “fast” models respond much quicker than large reasoning models). The Rooms page shows the same numbers live, per call, while you test.

How do I change the logo and the dashboard’s name?

Settings → Server → White-Label. Upload your own logo and set your own product name — they replace the defaults everywhere, including login and this guide.

How do I add another login for a colleague?

Settings → User Management. Create a sub-user with their email address, and tick exactly which pages they may see and what they may do (view, create, delete). They receive their own login and can change their own password.

Where do I put my AI provider keys (OpenAI, Deepgram, ElevenLabs, Google…)?

Settings → Integrations. Each provider has its own card — paste the API key and save. The relevant services restart automatically, and models from that provider become selectable in the agent editor. Without a key, a provider’s models show as unavailable.

How do I update the dashboard?

When an update is available, an Update Available badge appears under Settings in the sidebar. Open Settings, find the update section, and click the update button — the system downloads, installs and restarts itself. One click; no technical steps.

What happens if I delete something?

It’s gone. Deleting calls, chats, recordings, agents or reports is permanent — there is no recycle bin and no undo. The dashboard asks you to confirm first; take that prompt seriously, especially with bulk “Delete Selected” actions and cloud recordings.

Do I need a phone number to try an agent?

No. The Agent Tester (under Testing in the sidebar) lets you talk to any started agent from your browser, in text or by voice through your microphone. It’s the fastest way to test changes before real callers hear them.

How long is my data kept?

Forever, by default — calls, chats and recordings are never deleted unless you set retention rules in Settings → Storage. There you can set separate “delete after X days” rules for call history, chat history and recordings, each with independent settings for this server and for cloud storage.

Who ended the call — the caller or the agent?

The AI Insights tab on the Analytics page has a Call End Reasons breakdown (customer-ended vs agent-ended, with a reason table), and each call’s detail page in Call History shows how that particular call finished.

My calls cut off after about 10 minutes.

That’s the agent’s Max Call Duration limit — new agents default to 10 minutes as a cost guard. Open the agent in the editor, go to the Advanced tab, and under Resource Limits raise the limit or set it to 0 for no limit.

The agent keeps mishearing names, products, or suburbs.

Three fixes, in order. First: add the problem words to the agent’s Keywords / Key Terms list on the Speech Recognition tab — telling the recogniser what to listen for dramatically cuts mishearings. Second: if callers are often in noisy places (cars, worksites, speakerphone), try a Noise Cancellation engine on the Voice tab. Third: if your system includes the Improvement Lab, its STT Lab replays a real call through different recognition setups side by side, so you can see which one hears your callers best.

The chat widget doesn’t appear on my website.

Three things to check on the chatbot’s editor page. First: the agent’s Enabled switch is on. Second: your website’s address is listed on the Domains tab (use the exact https:// address) — the widget refuses to load on sites that aren’t listed. Third: the embed snippet from the Embed Code tab is pasted just before your site’s closing </body> tag. The Preview button shows the widget working without touching your website at all.

How do I make the agent transfer callers to a real person?

Two steps. On the Tools page, assign a transfer tool to the agent — blind_transfer sends the caller straight through; attended_transfer has the agent brief the staff member privately first and comes back to take a message if nobody answers. Then, in the agent editor’s Tool Usage Instructions box, tell it when: e.g. “If the caller asks for a human, transfer them to Reception.” Outbound calling needs your phone setup in place — see the SIP Trunks section.

What happens if my AI provider has an outage?

If you’ve set up LLM Fallback on the agent’s Behavior tab, the backup provider takes over automatically — mid-call if the primary stops responding, and (with auto-failover health checks on) for new calls before anyone notices. Chatbot agents have the same fallback option in their editor. If you haven’t set up fallbacks, calls during an outage will fail — it’s worth two minutes to configure a backup from a different AI company.

How much are my calls costing me?

The Price/Cost tab on the Analytics page shows total cost, cost per call and per minute, and which agent is spending the money; each call’s detail page in Call History shows that call’s exact breakdown. Remember the AI providers bill you directly on their own invoices — these figures are the dashboard’s running estimate. The rates behind the figures are set in Settings → Pricing — keep them accurate and the dashboard will track your invoices closely.

Glossary — the jargon, decoded

Every technical term used in this guide and around the dashboard, in one sentence each.

  • Agent: an AI that talks to people for you — a voice agent answers phone calls; a chatbot agent answers typed messages on your website or over SMS.
  • System Prompt: the written briefing that defines an agent’s personality, job, and rules — the single biggest influence on how it behaves.
  • LLM (Large Language Model): the AI “brain” that understands what callers say and decides what to reply — e.g. models from OpenAI, Anthropic, or Google.
  • STT (Speech-to-Text): the service that converts the caller’s spoken words into written text for the brain to read. Also called speech recognition.
  • TTS (Text-to-Speech): the service that converts the agent’s written reply into a spoken voice.
  • Realtime model: a single AI that listens and speaks directly, replacing the separate STT → LLM → TTS relay — very natural, but less mix-and-match flexibility.
  • SIP: the standard technology that carries phone calls over the internet — the plumbing between your system and the telephone network.
  • SIP Trunk: your digital phone line — the configured connection to a phone carrier (or office phone system) that lets calls in and out.
  • Dispatch Rule: the switchboard entry that decides which agent answers calls arriving on which numbers.
  • Room: the virtual space where one call happens — the caller and the agent meet in a room, and it closes when the call ends.
  • TTFB (Time to First Byte): the pause between the caller finishing a sentence and the agent starting to speak — the key measure of how responsive an agent feels. Under 500 ms feels natural.
  • Token: the unit AI providers charge by — roughly three-quarters of a word. More talking = more tokens = more cost.
  • Knowledge Base / RAG: your uploaded documents, made searchable so agents can answer from them mid-conversation instead of guessing. (RAG is the technical name for this look-it-up-then-answer technique.)
  • Embedding: the behind-the-scenes conversion of text into a searchable form — what makes Knowledge Base search and agent memory work.
  • VAD (Voice Activity Detection): how the agent notices that someone is speaking versus background noise or silence.
  • Turn Detection: the smarter layer that judges whether a caller has finished a sentence or is just pausing mid-thought — so the agent doesn’t jump in too early.
  • Webhook: a message the system sends to another system’s web address when something happens — how the dashboard connects to CRMs and automation platforms like n8n, Make, or Zapier.
  • MCP (Model Context Protocol): a standard way to plug entire external toolkits into your agents — connect one MCP server and the agent gains all of its tools at once.
  • Egress: the technical word for capturing audio out of a call — in practice, call recording.
  • Handoff: one agent passing a live call to another agent mid-conversation — announced (a transfer) or invisible to the caller (a transition).
