          Chatbot Agents

          Create and manage AI-powered chat agents that can be embedded on any website. Each chat agent has its own personality, LLM configuration, and widget appearance.

          Agent List

          Your own software can also drive a chatbot without the widget through the REST API (Settings → Integrations → REST API → Chatbot API card) — see the User Guide, Chatbot Agents → REST API. View all configured chat agents with status (enabled/disabled). Click an agent to edit, or use the Create Agent button. Agents can be toggled on/off, duplicated, exported individually, or deleted. The arrows button (Copy to Voice Agent) makes a phone agent from a chatbot: a preview shows what carries over (prompt, knowledge, tools, memory, language model, speech settings) and what does not (widget look, avatar, SMS, allowed websites, session limits, recording), then the voice agent is created stopped for you to review. It is a one-time copy, not a link. Duplicate now also copies the chatbot's tools and knowledge-base links. Use the Export button to download all agents as JSON, or Import to restore from a previously exported file.

          Templates

          The Templates button opens eight ready-made text chatbots — the same scenarios as the voice agent templates (healthcare clinic, e-commerce support, real estate, hotel concierge, restaurant reservations, IT helpdesk, trades bookings, feedback survey), each adapted for website chat with a complete prompt, reference information, and widget styling. Template chatbots are created ENABLED and answer as soon as the widget is embedded, so the API key shown on the card must be configured first. Templates are text-only; voice can be enabled later in the editor. The Feedback Survey template enables automatic summaries for itself so its answers are captured as extraction fields.

          Voice tab

          Chat Mode (Text / Voice with avatar / Full voice) plus four sub-tabs laid out like the voice-agent editor: Speech Recognition (recogniser, model, language, turn detector, stall recovery, advanced), Voice (provider, model, voice, output volume, markdown filter, advanced), Conversation Dynamics and Recording. The sub-tab you had open is remembered; a save blocked by an invalid value on another sub-tab switches to it. Owns the Chat Mode choice (Text / Voice with avatar / Full voice) and every setting that only matters with sound. Every field shows the value the chatbot already runs with, so opening the tab and saving changes nothing until you edit a field.

          Field Description
          Chat Mode Text (type only), Voice with avatar (agent speaks, visitor types, no mic prompt), Full voice (two-way voice; the browser asks for the microphone). Voice-only widget display modes and avatars need the matching mode.
          Speech Recognition Provider, model and language, plus responsiveness, custom vocabulary, smart formatting, filler removal and language auto-detect. Chatbots offer the same recognisers as voice agents (incl. xAI Grok, Telnyx, SLNG.ai, Speechmatics and Azure OpenAI), each greyed until its key is set. Some providers (AssemblyAI, Sarvam, Speechmatics) add their own panel that appears only while selected. Speechmatics decides end-of-turn itself: a long mid-sentence pause can end the turn early — raise its end-of-utterance silence if visitors pause a lot
          STT Stall Recovery Retries a recogniser that stops responding, then apologises with the Goodbye Message. Turning it on reveals the backup recognition provider used when retries are spent.
          Voice Provider, model, voice and language, speaking speed, output volume, and per-provider extras (ElevenLabs stability/similarity, Deepgram Flux expressivity, Hume description/instant mode) shown only for the selected provider. Chatbot voices match voice agents (incl. xAI, Speechmatics preview, SLNG.ai, Telnyx Kokoro, MiniMax and Azure OpenAI).
          Voice activity detection Whether and how sensitively the agent notices the visitor speaking; min silence is the pause that ends a turn.
          Turn detection & endpointing Turn detector threshold, audio-detector patience (blank = automatic), fixed/dynamic endpointing, response delay, and the Deepgram Flux end-of-turn controls when Flux is the recogniser.
          Interruptions Words needed to cut the agent off, how long the visitor must speak, and false-interruption handling.
          Noise cancellation Full voice only. Server-side cleaning of the visitor's microphone audio (Off / WebRTC APM / DTLN / ai-coustics), echo-canceller warm-up and microphone input rate. Browsers already suppress noise — start with Off. Always off in Voice with avatar (no microphone).
          Silence re-engage Full voice only. When the visitor goes quiet the agent nudges them (ask if still there / repeat / let the AI improvise / custom text) up to a maximum number of times, then says goodbye. Already active on Full voice chatbots; these controls tune it. Always off in Voice with avatar (no microphone, so a reading visitor is never cut off). Inactivity auto-close (Session tab) still ends idle sessions in every mode.
          Generation Pre-emptive generation and speech (faster replies, slightly more usage) and prompt caching for supporting LLM providers.
          Record full-voice sessions Full voice only, off by default. Text and avatar sessions are never recorded. Recordings appear on the chat's page in Chat History (player, download, consent receipt) and on the Recording/Egress page behind 'Include chat sessions'. The transcript is kept either way.
          Recording consent Four settings. Ask first and keep chatting unrecorded if they decline (recommended). Ask first and offer text chat instead. Don't ask and show your notice as a permanent line, recording regardless. Don't ask and show nothing. In the two 'ask' modes nothing is minted and no microphone is requested until the visitor answers. In the two 'don't ask' modes the server decides from this setting and ignores what the browser claims, the consent receipt records that the visitor was never asked rather than pretending they agreed, and the chat layouts show a 'Recording' marker in the header while audio is captured. The Voice Orb and Voice Button display modes render no header, so on 'Don't ask - show nothing' those two show the visitor nothing at all. Recording without consent is unlawful in much of Australia and many other places — that call is the operator's.

          Voice Mode

          Optionally enable voice input so visitors can speak to the agent via microphone. Requires STT and TTS provider configuration. In any voiced mode the agent is automatically given spoken-reply rules on top of your prompt (short replies, no lists or symbols read aloud, natural numbers and dates, one question at a time, typed and spoken messages treated the same) — the transcript still shows every reply as text while it's spoken, and text-only sessions are unaffected.

          Field Description
          Turn Detector How the agent decides the visitor has finished speaking (voice sessions only). "Audio (v1-mini)" is recommended and the default for new chatbots — it listens to the speech itself, runs on the server at no extra memory cost. "Text model" is the older approach: it needs roughly 1 GB of extra memory for the AI Agent Service, and on smaller servers it is skipped automatically (turn-taking then falls back to simple silence detection). "Off" uses silence detection only.
          STT Stall Recovery If the speech-to-text provider stops responding mid-conversation, the agent recovers missed words, asks the visitor to repeat if needed, reconnects a dead transcription stream, and as a last resort says a goodbye and ends the session. Off by default. Voice sessions only — typed chats are never interrupted by it. You can set how long to wait before recovery starts, and your own goodbye message.
          Virtual Avatar

          Render a lip-synced talking-head video of the agent in the chat widget. The avatar provider receives the agent's voice (TTS) and republishes synced audio + video into the room. Voice Mode must be enabled for the avatar to lip-sync to. Seven providers are supported: D-ID (highest quality, slow ~5–15s warm-up, requires a v4 expressive avatar), Tavus (hyper-realistic, requires a Replica + Persona configured for LiveKit transport), Beyond Presence (fastest setup — works with a stock avatar by default), LiveAvatar by HeyGen (dynamic real-time avatars, choose a public avatar or create your own), Anam (lifelike low-latency avatars — pick a stock avatar from the gallery or build a custom one in Anam Lab), Simli (very low-latency real-time faces — pick a Face ID from the default library, optional emotion), and Avatario (720p realtime avatars with an optional custom background image). Spatius is not supported: it renders in the browser with its own SDK, which the chat widget does not load. API keys are configured once on the Settings > Integrations page; per-chatbot avatar selection is on the Avatar tab in each agent's editor.

          Field Description
          Cost Avatar minutes are priced per minute on Settings > Pricing > Avatar Providers (one row per provider, seeded at each provider's entry-tier rate — lower it if you are on a bigger plan; Simli and Avatario rows are marked unverified, set them from your provider dashboard). Metered from the moment the avatar video appears until hang-up or drop, and shown as an 'Avatar' line in the call's cost breakdown, Chat History and reports. Use a row's Disable toggle (not Delete) to stop billing a provider — deleted default rows are re-created at the next restart.
          Avatar never appears (no picture AND no voice) The provider's cloud could not reach your LiveKit server: check LIVEKIT_PUBLIC_URL is a public wss:// address and that inbound connections are allowed by your firewall. The agent log records 'Avatar never joined the room within 20 s' and the agent recovers voice-only after 20 seconds. The Integrations Test button proves the API KEY only — not that the avatar can reach your server.
          First-reply latency First message may be delayed 5–15 seconds while the avatar warms up. Subsequent replies are real-time.
          Public-URL requirement Avatar providers run in the cloud and connect inbound to your LiveKit server, so LIVEKIT_PUBLIC_URL must be reachable from the public internet (a private IP or localhost will fail). Tronic-managed dashboards already meet this.
          Failure handling If anything goes wrong (missing key, missing IDs, provider outage, plugin not installed), the agent gracefully continues voice-only — visitors still hear the agent, just without the face.
          Tavus persona setup Tavus personas must be configured with pipeline_mode="echo" and transport_type="livekit". Leave Persona ID blank to let the plugin auto-create one with these settings.

          Human Handoff tab

          Hand a chat to a person. When the visitor asks for a human (or presses the widget's 'Talk to a person' button), the chatbot says the wait message, stops answering, and sends the conversation to your Webhook URL — usually an n8n workflow that posts to Slack, your CRM or a help desk. Every later visitor message is sent there too. Your team member replies through the reply link the webhook receives (the downloadable n8n workflow includes a reply form) and the reply appears in the visitor's chat, SMS or WhatsApp with their name. When they finish, or go quiet for the set time, the chatbot takes back over and already knows what was said. There is no inbox in the dashboard.

          Field Description
          Enable Human Handoff Switches the feature and the handoff_to_human tool on for this chatbot. A Webhook URL is required.
          Webhook URL Where conversations are sent. Must be reachable from this server, and this server's address (Settings → Server) must be reachable from there for replies.
          Signing secret Every event is signed with it (X-Handoff-Signature over timestamp.body). Generated on first save. Regenerating it means updating your n8n workflow or software.
          Name shown when the person gives none Label on their replies if they don't send a name.
          While a person is being brought in / When the assistant takes back over What the visitor is told at each step. Full-voice chats read them aloud.
          Talk to a person button Adds a header button to the widget so the visitor can ask directly; hidden while a handoff is active.
          If the button can't be honoured Shown when the daily limit is reached or the chat can't be handed over right now.
          Wait for a person / Then / Never wait longer than Nobody picks up in time: either the assistant carries on (with its message) or the chat keeps waiting, but never past the hard limit.
          Person silent for The person stops replying for this long → the assistant takes back over.
          Email me when a handoff starts One email per handoff using Settings → Email.
          Handoffs per day / Visitor messages per handoff / Forwarded messages per day Abuse limits. Exceeding a message cap hands the chat back to the assistant.
          Send test event Posts a sample conversation to your webhook, then waits a minute for your side to reply to it — proves both directions.
          Build n8n workflow (Slack) Downloads a ready-made workflow (Slack post + reply form) to import into n8n.
          SMS / WhatsApp Delivery Channel

          Let visitors text (or WhatsApp-message) a phone number and get replies from this same chatbot — same LLM, same system prompt, same knowledge base, same memory. Five providers: Twilio (global), Telnyx (global), Tronic Cloud (Tronic's own gateway at text.tronic.com.au), Sent.dm (one number for BOTH SMS and WhatsApp — replies go back on whichever channel the visitor used), and Custom (n8n) for any other SMS carrier via your own n8n instance. Preset setup is one-time: paste API keys on Settings > Integrations, enable SMS on the chatbot's SMS / WhatsApp tab, pick a provider, type the FROM number (not needed for Sent.dm), and copy the generated webhook URL into your provider's console.

          Field Description
          How it works An inbound text reaches your dashboard's webhook URL → the chatbot's LLM generates a reply → the provider sends it back as SMS. The visitor doesn't need an app or website — just their phone. Webhook responses go out within ~100ms (the LLM call runs on a background task), so providers don't retry or stall.
          Memory per phone number Each phone number is treated as its own visitor. Mem0 (if enabled) remembers the conversation across SMS sessions for that phone, scoped to this agent. Website widget visitors are kept separate.
          Daily reply cap Per-(agent, phone) cap (default 50/day) prevents Denial-of-Wallet abuse. 0 = unlimited. Drops silently after the limit — the inbound is accepted but no reply is sent (logged in the operator's logs).
          Twilio setup Console > Phone Numbers > your number > Messaging Configuration. Set 'A MESSAGE COMES IN' to Webhook + HTTP POST + paste the URL from this tab. Twilio signs every webhook with HMAC-SHA1; the dashboard verifies it automatically.
          Telnyx setup Mission Control > Messaging > Messaging Profiles > your profile > Inbound Settings. Set Webhook URL to the URL from this tab (HTTP POST), API Version V2 (Ed25519). Paste the Webhook Public Key into Settings > Integrations so the dashboard can verify signatures.
          Tronic Cloud setup Sign in at text.tronic.com.au, open your number's inbound webhook setting, paste the URL from this tab. Two-way SMS requires an AU 10-digit number in international format (e.g. 61400123456) — alpha senders like 'MyShop' are send-only.
          Sent.dm setup (SMS + WhatsApp) Sign in at app.sent.dm, provision your business number, and copy your API key into Settings > Integrations > Sent.dm. In the Sent.dm dashboard create a webhook endpoint pointed at the URL from this tab, subscribe it to message.received, and paste that endpoint's signing secret (whsec_…) into the tab. There is no From number — the sender is the business number on your Sent.dm account, and one Sent.dm number belongs to ONE chatbot (configure exactly one inbound endpoint per account). For WhatsApp, connect your Meta Business account inside Sent.dm (Meta login + payment method on the Meta side). Replies automatically go back on whichever channel the visitor used. Business-initiated sends (test button, voice-agent tool) use a passthrough template the dashboard auto-creates on save. The WhatsApp channel is code-complete but not yet verified end-to-end; SMS is fully tested.
          Custom (n8n) setup Bring any SMS carrier by wiring it through your own n8n instance. Select Custom (n8n), save the chatbot (this generates a shared secret), then download the two ready-made workflows from the SMS tab — they arrive pre-filled with this chatbot's webhook address and secret. Import both into n8n, drop your carrier's node into the Send workflow, activate both, paste the Send workflow's Production URL into the dashboard, and point your carrier's inbound webhook at the Inbound workflow. A Test panel on the tab verifies the setup and can send a real test SMS.
          n8n security Custom (n8n) messages carry an X-SMS-Secret header in both directions, generated by the dashboard (16+ characters, compared in constant time). The secret is baked into the downloaded workflows — if you regenerate it, re-download and re-import BOTH workflows or they stop authenticating.
          Webhook security Twilio + Telnyx use cryptographic webhook signatures (HMAC-SHA1 / Ed25519). Sent.dm signs webhooks HMAC-SHA256 (Svix-style) with a per-endpoint secret you paste into the tab; replayed deliveries are also suppressed. Custom (n8n) uses the shared-secret header. Tronic Cloud has no signature; it relies on your webhook URL staying secret. The agent ID in the URL is opaque, so don't share the URL publicly.
          Failure handling If a key is missing, the provider's API is down, or the LLM call fails, the visitor gets no reply that turn — but nothing crashes. Errors are visible in the operator logs (sms.send.failed / sms.reply.llm_failed).
          Session Management
          Field Description
          Auto-close Inactive Automatically close sessions after inactivity period
          Inactivity Timeout Minutes of inactivity before session closes
          Inactivity Message Message shown when session is auto-closed
          Max Messages Maximum messages per session before it closes
          Max session length Ends a single chat session after this many minutes with a polite message asking the visitor to start a new chat. 0 = no limit (the default, matching how chatbots have always behaved). Protects against a session being held open indefinitely and running up AI costs.
          Reconnect Grace Period How long (seconds) the conversation room stays open after the visitor closes or leaves the page, so a quick reload rejoins the same conversation. 0 = default (~20 seconds); maximum 600. Longer windows keep sessions alive (and any per-minute costs running) after the visitor has gone.
          Error Handling What the visitor sees if the AI hits an internal error: the standard apology (default), your own custom message, or nothing at all (silent — the typing dots clear automatically). Applies to both website chat and SMS.
          Domains (CORS)

          Configure which website origins are allowed to use this chat agent. Only listed origins can request tokens. Always use https:// in production.

          Embed Code

          Copy the generated script tag and paste it before the closing </body> tag on your website. The widget will automatically appear as a floating chat icon. Use the Preview button to open a live preview showing exactly how the widget will look and behave on your site.

          Per-Session Dynamic Variables

          Your website can hand the chatbot per-visitor context by adding a data-variables attribute to the embed snippet, e.g. data-variables='{"name": "Priya", "account_number": "1253566"}'. Each key becomes a {{placeholder}} usable in the system prompt and welcome message — "Hello {{name}}, your account {{account_number}} premium is due soon." Rules: variable names are lowercase letters/digits/underscores (max 32 chars), up to 10 variables, values up to 200 characters, ~2KB total. Unsupplied placeholders are removed from the welcome message automatically. IMPORTANT — personalization only, never identity: the token endpoint is public, so any caller can claim any value. The agent must never treat a variable like {{account_number}} as verified identity or feed it to tools as an authenticated lookup key without its own verification step.

          Prompt Versioning

          Every time you save changes to an agent's system prompt, the previous version is automatically saved. You can view version history, compare differences between versions, and restore any previous version.

          Field Description
          Version History Click the green Versions button to see all saved prompt versions with timestamps and source labels (manual, enrich, or autoresearch).
          Diff View Click 'Diff' on any version to see a color-coded comparison showing exactly what changed (green = added, red = removed).
          Restore Click 'Restore' to load a previous version into the editor. You must click Update Agent to save the restored version.
          Max Versions Configure how many versions to keep per agent (5-50, default 20). Oldest versions are automatically pruned.
          AutoResearch

          AI-powered prompt optimization that analyzes your agent's actual chat session transcripts to suggest specific improvements. Lives on its own AutoResearch page in the sidebar (Testing section) — the editor's purple AutoResearch button takes you there with the agent pre-selected. Can be run manually or scheduled to run overnight.

          Field Description
          Run Analysis Select analysis steps, choose an LLM provider/model, set the number of chat sessions to analyze (5-50), and click Run Now. Progress is shown step-by-step.
          Call Selection Choose 'Most recent calls' or 'Prioritise problem calls' — the latter hunts for sessions that were abandoned, didn't achieve their goal, had negative sentiment, or where the visitor barely engaged, mixing in normal sessions for contrast.
          Suggestions Each suggestion shows what would change, which issues it addresses, and a confidence score. Amber warnings flag suggestions that dropped placeholders, shrank suspiciously, or grew too much — review those carefully. Click 'Apply to Live Prompt' to review a side-by-side comparison (editable) and apply — the outgoing prompt is saved to Versions automatically, so applying is always reversible.
          Schedule Set AutoResearch to run automatically (daily or weekly) at a specific time, including the call-selection mode. Suggestions are never auto-applied — review in Results History.
          Reference Sessions Curate your best chat sessions as benchmarks. AutoResearch uses these to score suggestions and ensure they don't make good interactions worse.
          Methodology Advanced: customize the analysis, suggestion, and scoring prompts that drive AutoResearch.
          MCP / API Access

          External tools (Claude Code, Cursor, scripts) can manage chatbot agents through the built-in MCP server at /mcp: list_chatbot_agents, get_chatbot_agent, create_chatbot_agent, update_chatbot_agent, delete_chatbot_agent. Every field on this page is editable over MCP — including the widget appearance, avatar provider, memory settings, and the SMS / WhatsApp channel (stored secrets are preserved when a field is left empty, exactly like this editor). Ask your MCP client to call get_agent_config_reference() and read the chatbot_agents section for the full schema.
